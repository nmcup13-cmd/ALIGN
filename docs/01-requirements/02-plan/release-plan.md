# Release Plan: ระบบติดตามความสอดคล้อง CLO/PLO (ALIGN)

แปลงมาจาก [[product-backlog|product-backlog]] (26 User Story ที่ใช้งานอยู่จริง AB-01–AB-27 ไม่รวม AB-18) + [[feature-list|feature-list]] (26 Feature) แล้วผูกกับ [[../03-task/task-breakdown|task-breakdown]] (T-001–T-113 ไม่รวม T-062/T-063 ที่ตัดออกแล้ว) — เอกสารนี้**ไม่สร้าง** Epic/Story/Task ใหม่ มีหน้าที่จัด**ลำดับและกลุ่ม**ของสิ่งที่มีอยู่แล้วเท่านั้น

> สถานะ: ยืนยันแนวทางกับผู้ใช้ครบ 4 มิติแล้ว (2026-08-23) — ดูหัวข้อ 2 สำหรับรายละเอียดคำตอบและเหตุผล

**ขอบเขต**: วางแผนครอบคลุม**ทั้งหมดทุก Epic — E1 ถึง E6** (26 Feature จาก 26 User Story ที่ใช้งานอยู่จริง) ตามที่ผู้ใช้ยืนยันชัดเจนแล้ว ไม่ใช่แค่บางส่วน

**เอกสารต้นทางที่อ้างอิง**:
- [[../01-spec/requirement-align|requirement-align]] — Epic (E1–E6), กฎทางธุรกิจ #1–#6, 2 User Roles, Out of Scope
- [[product-backlog|product-backlog]] — 26 User Story พร้อม Priority และ Acceptance Criteria
- [[feature-list|feature-list]] — 26 Feature สรุปย่อต่อ Epic
- [[../03-task/task-breakdown|task-breakdown]] — T-001 ถึง T-113 (111 Task ที่ใช้งานจริง) พร้อมคอลัมน์ "หมายเหตุ" ที่ระบุ dependency ระหว่างงาน (ใช้เป็นฐานหลักของแผนนี้)
- [[../../02-design/02-technical/align-tech-stack|align-tech-stack]] — ข้อจำกัดทีมจริง (นักพัฒนา 1–2 คน ไม่มีโปรแกรมเมอร์มืออาชีพดูแลระบบหลัง deploy, ไม่ถนัดภาษาใดเป็นพิเศษ) และเดดไลน์ใช้งานจริงภายในปลาย ต.ค. 2569 — ใช้ประกอบการตัดสินใจเรื่อง timeline granularity (ดูหัวข้อ 2.4) แต่**ไม่ได้นำมาผูกเป็นวันที่ในแผนนี้**ตามที่ผู้ใช้ตัดสินใจ
- [[../../02-design/02-technical/align-nfr|align-nfr]] — NFR ที่ต้องมี/ตัดสินใจแล้ว/ยังไม่ยืนยัน ใช้ประกอบความเสี่ยงต่อ Phase (เช่น human-in-the-loop integrity กฎ #3, PDPA)

## 2. แนวทางการแบ่ง Phase ที่เลือก (Sequencing Strategy)

ผู้ใช้ตอบคำถามครบทั้ง 4 มิติ (2026-08-23) ดังนี้:

### 2.1 Sequencing Strategy — เลือก **Dependency-first**

เรียงลำดับ Epic/Story เข้า Phase ตามสายพึ่งพาทางเทคนิคจริงที่ปรากฏในคอลัมน์ "หมายเหตุ" ของ [[../03-task/task-breakdown|task-breakdown]] (เช่น "ขึ้นกับ T-xxx") โดยเฉพาะอย่างยิ่ง **guard กลางของ E6 (account-status guard) ต้องทำก่อนสุด** เพราะ task-breakdown ระบุไว้เองว่า T-086 เป็น "จุดที่ทุก API endpoint ของ E1–E5 ต้อง enforce ร่วม" — ทำก่อนช่วยหลีกเลี่ยงการย้อนกลับไปแปะ guard ทีหลังใน endpoint ที่สร้างไปแล้วของ E1–E5

### 2.2 จำนวน Phase — **6 Phase** ตรงกับจำนวน Epic พอดี (E6 → E1 → E2 → E3 → E4 → E5)

ผู้ใช้ระบุว่าไม่มีข้อกำหนดตายตัวเรื่องจำนวน Phase ให้ผู้วางแผนตัดสินใจเองโดยอิงจาก dependency clusters ตามธรรมชาติ — จากการไล่ตรวจ dependency ("ขึ้นกับ ...") ของทุก Task ใน task-breakdown พบว่า **จุดตัดของ dependency chain เกิดขึ้นตรงกับขอบเขตของแต่ละ Epic พอดี** กล่าวคือ:

- Task ของ E1 (การตั้งค่า curriculum/PLO/CLO/mapping/syllabus) ไม่มีตัวไหนพึ่งพา Task ของ E2–E5 เลย พึ่งพาเฉพาะ Task ภายใน E1 กับ E6 (guard) เท่านั้น
- Task ของ E2 (บันทึกการสอน/หลักฐาน) พึ่งพา schema `course`/`curriculum_group_id` จาก E1 (เช่น T-018 ขึ้นกับ T-013/T-017) แต่ไม่มี Task ไหนของ E2 core ที่ E3–E5 ต้องพึ่งย้อนกลับ
- Task ของ E3 (AI matching/gap) พึ่งพาทั้ง E1 (CLO/PLO/syllabus) และ E2 (teaching_log/evidence) ตรงตามลำดับ E1→E2→E3
- Task ของ E4 (dashboard) พึ่งพาผลลัพธ์ confirmed จาก E3 (เช่น T-039 ขึ้นกับ T-037, T-069, T-073)
- Task ของ E5 (export) พึ่งพาผลลัพธ์ confirmed จาก E3 (T-053 ขึ้นกับ T-037) และ logic gap จาก E3/E4 (T-056 ขึ้นกับ T-030, T-042, T-076)

จึงไม่มีเหตุผลเชิง dependency ที่จะรวมสอง Epic เข้า Phase เดียวกัน (จะทำให้ entry/exit criteria ปนกันโดยไม่จำเป็น) และไม่มีเหตุผลที่จะแตก Epic ใดเป็นสอง Phase (ไม่มีจุดตัด dependency ภายใน Epic เดียวที่ใหญ่พอ) **ยกเว้น 3 Task ที่ dependency บังคับให้ต้องขยับข้าม Epic ของตัวเอง** (ดูรายละเอียดในหัวข้อ 3 และ 4): **T-087** (checklist ครอบคลุม endpoint ของ E1–E5 ทั้งหมด — ต้องรอให้ E1–E5 สร้างเสร็จก่อนจึงตรวจครบจริงได้ แม้ PB Ref เป็น AB-25/E6), **T-103** และ **T-113** (ต้องพึ่ง query ของ E4 ที่ยังไม่มีในช่วง Phase ของ Epic ตัวเอง)

### 2.3 นิยามความสัมพันธ์ Phase ↔ Release — เลือก **1 Phase = 1 Release**

ปล่อยใช้งานจริงทันทีที่จบแต่ละ Phase — หมายความว่าแผนนี้เท่ากับ **6 Release** เรียงตามลำดับ Phase

### 2.4 ความละเอียดของ timeline — เลือก **ไม่ใส่วันที่ ใช้แค่ลำดับ Phase 1–6**

ผู้ใช้ยังไม่ตัดสินใจเรื่อง timeline/วันที่ (ดูหัวข้อ 5 "สิ่งที่ยังไม่ตัดสินใจ") — เอกสารนี้จึงใช้ลำดับ Phase เท่านั้น **ไม่ผูกกับเดดไลน์ปลาย ต.ค. 2569 ที่ระบุใน `align-tech-stack.md` และไม่ระบุวันที่ใดๆ** เพราะไม่มีข้อมูล velocity ทีมจริงมารองรับตัวเลขนั้น

## 3. Phase-by-Phase Breakdown

### Phase 1 — E6: สมัครและอนุมัติบัญชีผู้ใช้ + Guard กลาง (Account Gating Foundation)

**เป้าหมาย**: ผู้ใช้จบ Phase นี้แล้วจะมีระบบสมัครสมาชิกแบบ self-service ที่บัญชีใหม่เริ่มที่สถานะ "รออนุมัติ" เสมอ, ผู้บริหารหลักสูตรเห็นรายการบัญชีรออนุมัติ/ทั้งหมดและอนุมัติ/ปฏิเสธได้พร้อม audit log, อาจารย์เห็นสถานะบัญชีตนเองตอน login, และมี guard กลาง (account-status) ที่พร้อมบังคับใช้กับทุก endpoint ที่จะสร้างใน Phase ถัดไป — แม้ยังไม่มี endpoint ของ E1–E5 ให้ guard นี้ป้องกันจริงในตอนจบ Phase นี้

**Epic/Story ที่รวมอยู่**: E6 ทั้งหมด — AB-24, AB-25, AB-26, AB-27

**เงื่อนไขเริ่มต้น (Entry)**: ไม่ผูกกับ Phase อื่นมาก่อน (เป็น Phase แรกสุดตามการตัดสินใจ dependency-first) — ต้องมี infra พื้นฐานตาม `align-tech-stack.md` (Next.js + Supabase Auth/Postgres) พร้อมใช้งาน

**เงื่อนไขจบ (Definition of Done)**:
- สมัครสมาชิกสำเร็จ → บัญชีสถานะ `pending` เสมอ ไม่ auto-approve (กฎ #6)
- Guard กลาง (T-086/T-088/T-089/T-108) ปฏิเสธ (403) ทุก request จากบัญชี `pending`/`rejected`/`is_deleted` และ revalidate ทุกครั้ง ไม่ cache ระยะยาว
- ผู้บริหารหลักสูตรอนุมัติ/ปฏิเสธบัญชีได้ พร้อมบันทึก audit log (T-092) ผู้อนุมัติ+เวลา
- อาจารย์เห็นสถานะบัญชีตนเองตอน login โดยไม่เห็นข้อมูลบัญชีผู้อื่น (admin-only visibility)
- **ข้อยกเว้น**: T-087 (checklist/automated test ครอบคลุม endpoint ทั้งหมดของ E1–E5) **ยังปิดไม่ได้สมบูรณ์ใน Phase นี้** เพราะ endpoint ของ E1–E5 ยังไม่ถูกสร้าง — เลื่อนไปเป็นเงื่อนไขจบของ Phase 6 แทน (ดูหมายเหตุท้ายเอกสารและหัวข้อ 4)

**ความเสี่ยง/สมมติฐาน**:
- Guard ที่ยังไม่มี endpoint จริงให้ป้องกัน ตรวจสอบความถูกต้อง 100% ไม่ได้จนกว่าจะมี endpoint ของ E1 มาทดสอบร่วมจริงใน Phase 2 — ความเสี่ยงนี้ถูกส่งต่อเป็นเงื่อนไขตรวจสอบซ้ำใน Phase 2–6 ทุก Phase (ทีมต้องอัปเดต checklist ของ T-087 ทุกครั้งที่เพิ่ม endpoint ใหม่ ไม่ใช่รอทำทีเดียวตอนจบ)
- สมมติฐาน: Supabase Auth (ตาม align-tech-stack.md §2.7) ใช้งานได้ตามคาด ไม่มีข้อจำกัดที่ค้นพบทีหลัง

### Phase 2 — E1: ป้อนข้อมูลวิชา (Course Syllabus + CLO + PLO)

**เป้าหมาย**: ผู้บริหารหลักสูตรตั้งค่ากลุ่มหลักสูตร 2565/2570 พร้อม PLO แยกกันได้, อาจารย์ป้อน CLO ของรายวิชาพร้อมผูกกับ PLO ภายในกลุ่มหลักสูตรเดียวกันได้ (ครบเงื่อนไขกฎ #1), อัปโหลด/กรอก course syllabus (ไฟล์แนบทางการ + หัวข้อรายสัปดาห์) ต่อรายวิชาได้ และลบ (soft-delete) PLO/CLO ได้อย่างปลอดภัยโดยไม่กระทบข้อมูลอ้างอิงเดิม

**Epic/Story ที่รวมอยู่**: E1 ทั้งหมด — AB-01, AB-02, AB-03, AB-04, AB-19

**เงื่อนไขเริ่มต้น (Entry)**: Phase 1 เสร็จ (มีบัญชีที่ถูกอนุมัติแล้วอย่างน้อย 1 บัญชีเพื่อใช้งาน E1 ได้จริง และ guard กลางพร้อม enforce endpoint ใหม่ที่จะสร้างใน Phase นี้)

**เงื่อนไขจบ (Definition of Done)**:
- มีตัวเลือกกลุ่มหลักสูตร 2565/2570 ให้เลือกก่อนป้อน PLO/CLO เสมอ, ห้ามผูก CLO–PLO ข้ามกลุ่ม
- ทุกรายวิชาต้องมี CLO ≥1 ผูกกับ PLO ≥1 ก่อนจึงปลดล็อกการบันทึกการสอนได้ (กฎ #1, guard จาก T-012/T-013)
- Soft-delete ของ PLO (T-098–T-101) และ CLO (T-109–T-112) ทำงานถูกต้อง ไม่ลบแถวจริง ไม่บล็อกด้วย error แม้มีการอ้างอิงอยู่แล้ว และ re-evaluate ความครบถ้วนของ CLO–PLO ทันทีหลัง soft-delete
- Syllabus (ไฟล์แนบ + หัวข้อรายสัปดาห์) บันทึก/แก้ไขได้ต่อรายวิชา

**ความเสี่ยง/สมมติฐาน**:
- Phase นี้มีจำนวน Task มากที่สุด (28 Task) ในทั้ง 6 Phase — เป็นความเสี่ยงด้านเวลาเมื่อเทียบกับทีมพัฒนา 1–2 คน (align-tech-stack.md §1.1) แม้จะสอดคล้องกับ dependency จริงก็ตาม (ดูข้อเปิดในหัวข้อ 5)
- ต้องอัปเดต checklist ของ T-087 (Phase 1) ให้ครอบคลุม endpoint ใหม่ทั้งหมดที่สร้างใน Phase นี้

### Phase 3 — E2: บันทึกการสอนและแนบหลักฐาน

**เป้าหมาย**: อาจารย์บันทึกหัวข้อการสอนพร้อมแนบหลักฐาน/ชิ้นงานหลังสอนจริงได้ (เฉพาะรายวิชาที่ผ่านเงื่อนไข Phase 2 แล้ว) แนบได้หลายไฟล์ ลบไฟล์ผิดได้ก่อนยืนยัน และการเข้าถึงไฟล์หลักฐานถูกจำกัดสิทธิ์ตาม PDPA พร้อม log การเข้าถึง

**Epic/Story ที่รวมอยู่**: E2 ทั้งหมด — AB-05, AB-06, AB-07

**เงื่อนไขเริ่มต้น (Entry)**: Phase 2 เสร็จ (มีรายวิชาอย่างน้อย 1 วิชาที่ผูก CLO–PLO ครบเงื่อนไขกฎ #1 แล้ว)

**เงื่อนไขจบ (Definition of Done)**:
- บันทึกการสอนถูกบล็อกถ้ารายวิชายังผูก CLO–PLO ไม่ครบ (reuse guard จาก T-013)
- แนบหลักฐานได้หลายไฟล์ต่อการบันทึกหนึ่งครั้ง ลบ/แก้ไขไฟล์ที่แนบผิดได้ก่อนกดยืนยัน
- เข้าถึงไฟล์หลักฐานได้เฉพาะอาจารย์ผู้สอนวิชานั้น/ผู้บริหารหลักสูตรที่เกี่ยวข้องเท่านั้น พร้อม log ทุกครั้งที่เข้าถึง (กฎ #5)
- Soft-delete ของ `teaching_log` (T-102) และ `evidence_file` (T-104/T-105) ทำงานถูกต้อง (ลบแบบ soft เสมอ ไม่กระทบเอกสารที่เคย export ไปแล้ว)
- **ข้อยกเว้น**: T-103 (กรอง `is_deleted` ในการคำนวณ % ความสอดคล้อง/CLO×สัปดาห์) และ T-106 (กรอง `is_deleted` ในรายการหลักฐานที่ใช้ export) **ยังทำไม่ได้ใน Phase นี้** เพราะ query ปลายทาง (T-039/T-047 ของ E4, T-053 ของ E5) ยังไม่ถูกสร้าง — เลื่อนไป Phase 5 และ Phase 6 ตามลำดับ

**ความเสี่ยง/สมมติฐาน**:
- ระหว่าง Phase 3–4 ข้อมูล teaching_log ที่ soft-delete แล้วอาจยังไม่ถูกกรองออกจากการคำนวณ (เพราะ T-103 เลื่อนไป Phase 5) — ต้องระบุเป็น known-gap ชั่วคราวและปิดให้ครบก่อนเข้าสู่ Phase 6 (release)

### Phase 4 — E3: AI ประมวลผลจับคู่ CLO/PLO และวิเคราะห์ Gap

**เป้าหมาย**: ระบบใช้ AI จับคู่ข้อมูลการสอนกับ CLO ของกลุ่มหลักสูตรที่ถูกต้อง พร้อมเชื่อมโยงไปยัง PLO, คำนวณ % ความสอดคล้อง (สัดส่วน CLO ที่แมทช์ต่อ CLO ทั้งหมดของวิชา) และความถี่ที่แมทช์ ร่วมกับวิเคราะห์ gap เทียบ course syllabus — ผลทั้งหมดเป็นค่าตั้งต้น (draft) ที่อาจารย์ต้องตรวจสอบ/แก้ไข/ยืนยันก่อนบันทึกจริง

**Epic/Story ที่รวมอยู่**: E3 ทั้งหมด — AB-08, AB-09, AB-10, AB-20, AB-21, AB-22

**เงื่อนไขเริ่มต้น (Entry)**: Phase 2 เสร็จ (มี CLO/PLO/syllabus) และ Phase 3 เสร็จ (มี teaching_log/evidence ให้ AI ประมวลผล)

**เงื่อนไขจบ (Definition of Done)**:
- AI จับคู่เฉพาะ CLO ของกลุ่มหลักสูตรเดียวกับรายวิชา ห้าม merge ข้ามกลุ่ม
- ผลจับคู่ CLO/PLO, % ความสอดคล้อง, ความถี่ที่แมทช์, และผล gap analysis ทั้งหมดเป็นสถานะ `draft` จนกว่าอาจารย์ยืนยัน (กฎ #3 — human-in-the-loop) ไม่มี endpoint ใด bypass การยืนยันได้ (guard T-038)
- % ความสอดคล้องคำนวณจากสัดส่วน CLO ที่แมทช์ได้จริงต่อจำนวน CLO ทั้งหมดของวิชา (ฐาน 100%) ไม่ใช่ค่าคงที่ตายตัว
- ความถี่ที่แมทช์แสดงคู่กับ raw count เสมอ แยกจาก % ความสอดคล้องอย่างชัดเจน

**ความเสี่ยง/สมมติฐาน**:
- **นี่คือ Phase ที่มีความไม่แน่นอนทางเทคนิคสูงสุดในทั้งแผน** — `align-tech-stack.md` §2.4 เลือก hybrid AI (Transformers.js embedding ภาษาไทย/หลายภาษารันในเครื่องเป็นหลัก + external API แบบ feature-flag ที่ปิดอยู่) ซึ่งยังไม่เคยผ่านการทดสอบความแม่นยำจริงกับข้อมูล CLO/หัวข้อการสอนจริงของสาขา — ถ้าทีมเลือกกลยุทธ์ Risk/foundation-first แทน Dependency-first, Phase นี้จะถูกทำก่อนสุด แต่ผู้ใช้ยืนยันเลือก Dependency-first แล้ว จึงยอมรับความเสี่ยงนี้อยู่กลางแผนแทน
- สมมติฐาน: คุณภาพผลจับคู่ที่ต่ำกว่าคาดยังยอมรับได้ เพราะกฎ #3 บังคับให้อาจารย์ตรวจสอบ/แก้ไขได้เสมอก่อนใช้เป็นหลักฐานทางการ (ไม่ใช่ผลสุดท้าย)

### Phase 5 — E4: แดชบอร์ดและแจ้งเตือนความสอดคล้อง

**เป้าหมาย**: อาจารย์เห็นแดชบอร์ดหน้าแรกแสดง % ความสอดคล้องรวมและรายวิชาที่สอน, ได้รับแจ้งเตือนทันทีที่ CLO ใดไม่มีหลักฐานรองรับ, เห็นแผนที่ CLO×สัปดาห์, และเห็นการเปรียบเทียบการสอนจริงกับ CLO/syllabus บนแดชบอร์ด — ผู้บริหารหลักสูตรเห็นภาพรวมระดับหลักสูตรแยกกลุ่ม 2565/2570 — ทั้งหมดจากข้อมูลที่ยืนยันแล้วเท่านั้น (ไม่ใช้ข้อมูล draft)

**Epic/Story ที่รวมอยู่**: E4 ทั้งหมด — AB-11, AB-12, AB-13, AB-14, AB-23

**เงื่อนไขเริ่มต้น (Entry)**: Phase 4 เสร็จ (มีผลจับคู่/gap ที่ยืนยันแล้ว (`confirmed`) อย่างน้อยบางส่วนให้แดชบอร์ดอ่าน)

**เงื่อนไขจบ (Definition of Done)**:
- ตัวเลขบนแดชบอร์ดทุกตัวสะท้อนเฉพาะข้อมูล `confirmed` ไม่ใช่ `draft`
- แจ้งเตือน CLO ที่ขาดหลักฐานเกิดขึ้นอัตโนมัติทันที ไม่ต้องให้ผู้ใช้ตรวจสอบเองแบบ manual (กฎ #2)
- แดชบอร์ดระดับหลักสูตรแยกข้อมูล 2565/2570 ชัดเจน ไม่ปนกัน เข้าถึงได้เฉพาะผู้บริหารหลักสูตรที่เกี่ยวข้อง (กฎ #5)
- **ปิดข้อยกเว้นจาก Phase 3**: T-103 (กรอง `is_deleted` ของ teaching_log ในการคำนวณ % และ CLO×สัปดาห์) และ T-113 (ปรับฐาน `total_clo_count` ให้นับเฉพาะ CLO ที่ไม่ถูก soft-delete) ต้องทำให้เสร็จใน Phase นี้ เพราะเป็นจุดที่ query ปลายทาง (T-039/T-047) ถูกสร้างจริงแล้ว

**ความเสี่ยง/สมมติฐาน**:
- ถ้า T-103/T-113 ไม่เสร็จในนี้จริง ตัวเลขแดชบอร์ดอาจรวมข้อมูลที่ถูก soft-delete ไปแล้ว ซึ่งขัดกับ NFR "Data Integrity" ที่ align-nfr.md ระบุไว้ — ต้องตรวจสอบเป็นพิเศษก่อนปิด Phase

### Phase 6 — E5: ออกเอกสารหลักฐาน (Word Export) + ปิด Guard Checklist (Final Release Gate)

**เป้าหมาย**: อาจารย์ออกเอกสาร Word สรุปความสอดคล้อง CLO/PLO พร้อมส่วน Area of Improvement (free-text) ได้ ผู้บริหารหลักสูตรดาวน์โหลดเอกสารของหลักสูตรที่ตนดูแลไปทำ SAR ได้ — และเป็น Phase สุดท้ายที่ปิด T-087 (checklist/automated test ครอบคลุม guard ของทุก endpoint ใน E1–E5) ก่อนประกาศ Release จริง

**Epic/Story ที่รวมอยู่**: E5 ทั้งหมด — AB-15, AB-16, AB-17 (+ ปิดงานค้าง T-087 จาก E6/Phase 1)

**เงื่อนไขเริ่มต้น (Entry)**: Phase 4 เสร็จ (มีข้อมูลยืนยันแล้วให้เอกสารอ้างอิง) และ Phase 5 เสร็จ (มี logic gap analysis ที่ confirmed แล้วสำหรับ Area of Improvement)

**เงื่อนไขจบ (Definition of Done)**:
- เอกสาร Word อ้างอิงเฉพาะชิ้นงาน/หลักฐานที่แนบไว้จริงและข้อมูลที่ยืนยันแล้วเท่านั้น ไม่มีข้อมูลอ้างอิงที่ไม่มีหลักฐานรองรับ (กฎ #4)
- เอกสารระบุกลุ่มหลักสูตร (2565/2570) ชัดเจน มีส่วน Area of Improvement เป็น free-text อิงข้อมูล gap จริงที่ยืนยันแล้ว
- ผู้บริหารหลักสูตรดาวน์โหลดเอกสารได้เฉพาะรายวิชาในหลักสูตรที่ตนดูแล (กฎ #5)
- **ปิดข้อยกเว้นจาก Phase 3**: T-106 (กรอง `is_deleted` ของ evidence ในรายการที่ใช้ export) ต้องเสร็จในนี้ เพราะ T-053 (API generate เอกสาร) ถูกสร้างจริงแล้ว
- **T-087 (จาก Phase 1) ต้องปิดให้ครบที่นี่**: รันตรวจสอบ/automated test ว่าไม่มี endpoint ใดของ E1–E5 (ที่สร้างครบทุก Phase แล้ว ณ จุดนี้) หลุดการ enforce guard กลาง (T-086) — ถือเป็นเงื่อนไขบังคับก่อนประกาศ Release สุดท้าย (ตาม NFR "Security/Access Control — 0 endpoint ที่หลุดการตรวจ" ใน align-nfr.md §2)

**ความเสี่ยง/สมมติฐาน**:
- Phase นี้แบก 2 บทบาท (ส่งมอบฟีเจอร์ E5 + เป็น final security gate ของทั้งระบบ) — มีความเสี่ยงใช้เวลานานกว่าที่ประเมินถ้าการตรวจ T-087 พบ endpoint ที่หลุด guard จริง ต้องแก้ไขย้อนกลับไปยัง Phase ก่อนหน้า (ถือเป็นความเสี่ยงที่ยอมรับได้ของกลยุทธ์ dependency-first ที่เลือก guard-first แต่ verification-last)

## 5. สิ่งที่ยังไม่ตัดสินใจ/ต้องทบทวน

1. **Timeline/วันที่จริงต่อ Phase — ยังไม่ตัดสินใจ (เปิดไว้ตามคำขอผู้ใช้)**: แผนนี้ใช้ลำดับ Phase 1–6 เท่านั้น ไม่ผูกกับเดดไลน์ปลาย ต.ค. 2569 ที่ระบุใน `align-tech-stack.md` เพราะยังไม่มีข้อมูล velocity ทีมจริง (ทีม 1–2 คน) มารองรับตัวเลขวันที่ที่แม่นยำ — ต้องกลับมาทบทวนทันทีที่มีข้อมูล velocity จริงจาก Phase 1 หรือ Phase 2 ที่ทำเสร็จแล้วอย่างน้อย 1 Phase
2. **ขนาดของ Phase 2 (E1) ใหญ่ที่สุด (28 Task)**: แม้จะมีเหตุผลด้าน dependency รองรับชัดเจนว่าไม่ควรแยก แต่เมื่อเทียบกับทีม 1–2 คนที่ไม่มีข้อมูล velocity มาก่อน อาจกลายเป็นคอขวดของทั้งแผน — แนะนำให้ทีมพัฒนาประเมินซ้ำหลัง Phase 1 เสร็จจริงว่าควรแตก Phase 2 เป็น 2 ช่วงย่อยหรือไม่ (เช่น "PLO/CLO/mapping พื้นฐาน" กับ "syllabus + soft-delete") แต่เอกสารนี้ไม่ตัดสินใจแทนเพราะยังไม่มีข้อมูลรองรับ
3. **6 Release แยกกัน อาจมี overhead deploy/QA สูงสำหรับทีมเล็ก**: `align-nfr.md` ระบุว่าผู้ดูแลระยะยาวไม่ใช่โปรแกรมเมอร์มืออาชีพ และยังไม่มี runbook go-live จริง — การนิยาม 1 Phase = 1 Release (6 ครั้ง) ตามที่ผู้ใช้เลือก อาจต้องทบทวนภาระ deploy ซ้ำเมื่อเริ่มลงมือทำจริง แต่ไม่ใช่การตัดสินใจของเอกสารนี้ที่จะเปลี่ยนแปลงเอง
4. **กลไก/ผู้รับผิดชอบรัน T-087 (final guard checklist) ให้ชัดเจน**: task-breakdown ระบุ T-087 เป็น "automated test ตรวจว่าไม่มี endpoint ใดหลุดการ enforce" แต่ยังไม่มีเอกสารใดระบุว่าใครในทีม 1–2 คนเป็นเจ้าภาพรันเช็คนี้ก่อนแต่ละ Release หรือเฉพาะ Release สุดท้าย (Phase 6) เท่านั้น — เป็นช่องว่างที่ควรถามทีมพัฒนา/technical-designer เพิ่มเติม
5. **จุดที่ควร sign-off ด้าน PDPA และตั้งตารางสำรองข้อมูล**: `align-nfr.md` §3–4 ระบุว่าต้อง sign-off จากหน่วยงาน PDPA ก่อนใช้ข้อมูลนักศึกษาจริง และมี manual backup ก่อนเส้นตายสำคัญ — เอกสารนี้ยังไม่ได้กำหนดว่าควรผูกกิจกรรมเหล่านี้กับ Phase ใด (เช่น ก่อน Phase 3 ที่เริ่มมีไฟล์หลักฐานจริง หรือก่อน Phase 6/Release สุดท้าย) เพราะเป็นกิจกรรมนอกเหนือ Task ที่มีอยู่แล้วใน task-breakdown ไม่ใช่ Task ใหม่ที่เอกสารนี้จะเพิ่มเอง
6. **ไม่มีช่องว่าง Task ที่ต้องสร้างใหม่**: ตรวจสอบแล้วว่าทุก Story (AB-01–AB-27 ไม่รวม AB-18) มี Task รองรับครบใน task-breakdown ไม่พบ Epic/Story ใดที่ขาด Task เชื่อม/เตรียมงานที่ต้องรายงานเป็นช่องว่างเพิ่มเติมในรอบนี้
