## 0. โครงหน้าจอร่วม (App Shell) — ใช้ทั้งบทบาทอาจารย์และผู้บริหารหลักสูตร

> **ข้อยกเว้น**: หน้าจอ 0A (สมัครใช้งาน) และหน้าจอ 0B (สถานะบัญชี/รออนุมัติ) ด้านล่าง **ไม่ได้อยู่ภายใต้ App Shell นี้** — ทั้งสองหน้าเกิดขึ้น**ก่อน**ที่บัญชีจะผ่านการอนุมัติ (`account_status = 'approved'`) จึงไม่มี Side Navigation แสดงเลย (มีเพียง App Header แบบย่อ) ตามกฎทางธุรกิจ #6 ที่บัญชี "รออนุมัติ"/"ถูกปฏิเสธ" ต้องเข้าถึงฟีเจอร์อื่นของระบบไม่ได้ไม่ว่ากรณีใด — App Shell แบบเต็ม (มี Side Navigation) เริ่มปรากฏเฉพาะหลังหน้าจอ 0B ยืนยันว่า `account_status = 'approved'` แล้วเท่านั้น

ทุกหน้าจอในเอกสารนี้และใน [[align-program-admin-screens|align-program-admin-screens]] อยู่ภายใต้โครงหน้าจอเดียวกัน:

- **App Header** (สูงคงที่, พื้นหลัง `bg.surface`, เส้นขอบล่าง `border.default`, padding `space.md`):
  - ซ้าย: **ALIGN wordmark** — ข้อความ "ALIGN" น้ำหนัก SemiBold ขนาด `text.h2` สี `primary.green` (ตาม DESIGN.md §1.4) **ไม่มีไอคอนประกอบ** ในต้นแบบนี้
  - ขวา: ชื่อผู้ใช้ + badge บทบาทปัจจุบัน (Instructor/Program Administrator) + เมนู account แบบ dropdown เรียบ (ไม่มี avatar สีสันจัด)
  - > **หมายเหตุเปิด (Open Question)**: `DESIGN.md` §1.4 ยังไม่มีมติเรื่องไอคอน/สัญลักษณ์เฉพาะของ ALIGN (มีแค่ข้อเสนอ "เส้นโค้ง 2 เส้นไขว้กัน" ที่ยังไม่ยืนยัน) ต้นแบบนี้จึงใช้ **wordmark ข้อความล้วนชั่วคราว** ตามแนวทางที่ DESIGN.md ระบุไว้เป็นทางเลือกระยะแรก หากทีมตัดสินใจไอคอนภายหลัง ต้องกลับมาอัปเดต App Header ในทุกหน้าจอของเอกสารนี้และเอกสารบทบาทผู้บริหารหลักสูตร
- **Side Navigation** (ซ้าย, กว้างคงที่, พื้นหลัง `bg.base`, ไอคอน line icon stroke 1.5px ตาม DESIGN.md §2.5): เมนูเปลี่ยนตามบทบาทของผู้ใช้ที่ login (ดูเมนูของแต่ละบทบาทในหัวข้อถัดไปและใน [[align-program-admin-screens|align-program-admin-screens]]) — ระบบมี 2 บทบาทเท่านั้น (`CLAUDE.md`), ไม่มีการสลับบทบาทเองในแอป (สิทธิ์ผูกกับ account)
- **Content Area**: พื้นหลัง `bg.base`, การ์ด/panel ใช้ `bg.surface` + `radius.md` + `shadow.card` เบาๆ ตาม DESIGN.md §2.4, เว้นขอบ content จาก header/side nav ด้วย `space.xl`
- **Curriculum tag ทุกจุดที่มี CLO/PLO/รายวิชา** ใช้ Curriculum Tag / Chip token `curriculum.2565` (taupe) หรือ `curriculum.2570` (moss) เสมอ ไม่มีข้อยกเว้น (UX Rule 2)

เมนู Side Navigation ของบทบาท **อาจารย์ผู้สอน**:

| ไอคอน (แนวคิด) | label | ลิงก์ไปหน้าจอ |
|---|---|---|
| home | หน้าแรก | หน้าจอ 1 — แดชบอร์ด |
| book | รายวิชาของฉัน | หน้าจอ 2 — รายวิชาของฉัน |
| grid | แผนที่ CLO × สัปดาห์ | หน้าจอ 7 (เลือกวิชาก่อนเข้า) |

หมายเหตุ: การ "บันทึกการสอน" (หน้าจอ 5) และ "สรุปรายวิชา" (หน้าจอ 8) ไม่มีปุ่มตายตัวใน Side Navigation เพราะเป็น context เฉพาะรายวิชา — เข้าถึงจากภายในหน้า "รายวิชาของฉัน" หรือปุ่ม CTA บนแดชบอร์ด (ดู [[align-navigation-flow|align-navigation-flow]])

หมายเหตุ (E6): เมนู Side Navigation ข้างต้นแสดง**เฉพาะบัญชีที่ผ่านการอนุมัติแล้ว** (`account_status = 'approved'`) เท่านั้น — บัญชีที่อยู่ในสถานะ "รออนุมัติ"/"ถูกปฏิเสธ" จะไม่เห็นเมนูนี้เลย เพราะยังไม่หลุดออกจากหน้าจอ 0B (ดูด้านล่าง) เป็น **gate ที่ต้องผ่านก่อน** จึงจะถึงหน้าจอ 1 ได้ (กฎทางธุรกิจ #6, AB-25)

## หน้าจอ 0A — สมัครใช้งาน (Sign Up)

**Map**: AB-24

**จุดประสงค์**: ให้อาจารย์ผู้สอนที่ยังไม่มีบัญชีในระบบสมัครใช้งาน ALIGN ได้ด้วยตนเอง (self-service) โดยกรอกข้อมูลตนเอง โดยไม่ต้องรอให้ผู้บริหารหลักสูตรสร้างบัญชีให้ล่วงหน้า — เป็น**หน้าจอแรกสุด**ของ flow อาจารย์ผู้สอน มาก่อนหน้าจอ 1 เสมอสำหรับผู้ที่ยังไม่มีบัญชี

**Layout**:
1. App Header แบบย่อ: มีเพียง **ALIGN wordmark** กึ่งกลาง/ซ้ายจอ (ตาม DESIGN.md §1.4) — **ไม่มี Side Navigation, ไม่มีเมนู account** เพราะยังไม่มีบัญชีที่ login ได้
2. หัวข้อหน้า (`text.h1`) "สมัครใช้งาน ALIGN" + คำอธิบายรอง (`text.body-sm`, สี `text.secondary`): "สำหรับอาจารย์ผู้สอน — บัญชีที่สมัครใหม่ต้องรอผู้บริหารหลักสูตรอนุมัติก่อนใช้งานจริง (AB-24)"
3. ฟอร์มสมัครสมาชิก 5 ฟิลด์ (เรียงบนลงล่าง, ระยะห่างระหว่างฟิลด์ `space.sm`–`space.md`):
   - **ชื่อ-นามสกุล** (text field, placeholder "เช่น นายสมชาย ใจดี")
   - **อีเมลสถาบัน** (text field, placeholder "name@university.ac.th") — validate รูปแบบอีเมลแบบ inline ทันทีที่ผู้ใช้แตะออกจากช่อง (ไม่ต้องรอกด submit): ถ้าไม่ผ่าน แสดงข้อความ error สีเดียวกับ `status.gap` ใต้ช่อง "กรุณากรอกอีเมลสถาบันให้ถูกต้อง" พร้อมเปลี่ยนเส้นขอบ input เป็นสี `status.gap`
   - **สังกัด/ภาควิชา** (text field, placeholder "เช่น สาขา New Media Communication")
   - **รหัสผ่าน** (password field)
   - **ยืนยันรหัสผ่าน** (password field) — validate ว่าตรงกับรหัสผ่านแบบ inline เช่นเดียวกับอีเมล ถ้าไม่ตรงแสดง "รหัสผ่านไม่ตรงกัน" (สี `status.gap`)
4. ปุ่มหลัก **"สมัครสมาชิก"** (primary button, สี `primary.green`) — **disabled** (พื้นหลัง `border.strong`, ตัวอักษร `text.disabled`) จนกว่าจะกรอกครบทุกฟิลด์ + ผ่าน validation ทั้งหมด (ไม่ปล่อยให้กดแล้วเจอ error ทีหลัง — ป้องกัน error state ที่หลีกเลี่ยงได้)
5. ลิงก์ท้ายฟอร์ม (`text.caption`, สี `text.secondary`, คำว่า "เข้าสู่ระบบ" เน้นสี `primary.green`): "มีบัญชีอยู่แล้ว? เข้าสู่ระบบ"

> **ข้อสมมติที่ต้องยืนยันก่อนพัฒนาจริง**: ชุดฟิลด์ข้างต้น (ชื่อ-นามสกุล, อีเมลสถาบัน, สังกัด/ภาควิชา, รหัสผ่าน) เป็นข้อเสนอของผู้ออกแบบที่สืบทอดมาจากต้นแบบที่คลิกได้ ([[align-interactive-prototype|align-interactive-prototype]], ไฟล์ `M-SignUp.dc.html`) เพราะ AB-24 ในสเปคยังไม่กำหนดรายการฟิลด์ที่แน่นอน — คงชุดฟิลด์เดียวกันไว้ในเอกสารนี้เพื่อความสอดคล้อง หากมีข้อกำหนดจริงจากมหาวิทยาลัย (เช่น ต้องใช้ SSO/รหัสพนักงานแทนอีเมล+รหัสผ่าน) ต้องปรับทั้งสองเอกสารพร้อมกัน

**Curriculum tag**: ไม่มี — หน้านี้ไม่มี CLO/PLO/รายวิชาปรากฏ (UX Rule 2 ใช้เฉพาะจุดที่มีข้อมูลหลักสูตร)

**States**:
- ฟอร์มว่าง (เริ่มต้น) — ปุ่ม "สมัครสมาชิก" disabled
- กรอกบางส่วน/มี error inline ต่อฟิลด์ (อีเมลรูปแบบผิด, รหัสผ่านไม่ตรงกัน) — ปุ่มยัง disabled
- กรอกครบและผ่าน validation ทั้งหมด — ปุ่ม enable
- **ส่งฟอร์มสำเร็จ**: เปลี่ยนเนื้อหาในหน้าเดียวกันเป็นข้อความยืนยัน — ไอคอนติ๊กถูกในวงกลม (line icon สี `primary.green`), หัวข้อ "ส่งคำขอสมัครแล้ว", **badge "สถานะบัญชี: รออนุมัติ"** (เส้นขอบ**ประ** สี `status.draft`, พื้นหลัง `status.draft-tint` — ตาม UX Rule 1 เพราะยังไม่ใช่ผลตัดสินใจสุดท้าย), ข้อความอธิบายกลางๆ ไม่กระตุ้นความเร่งรีบ: "คำขอของคุณถูกส่งให้ผู้บริหารหลักสูตรตรวจสอบแล้ว ระบบจะแจ้งผลเมื่อได้รับการอนุมัติ — ระหว่างนี้ยังไม่สามารถใช้งานฟีเจอร์อื่นของระบบได้ (กฎทางธุรกิจ #6)", ปุ่ม ghost "กลับไปหน้าสมัครสมาชิก"

**จุดเชื่อมต่อ**: จุดเริ่มต้นแรกสุดของ flow อาจารย์ผู้สอนที่ยังไม่มีบัญชี (ไม่มีหน้าจออื่นนำมาก่อนหน้านี้) → หลังส่งฟอร์มสำเร็จ ไปหน้าจอ 0B (สถานะบัญชี/รออนุมัติ) — **ไม่พาเข้าหน้าจอ 1 หรือหน้าจอใดของ App Shell ทันที ไม่ว่ากรณีใด** (AB-24)

## หน้าจอ 0B — สถานะบัญชี / รอการอนุมัติ (Account Status / Pending Approval)

**Map**: AB-25, AB-27

**จุดประสงค์**: ให้อาจารย์ผู้สอนที่เคยสมัครไว้เห็นสถานะบัญชีของตนเอง (รออนุมัติ/อนุมัติแล้ว/ถูกปฏิเสธ) ทุกครั้งที่พยายามเข้าสู่ระบบ — เป็น**หน้าจอ gate หลัก**ที่ทำให้กฎทางธุรกิจ #6 มีผลจริง: บัญชีที่ยังไม่ได้รับอนุมัติต้องไม่ถูกพาเข้าฟีเจอร์ใดของระบบไม่ว่ากรณีใด (สอดคล้องกับ `GET /auth/me/account-status` ใน [[../02-technical/align-technical-design|align-technical-design]] §3 — endpoint นี้เรียกได้แม้บัญชียัง pending/rejected)

**Layout**: App Header แบบย่อเหมือนหน้าจอ 0A (wordmark + avatar placeholder เฉยๆ ไม่มี dropdown เมนู, **ไม่มี Side Navigation**) — เนื้อหากลางจอเปลี่ยนไปตาม `account_status` 3 แบบ:

1. **สถานะ "รออนุมัติ" (`pending`)**: ไอคอนนาฬิกา (line icon stroke 1.5px สี `status.draft`), **badge "รออนุมัติ"** (เส้นขอบ**ประ** สี `status.draft`, พื้นหลัง `status.draft-tint`), หัวข้อ (`text.h1`) "บัญชีของคุณอยู่ระหว่างตรวจสอบ", คำอธิบาย (`text.body-sm`, `text.secondary`) โทนกลาง: "ผู้บริหารหลักสูตรกำลังตรวจสอบคำขอสมัครของคุณ ระบบจะแจ้งผลให้ทราบทันทีที่มีการอนุมัติ — ระหว่างนี้ยังไม่สามารถเข้าถึงฟีเจอร์อื่นของระบบได้ (กฎทางธุรกิจ #6)"
2. **สถานะ "ถูกปฏิเสธ" (`rejected`)**: ไอคอนกากบาทในวงกลม (สี `status.gap`), **badge "ถูกปฏิเสธ"** (เส้นขอบ**ทึบ** สี `status.gap`, พื้นหลัง `status.gap-tint` — ใช้เส้นทึบไม่ใช่เส้นประ เพราะเป็นผลตัดสินใจสุดท้ายของผู้บริหารหลักสูตรแล้ว ไม่ใช่ค่า draft ที่รอตรวจสอบต่อ), หัวข้อ "คำขอสมัครไม่ได้รับการอนุมัติ", คำอธิบาย: "กรุณาติดต่อผู้บริหารหลักสูตรของท่านเพื่อสอบถามรายละเอียด หรือส่งคำขอสมัครใหม่พร้อมข้อมูลที่ถูกต้อง", ปุ่ม ghost "สมัครสมาชิกใหม่" → กลับหน้าจอ 0A
3. **สถานะ "อนุมัติแล้ว" (`approved`)**: ไอคอนติ๊กถูกในวงกลม (สี `primary.green`), **badge "อนุมัติแล้ว"** (เส้นขอบ**ทึบ** สี `status.confirmed`, พื้นหลัง `primary.green-tint`), หัวข้อ "ยินดีด้วย บัญชีของคุณพร้อมใช้งาน", คำอธิบาย "คุณสามารถเข้าใช้งานทุกฟีเจอร์ของระบบได้แล้ว", ปุ่มหลัก (primary, `primary.green`) "เข้าสู่หน้าแรก" → หน้าจอ 1
4. **ในสถานะ "รออนุมัติ"/"ถูกปฏิเสธ" เท่านั้น** — ใต้ข้อความอธิบาย แสดง**รายการฟีเจอร์ที่ถูกล็อก** เป็น list แถวละฟีเจอร์ (opacity ลด + grayscale, `pointer-events: none` — ไม่ใช่ปุ่มกดได้จริง): "ตั้งค่ารายวิชา (CLO/PLO)", "บันทึกการสอน", "แดชบอร์ดและฟีเจอร์อื่น" พร้อม caption (`text.caption`, `text.secondary`) ท้ายรายการ: "ฟีเจอร์ทั้งหมดถูกล็อกจนกว่าบัญชีจะได้รับการอนุมัติ (AB-25)" — สื่อภาพให้เห็นชัดว่า E1–E5 ทั้งหมดถูกปิดกั้น ไม่ใช่แค่บอกเป็นข้อความ

**Curriculum tag**: ไม่มี — หน้านี้ไม่มี CLO/PLO/รายวิชาปรากฏ

**States**: 3 สถานะข้างต้น (`pending`/`rejected`/`approved`) ต้องแยก visual ให้ชัดเจนที่สุด (ตาม UX Rule 1 ที่ใช้กับสถานะบัญชีนี้เช่นเดียวกับผล AI: ค่าที่ยัง "รอ" ต้องใช้เส้นประ `status.draft`, ค่าที่ "ตัดสินใจสุดท้ายแล้ว" — อนุมัติหรือปฏิเสธ — ต้องใช้เส้นทึบเสมอ)

**จุดเชื่อมต่อ**: มาจากหน้าจอ 0A (ทันทีหลังส่งฟอร์มสมัครสำเร็จ) หรือจากความพยายาม login ของบัญชีที่เคยสมัครไว้ก่อนหน้านี้ → ถ้า `approved` ไปหน้าจอ 1 (แดชบอร์ด, เปิด App Shell เต็มรูปแบบ) → ถ้า `pending`/`rejected` ค้างอยู่ที่หน้านี้เท่านั้น **ไม่มีทางลัดไปหน้าจอหรือฟีเจอร์อื่นของระบบได้ไม่ว่ากรณีใด** (กฎทางธุรกิจ #6) — การอนุมัติจริงเกิดขึ้นที่ [[align-program-admin-screens#หน้าจอ 6 — อนุมัติบัญชีผู้ใช้ (Account Approval Queue)|align-program-admin-screens หน้าจอ 6]] คนละบทบาท

## หน้าจอ 3 — จัดการรายวิชา: CLO และผูก PLO

**Map**: AB-02, AB-03

**จุดประสงค์**: ให้อาจารย์ป้อน CLO ของรายวิชา (ระบุกลุ่มหลักสูตรของวิชาก่อนเสมอ) และผูกความสัมพันธ์ CLO–PLO ภายในกลุ่มหลักสูตรเดียวกันเท่านั้น ก่อนระบบจะปลดล็อกให้บันทึกการสอนได้

**Layout**: หน้าจัดการรายวิชาใช้ tab 2 แท็บ — แท็บนี้คือ "CLO & PLO" (แท็บที่สองคือ "Course Syllabus" หน้าจอ 4)

1. หัวหน้า: ชื่อวิชา + Curriculum Tag ของวิชานี้ (fixed ตอนสร้างวิชา, ไม่ให้แก้ทีหลังในหน้านี้เพื่อกันข้อมูลปนกลุ่ม — ตาม AB-02: "ไม่สามารถป้อน CLO โดยไม่ระบุกลุ่มหลักสูตรได้")
2. รายการ CLO ของวิชา (การ์ดต่อข้อ): รหัส CLO (font `IBM Plex Mono` ตาม DESIGN.md §2.2), คำอธิบาย, และรายการ PLO ที่ผูกไว้แสดงเป็น chip เล็ก — **ตัวเลือก PLO ที่เลือกผูกได้ต้องกรองมาจากกลุ่มหลักสูตรเดียวกับ CLO นี้เท่านั้น** (dropdown/selector ไม่แสดง PLO ต่างกลุ่มให้เลือกเลย ป้องกันการผูกผิดตั้งแต่ UI ไม่ใช่แค่ validate ตอนบันทึก — ตรงกับ constraint ที่ backend บังคับใน `clo_plo_mapping`)
   - ตัวอย่าง (วิชา 127121 การรู้เท่าทันสื่อดิจิทัล, หลักสูตร 2565): CLO1 "วิเคราะห์และประเมินความน่าเชื่อถือของข้อมูลข่าวสารดิจิทัลได้" ผูก PLO1; CLO2 "อธิบายกลไกการทำงานของอัลกอริทึมสื่อสังคมออนไลน์และผลกระทบต่อผู้รับสารได้" ผูก PLO2; CLO3 "ประยุกต์ใช้เครื่องมือตรวจสอบข้อเท็จจริง (Fact-checking) กับเนื้อหาสื่อดิจิทัลได้" ผูก PLO2, PLO3; CLO4 "วิเคราะห์ผลกระทบของสื่อดิจิทัลต่อพฤติกรรมผู้รับสารและสังคมได้" ผูก PLO4 (ดูรายการ PLO ทั้งหมดที่ [[../../01-requirements/01-spec/plo-course-master-data|plo-course-master-data]])
3. Gap Alert Banner แบบ inline ท้ายรายการ: ถ้ายังไม่มี CLO ใดผูกกับ PLO เลยสักข้อ แสดงข้อความ "ยังไม่มี CLO ที่ผูกกับ PLO — ต้องผูกอย่างน้อย 1 คู่ก่อนจึงบันทึกการสอนได้" (โทน `status.gap`, เป็นกลาง)
4. ปุ่ม "เพิ่ม CLO" ท้ายรายการ

**Curriculum tag**: แสดงที่หัวหน้าและกำกับตัวเลือก PLO ทุกจุด (UX Rule 2)

**States**: Empty State (ยังไม่มี CLO เลย), บล็อกไม่ให้ไปหน้าจอ 5 (บันทึกการสอน) จนกว่าเงื่อนไข "CLO ≥1 ผูก PLO ≥1" ผ่าน — สะท้อนด้วย badge สถานะที่หน้าจอ 2

**จุดเชื่อมต่อ**: จากหน้าจอ 2 → สลับแท็บไปหน้าจอ 4 (Course Syllabus) ได้ในหน้าเดียวกัน → เมื่อเงื่อนไขผ่านแล้ว ปลดล็อกปุ่ม "บันทึกการสอน" ที่หน้าจอ 2 ให้ไปหน้าจอ 5

2. ตารางรายการหัวข้อ syllabus ปัจจุบัน แสดงคอลัมน์: สัปดาห์ที่, หัวข้อ, รายละเอียด (ย่อ), ปุ่มแก้ไข/ลบต่อแถว — ตัวอย่าง (127121 การรู้เท่าทันสื่อดิจิทัล): สัปดาห์ที่ 5 "อัลกอริทึมสื่อสังคมออนไลน์", สัปดาห์ที่ 10 "การตรวจสอบข้อเท็จจริง (Fact-checking)" ส่วนสัปดาห์ที่ 1 และ 14 เป็นตัวอย่างหัวข้อที่ยังไม่มีบันทึกการสอนรองรับ (ดู gap ที่หน้าจอ 1/6/7)
3. แถบท้ายหน้า: "แก้ไขล่าสุดโดย [ชื่อ] เมื่อ [วันที่]" (`text.caption`, สี `text.secondary`) — สอดคล้องกับ `updated_by`/`updated_at`
4. Curriculum Tag ของวิชานี้แสดงกำกับที่หัวหน้า (สืบทอดจาก `course.curriculum_id`)

**Curriculum tag**: กำกับที่หัวหน้าเช่นเดียวกับหน้าจอ 3 (UX Rule 2)

**States**: Empty State เมื่อยังไม่มี syllabus — ข้อความ "ยังไม่มีข้อมูล course syllabus ของวิชานี้ — เริ่มป้อนหรืออัปโหลด" (ไม่ใช้คำว่า "ขาด/ผิดพลาด")

**จุดเชื่อมต่อ**: แท็บคู่กับหน้าจอ 3 ภายในหน้าจัดการรายวิชาเดียวกัน — syllabus ที่ป้อนที่นี่ถูกใช้เป็น input ให้ AI Review Panel (หน้าจอ 6) และสรุปรายวิชา (หน้าจอ 8)

## หน้าจอ 5 — บันทึกการสอน (Teaching Record Entry)

**States**: ฟอร์มว่าง (เริ่มต้น), มีไฟล์แนบแล้วอย่างน้อย 1 ไฟล์ (ปุ่มบันทึก enable), Empty State ของ Evidence Attachment List ก่อนแนบไฟล์แรก ("ยังไม่มีไฟล์แนบ — ลากไฟล์มาวางหรือเลือกไฟล์")

## หน้าจอ 6 — ตรวจสอบและยืนยันผล AI (AI Review Panel)

**Map**: AB-08, AB-09, AB-10, AB-20, AB-21, AB-22

**จุดประสงค์**: หน้านี้คือหัวใจของกฎ human-in-the-loop (กฎทางธุรกิจ #3) — แสดงผลจาก AI ทั้งหมด (ผลจับคู่ CLO/PLO, สัดส่วน %, ความถี่ที่แมทช์, ผล gap เทียบ syllabus) เป็น **draft ล้วน** ให้อาจารย์ตรวจสอบ แก้ไข และกด "ยืนยัน" ก่อนเท่านั้นจึงจะถือเป็นข้อมูลจริง

**Layout** (แบ่ง 2 ส่วนชัดเจนตามที่ technical design แยก entity คนละตัว — **ห้ามปนกันในสายตาเดียว**):

### ส่วนที่ 1 — ผลจับคู่ CLO/PLO (จาก `ai_match_result`, AB-08/AB-09/AB-10)

- ใช้ **AI Review Panel** component ตาม DESIGN.md §3: ปุ่มหลักคือ **"ยืนยัน"** ไม่ใช่ auto-save, มีปุ่ม **"แก้ไข"** และ **"ปฏิเสธ"** แยกชัดเจนต่อรายการ
- ต่อ CLO แต่ละข้อที่ AI จับคู่ได้ (เฉพาะ CLO ในกลุ่มหลักสูตรเดียวกับวิชานี้เท่านั้น — AB-08): แสดง **Match % Indicator แบบ Draft** — เส้นขอบ**ประ** สี `status.draft`, พื้นหลัง `status.draft-tint` พร้อม label "ผลจาก AI — ยังไม่ยืนยัน" กำกับเสมอ (แยกจาก Confirmed อย่างชัดเจนที่สุดตาม UX Rule 1 — นี่คือกฎที่พลาดไม่ได้ที่สุดของระบบ)
- รายการ PLO ที่เชื่อมโยงต่อจาก CLO นั้น (AB-09) แสดงเป็น chip ใต้ CLO แต่ละข้อ พร้อมข้อความสรุป เช่น "CLO3 · ประยุกต์ใช้เครื่องมือตรวจสอบข้อเท็จจริง (Fact-checking) กับเนื้อหาสื่อดิจิทัลได้ — เชื่อมกับ PLO2 · PLO3 (127121 การรู้เท่าทันสื่อดิจิทัล · หลักสูตร 2565)" — ระบุ Curriculum Tag กำกับ (สืบทอดจากกลุ่มหลักสูตรเดียวกับ CLO)
- อาจารย์แก้ไขได้ก่อนยืนยัน (AB-10): ปุ่ม "แก้ไข" เปิดให้ปรับค่า % หรือปลด CLO ที่จับคู่ผิดออก (state เปลี่ยนเป็น "edited" — ยังคงแสดงเป็นเส้นประ `status.draft` จนกว่าจะกด "ยืนยัน" จริง)
- ปุ่ม "ยืนยันผลจับคู่ทั้งหมด" ต่อท้าย — กดแล้ว badge ของรายการที่ยืนยันเปลี่ยนเป็น **เส้นทึบสี `status.confirmed`** ทันที (visual feedback ชัดเจนว่าเปลี่ยนสถานะแล้ว)

### ส่วนที่ 2 — ผลวิเคราะห์ Gap เทียบ Course Syllabus (จาก `syllabus_gap_result`, AB-22 — **แยกจากส่วนที่ 1 โดยสิ้นเชิงตามสเปค**)

- Gap Alert Banner โทน `status.gap`/`status.gap-tint` แสดง 2 รายการแยกกัน:
  - **หัวข้อที่ขาด** (`missing_topics`) — หัวข้อใน syllabus ที่ยังไม่พบการสอนจริงรองรับ
  - **หัวข้อที่สอนเพิ่มนอกแผน** (`extra_topics`) — หัวข้อที่สอนจริงแต่ไม่มีใน syllabus
  - ตัวอย่าง (127121 การรู้เท่าทันสื่อดิจิทัล): `missing_topics` พบหัวข้อสัปดาห์ที่ 1 และสัปดาห์ที่ 14 ที่ยังไม่มีบันทึกการสอนรองรับ (ตรงกับ CLO4 ที่ยังไม่มีหลักฐานที่หน้าจอ 1); `extra_topics` พบการสอนเสริมสัปดาห์ที่ 12 (Workshop "การตรวจสอบข่าวปลอมด้วยเครื่องมือ AI") ที่ไม่ได้ระบุไว้ใน syllabus เดิม
- ทั้งสองรายการมีเส้นขอบ**ประ** สี `status.draft` เช่นเดียวกับส่วนที่ 1 จนกว่าจะยืนยัน (state เดียวกัน: draft/edited/confirmed/rejected) — อาจารย์แก้ไขรายการก่อนกดยืนยันได้เช่นกัน
- ปุ่ม "ยืนยันผลวิเคราะห์ gap" แยกต่างหากจากปุ่มยืนยันผลจับคู่ CLO/PLO ในส่วนที่ 1 (เพราะเป็นคนละ endpoint/entity — บันทึกอิสระจากกัน อาจยืนยันส่วนใดส่วนหนึ่งก่อนก็ได้)
- โทนข้อความเป็นกลาง ไม่ตัดสิน เช่น "พบหัวข้อใน syllabus ที่ยังไม่มีบันทึกการสอนรองรับ 2 หัวข้อ" (ไม่ใช้ "ผิดพลาด/สอนไม่ครบ")

**Curriculum tag**: กำกับทุกจุดที่มี CLO/PLO (UX Rule 2)

**States**: กำลังประมวลผล (AI กำลังทำงาน — ใช้ inline loading indicator เรียบ ไม่ใช้แอนิเมชันดึงความสนใจ), draft ครบทุกรายการยังไม่ยืนยัน, ยืนยันบางส่วนแล้ว (ผสม draft+confirmed ในหน้าเดียวได้ แต่ต้องแยก visual ชัดต่อรายการเสมอ), ปฏิเสธผลบางรายการ (state='rejected' — เอาออกจากรายการที่จะถูกนับ ไม่ลบประวัติ)

**จุดเชื่อมต่อ**: มาจากหน้าจอ 5 ทันทีหลังบันทึก → เมื่อยืนยันแล้วกลับไปหน้าจอ 1 (แดชบอร์ด, ค่าจะอัปเดต) หรือหน้าจอ 8 (สรุปรายวิชา)

## หน้าจอ 8 — สรุปรายวิชา (Course Summary)

**Map**: AB-11 (ระดับวิชา), AB-16 (เนื้อหา Area of Improvement), AB-20, AB-21, AB-22/23 (สรุป gap ระดับวิชา)

**จุดประสงค์**: สรุปความสอดคล้อง CLO/PLO, แนวโน้ม, และจุดที่ควรพัฒนาของรายวิชาหนึ่งวิชา ก่อนออกเอกสาร

**Layout**:
1. หัวหน้า: ชื่อวิชา + Curriculum Tag + Stat Tile ตัวเลข % ความสอดคล้องรวมของวิชานี้ (เส้นทึบ `status.confirmed` เท่านั้น เพราะเป็นค่าที่คำนวณจาก confirmed แล้วเสมอตามนิยาม `clo_coverage_summary`)
2. รายการ CLO แต่ละข้อ: Match % Indicator (เส้นทึบ confirmed) + **ความถี่ที่แมทช์ (match frequency)** แสดงประกอบกันเสมอในบรรทัดเดียว เช่น "CLO3 · ประยุกต์ใช้เครื่องมือตรวจสอบข้อเท็จจริง (Fact-checking) กับเนื้อหาสื่อดิจิทัลได้ — แมทช์แล้ว 72% · พบหลักฐานรองรับ 2 ครั้ง (สัปดาห์ที่ 10 และสอนเสริมสัปดาห์ที่ 12, 127121 การรู้เท่าทันสื่อดิจิทัล)" (AB-21 — ห้ามแสดงแค่สัดส่วนอย่างเดียวโดยไม่มีความถี่)
3. **Trends** (แนวโน้มตลอดเทอม): กราฟเส้นเรียบง่าย (line, สีเดียว `primary.green`, ไม่มี gradient) แสดงแนวโน้ม coverage_percent ตามช่วงเวลา
4. **สรุป Gap เทียบ course syllabus** (จาก `syllabus_gap_result` ที่ confirmed แล้ว): รายการ missing/extra topics แบบย่อ (ลิงก์ไปหน้าจอ 6 หากมี draft ค้างอยู่ที่ยังไม่ยืนยัน)
5. **Area of Improvement** (AB-16): แบ่ง 3 ระดับตามสเปค — เนื้อหาอ้างอิงเฉพาะช่องว่าง/CLO ขาดหลักฐาน, match % ต่ำ, หรือ gap เทียบ syllabus ที่ตรวจพบจริงและ**ยืนยันแล้ว**เท่านั้น (กฎทางธุรกิจ #3) ไม่ใช่ข้อความลอยๆ — ใช้โทนภาษาเป็นกลาง ให้กำลังใจ (UX Rule 3) เช่น "CLO2 (127121 การรู้เท่าทันสื่อดิจิทัล — อธิบายกลไกการทำงานของอัลกอริทึมสื่อสังคมออนไลน์และผลกระทบต่อผู้รับสารได้) ยังมีหลักฐานรองรับน้อย (ความถี่ 1 ครั้ง จากสัปดาห์ที่ 5) — พิจารณาเพิ่มกิจกรรม/ชิ้นงานที่เชื่อมโยงกับหัวข้อนี้ในรอบถัดไป"

## หน้าจอ 9 — ออกเอกสาร Word (Word Export Panel)

**Map**: AB-15, AB-16, AB-18

**จุดประสงค์**: สร้างเอกสารสรุปความสอดคล้อง CLO/PLO เป็นหลักฐานประกันคุณภาพ/มคอ. โดยอ้างอิงเฉพาะข้อมูลที่ยืนยันแล้วเท่านั้น (กฎทางธุรกิจ #4)

**Layout**: ใช้ **Word Export Panel** component ตาม DESIGN.md §3 — แสดงเป็น modal/panel ลอย (`radius.lg`, `shadow.card`) เหนือหน้าจอ 8

1. หัวข้อ panel: "ออกเอกสาร Word — [ชื่อวิชา] · [Curriculum Tag]"
2. รายการสรุปสิ่งที่จะรวมในเอกสาร (read-only preview list): CLO/PLO ที่ยืนยันแล้ว, % ความสอดคล้อง, รายชื่อไฟล์หลักฐานที่จะอ้างอิง (เฉพาะที่แนบจริงในระบบ — กฎทางธุรกิจ #4)
3. **Toggle "รวมส่วน Area of Improvement"** (AB-18, ค่าเริ่มต้นเปิด) — ปิดได้ตามความต้องการของแต่ละสถานการณ์ ไม่กระทบความถูกต้องของเนื้อหาหลักฐานหลัก (AC ของ AB-18)
4. ปุ่มหลัก "ดาวน์โหลดเอกสาร Word" (`primary.green`)
5. หมายเหตุท้าย panel (`text.caption`, `text.secondary`): "เอกสารอ้างอิงเฉพาะข้อมูลและหลักฐานที่ยืนยันแล้วในระบบเท่านั้น" — ย้ำกฎทางธุรกิจ #4 ให้อาจารย์เห็นก่อนกดดาวน์โหลดทุกครั้ง

**Curriculum tag**: กำกับที่หัวข้อ panel เสมอ (ป้องกันสับสนเมื่อวิชาเดียวมีหลายกลุ่มหลักสูตรในบางกรณี)

**States**: กำลังสร้างเอกสาร (loading เรียบ), สร้างเสร็จ (ปุ่มเปลี่ยนเป็น "ดาวน์โหลดไฟล์" พร้อม timestamp), มี draft ค้างที่ยังไม่ยืนยัน (แสดง Gap Alert Banner เตือนใน panel นี้ด้วยว่าข้อมูลบางส่วนจะไม่ถูกรวมเพราะยังไม่ยืนยัน — ไม่บล็อกการ export แต่แจ้งให้ทราบล่วงหน้า)

**จุดเชื่อมต่อ**: เปิดจากหน้าจอ 8 (modal ทับหน้าเดิม) → ปิดกลับไปหน้าจอ 8 หลังดาวน์โหลดเสร็จ
