# High-Level Architecture (Conceptual): ระบบติดตามความสอดคล้อง CLO/PLO (ALIGN)

เอกสารนี้อธิบายภาพรวมของระบบ ALIGN ในระดับ **ส่วนประกอบเชิงตรรกะ (logical component) และการไหลของข้อมูลตาม user journey จริง** โดยตั้งใจ**ไม่ผูกมัดกับ technical stack ใดๆ** (ไม่มีชื่อภาษาโปรแกรม, framework, database engine, cloud provider) — ใช้คำอธิบายเชิงหน้าที่ (functional) แทนเสมอ

เอกสารนี้เป็น**ชั้นแนวคิดที่มาก่อน** [[align-technical-design|align-technical-design]] — แนะนำให้อ่านเอกสารนี้ก่อนเพื่อเข้าใจภาพรวม "มีส่วนไหนบ้าง คุยกับใคร ข้อมูลไหลยังไง" แล้วจึงไปอ่าน `align-technical-design.md` ต่อสำหรับรายละเอียด schema/API/endpoint จริง เมื่อพบว่าเนื้อหาที่นี่ทับซ้อนกับ `align-technical-design.md` §1/§4 จะใช้วิธีอ้างอิง (ลิงก์) แทนการ copy ซ้ำ

## 1. System Context

### ผู้ใช้งาน (Actors ที่มี login จริง — 2 บทบาทเท่านั้น)

- **อาจารย์ผู้สอน (Instructor)** — สมัครใช้งานเอง, ป้อนข้อมูลรายวิชา/CLO/course syllabus, บันทึกการสอน+แนบหลักฐาน, ตรวจสอบ/ยืนยันผล AI, ออกเอกสาร Word ของวิชาตนเอง
- **ผู้บริหารหลักสูตร (Program Administrator)** — อาจารย์ที่รับผิดชอบหลักสูตร ตั้งค่ากลุ่มหลักสูตร/PLO, ดูภาพรวมระดับหลักสูตร, **อนุมัติ/ปฏิเสธบัญชีอาจารย์ผู้สอนที่สมัครเอง**, ดาวน์โหลดเอกสารหลักฐานของวิชาในความดูแลเพื่อทำ SAR

ทั้งสองบทบาทมี**ประสบการณ์ผู้ใช้แยกขาดจากกัน**อย่างสมบูรณ์ (คนละบัญชี คนละเมนู) — ระบบไม่มีกลไก "สลับบทบาท" ภายในเซสชันเดียว (อ้าง [[../01-prototypes/align-navigation-flow|align-navigation-flow]] หัวข้อเปิด)

### ระบบ/บุคคลภายนอกที่เกี่ยวข้อง (แต่ไม่ใช่ user ของระบบ)

- **งานประกันคุณภาพ (QA)** — เป็น **touchpoint ภายนอกระบบโดยเจตนา** ไม่มี login, ไม่มีบัญชี, ไม่มี endpoint ใดในระบบ ALIGN ให้เข้าถึงโดยตรง ได้รับเฉพาะ**ไฟล์เอกสารที่ผู้บริหารหลักสูตรดาวน์โหลดแล้วส่งต่อเองนอกระบบ** (ดู Data Flow ข้อ 4 ด้านล่าง) — ห้ามออกแบบ component ใดที่เปิดช่องให้ QA เข้าระบบ ไม่ว่าทางตรงหรือทางอ้อม (กฎทางธุรกิจ #6, Out of Scope)

### ขอบเขตของระบบ (System Boundary)

**อยู่ในขอบเขต** (สอดคล้อง Epic E1–E6 ในสเปค):
- การตั้งค่ากลุ่มหลักสูตร (2565/2570), PLO, CLO และการผูก CLO–PLO
- การป้อน/อัปโหลด course syllabus (ทั้งไฟล์ทางการและหัวข้อรายสัปดาห์)
- การบันทึกการสอนจริงพร้อมแนบหลักฐาน
- การจับคู่ CLO/PLO ด้วย AI และการวิเคราะห์ gap เทียบ syllabus ด้วย AI (สองงานอิสระจากกัน)
- แดชบอร์ด/การแจ้งเตือนความสอดคล้อง
- การออกเอกสาร Word สำหรับหลักฐานประกันคุณภาพ/มคอ.
- การสมัครสมาชิกแบบ self-service และการอนุมัติ/ปฏิเสธบัญชีโดยผู้บริหารหลักสูตร

**อยู่นอกขอบเขต** (ตาม Out of Scope ในสเปค — ห้ามออกแบบ component ใดๆ ที่ทำหน้าที่เหล่านี้):
- ระบบจัดตารางสอน/ตารางเรียน
- ระบบให้คะแนน/เกรดรายบุคคลของนักศึกษา
- ระบบบริหารจัดการหลักสูตรแบบเต็มรูปแบบ (เช่น การปรับปรุงหลักสูตร มคอ.2)
- บัญชีผู้ใช้/สิทธิ์การเข้าถึงสำหรับ QA — ไม่มี role/entity ใดในระบบสำหรับ QA

### แผนภาพบริบทระบบ (conceptual)

        อาจารย์ผู้สอน                         ผู้บริหารหลักสูตร
       (Instructor)                    (Program Administrator)
             │                                     │
             │  (คนละบัญชี คนละประสบการณ์ผู้ใช้ ไม่มีจุดสลับบทบาท)
             ▼                                     ▼
     ┌─────────────────────────────────────────────────────┐

## 2. Logical Components

ตารางต่อไปนี้ใช้ชื่อเชิงหน้าที่ล้วนๆ — ผู้อ่านที่ต้องการชื่อ/เทคโนโลยีที่เสนอจริงให้ดูที่ [[align-technical-design|align-technical-design]] §1 (ภาพรวมสถาปัตยกรรม) และ §5 (Tech Stack — ข้อเสนอ) แทน

| Logical Component | ความรับผิดชอบ | ใครคุยด้วย / Trust Boundary |
|---|---|---|
| **ส่วนติดต่อผู้ใช้ (User-Facing Interface)** — แยก 2 ชุดตามบทบาท | แสดงหน้าจอ/รับข้อมูลจากอาจารย์ผู้สอน และแยกอีกชุดสำหรับผู้บริหารหลักสูตร (ตาม [[../01-prototypes/align-app-screens|align-app-screens]] และ [[../01-prototypes/align-program-admin-screens|align-program-admin-screens]]) | อยู่ฝั่งผู้ใช้ (**untrusted**) — ไม่ถือสิทธิ์ตัดสินใจใดๆ เอง ทุกคำสั่งต้องผ่าน "ประตูควบคุมสิทธิ์" ก่อนเสมอ แม้ UI จะ disable ปุ่มไว้ล่วงหน้าเพื่อ UX (เช่น ปุ่มบันทึกการสอนที่ล็อกไว้จนกว่า CLO–PLO จะครบ) ก็เป็นเพียง "ความสะดวก" ไม่ใช่ตัวบังคับใช้กฎจริง |
| **ประตูควบคุมสิทธิ์และสถานะบัญชี (Access Gate)** | ตรวจสอบ **ทุก** คำร้องขอที่ต้อง login ว่า (ก) บัญชีอยู่ในสถานะ "อนุมัติแล้ว" หรือไม่ (กฎ #6) และ (ข) บทบาท/ขอบเขตหลักสูตรของผู้ใช้ตรงกับสิ่งที่ร้องขอหรือไม่ (PDPA, กฎ #5) — มีเพียง 2 ทางร้องขอเท่านั้นที่ยกเว้นการตรวจ (ก): "สมัครสมาชิก" และ "เช็คสถานะบัญชีของตนเอง" | เป็น**ขอบเขตความน่าเชื่อถือหลักของระบบ** (trust boundary) คั่นระหว่างส่วนติดต่อผู้ใช้ (untrusted) กับส่วนที่เหลือของระบบ (trusted) — ไม่มี component อื่นใดอนุญาตให้ข้ามประตูนี้ได้ |
| **แกนประสานงานและบังคับใช้กฎทางธุรกิจ (Core Orchestration)** | เป็นจุดศูนย์กลางที่: (1) บังคับเงื่อนไข "ต้องผูก CLO–PLO ครบก่อนบันทึกการสอน" (กฎ #1) ก่อนเขียนข้อมูลจริงทุกครั้ง ไม่ใช่แค่ที่หน้าจอ, (2) ส่งข้อมูลที่ scope เฉพาะกลุ่มหลักสูตรเดียวกันให้กลไก AI ประมวลผล, (3) รวมผลที่ยืนยันแล้วเป็นค่าสรุป (% ความสอดคล้อง, ความถี่ที่แมทช์), (4) เป็นประตูเดียวที่คุยกับที่เก็บหลักฐาน — ไม่ให้ส่วนติดต่อผู้ใช้เข้าถึงตรง | รับคำร้องเฉพาะที่ผ่านประตูควบคุมสิทธิ์แล้วเท่านั้น เป็นผู้เขียนเพียงผู้เดียวลงที่เก็บข้อมูลโครงสร้างและเป็นผู้ตัดสินว่าอะไรคือ "ข้อมูลยืนยันแล้ว" |
| **กลไกจับคู่/วิเคราะห์ด้วย AI (AI Matching & Gap-Analysis Engine)** — แยกเป็น **2 งานอิสระจากกัน** ตามสเปค (E3, AB-08/20/21 กับ AB-22) | (ก) จับคู่ข้อมูลการสอน 1 รายการกับ CLO **เฉพาะของกลุ่มหลักสูตรเดียวกับวิชานั้น** พร้อมค่าความตรง แล้วเชื่อมต่อ PLO ที่ผูกไว้แล้ว, (ข) เปรียบเทียบหัวข้อการสอนจริงสะสมของทั้งวิชา กับหัวข้อรายสัปดาห์ที่วางแผนไว้ใน syllabus แยกหา "หัวข้อที่ขาด" และ "หัวข้อที่สอนเพิ่มนอกแผน" — **ทั้งสองงานคืนผลเป็น "ค่าตั้งต้น/draft" เสมอ ไม่มีสิทธิ์เขียนเป็นข้อมูลยืนยันเอง** ไม่ว่าค่าความมั่นใจจะสูงแค่ไหน (กฎ #3 — ข้อบังคับที่พลาดไม่ได้ที่สุด) | รับ input เฉพาะที่แกนประสานงานคัดกรอง/จำกัด scope มาให้แล้ว (เช่น เฉพาะ CLO ของ curriculum เดียวกัน) — **ไม่มีสิทธิ์เขียนตรงลงที่เก็บข้อมูลโครงสร้างส่วนที่ถือเป็น "ข้อมูลจริง"** ผลลัพธ์ทั้งหมดต้องผ่านแกนประสานงานไปพักในสถานะ draft ก่อนเสมอ |
| **ที่เก็บข้อมูลโครงสร้าง (Structured Data Store)** | เก็บ curriculum/PLO/CLO/การผูก CLO–PLO/รายวิชา/บันทึกการสอน/ผลจับคู่ AI (ทั้ง draft และยืนยันแล้ว)/ผลวิเคราะห์ gap/บัญชีผู้ใช้และสถานะบัญชี — เป็นแหล่งความจริงเดียว (single source of truth) ของสถานะ "ยืนยันแล้ว" เทียบกับ "draft" | เขียน/อ่านได้เฉพาะผ่านแกนประสานงานเท่านั้น ไม่มี component ภายนอก (รวม AI engine และ Document Export Generator) เขียนตรงได้ |
| **ที่เก็บหลักฐาน/ชิ้นงานควบคุมสิทธิ์ตาม PDPA (Access-Controlled Evidence Repository)** | เก็บไฟล์ชิ้นงาน/หลักฐานที่แนบกับบันทึกการสอน และไฟล์ course syllabus ทางการที่อัปโหลด (เก็บไว้อ้างอิงเฉยๆ ไม่ถูกนำไปวิเคราะห์อัตโนมัติ) — ชิ้นงานนักศึกษาอาจมีข้อมูลส่วนบุคคลปะปน จึงต้องมีการควบคุมสิทธิ์เข้มงวดกว่าข้อมูลอื่น | **ทุก**การเข้าถึง (ดู/ดาวน์โหลด) ต้องผ่านแกนประสานงานเพื่อตรวจสิทธิ์ PDPA ก่อนเสมอ (เฉพาะอาจารย์ผู้สอนวิชานั้น หรือผู้บริหารหลักสูตรที่มีขอบเขตหลักสูตรตรงกัน — กฎ #5) — ไม่มี component ใด (รวมส่วนติดต่อผู้ใช้) เข้าถึง storage ได้ตรง |
| **กลไกแจ้งเตือนช่องว่างหลักฐาน (Gap Notification Mechanism)** | ตรวจจับ CLO ที่ยังไม่มีข้อมูลการสอน/หลักฐานรองรับ แล้วแจ้งอาจารย์**ทันที**ที่ตรวจพบ (กฎ #2) — คำนวณจากข้อมูลล่าสุด ณ เวลาที่มีการโหลดแดชบอร์ดหรือหลังมีเหตุการณ์เกี่ยวข้อง (เช่น บันทึกการสอนใหม่/ยืนยันผล AI ใหม่) ไม่ใช่รอบตรวจแบบสรุปเป็นรอบ (แนวทางนี้ยึดตามที่ [[align-technical-design|align-technical-design]] §3 ระบุไว้แล้วว่าเป็น near-real-time query ไม่ใช่ batch job) | อ่านจากที่เก็บข้อมูลโครงสร้างผ่านแกนประสานงานเท่านั้น เป็น component อ่านอย่างเดียว ไม่มีสิทธิ์เขียน |
| **กลไกสร้างเอกสารส่งออก (Document Export Generator)** | ประกอบเอกสาร Word/มคอ. จากข้อมูลที่ "ยืนยันแล้ว" เท่านั้น (ผลจับคู่ CLO/PLO ที่ยืนยัน, ค่าสรุป %/ความถี่ที่คำนวณจากค่ายืนยันแล้ว, ผลวิเคราะห์ gap ที่ยืนยันแล้วสำหรับ Area of Improvement, และหลักฐานที่แนบจริง) — **ห้ามอ่าน draft จาก AI เด็ดขาด** (กฎ #4) | รับคำสั่งผ่านแกนประสานงานเท่านั้น อ่านที่เก็บข้อมูลโครงสร้าง+ที่เก็บหลักฐานผ่านแกนประสานงาน ไม่เชื่อมตรงกับกลไก AI — เอกสารที่สร้างเสร็จแล้ว "ออกจากขอบเขตระบบ" ทันทีที่ถูกดาวน์โหลด (กลายเป็นไฟล์ภายนอกที่ผู้บริหารหลักสูตรส่งต่อ QA เอง) |
| **บันทึกการเข้าถึงหลักฐาน (Access Audit Log)** | บันทึกทุกครั้งที่มีการดู/ดาวน์โหลดไฟล์หลักฐาน (ใคร, เมื่อไร, ทำอะไร) เพื่อให้ผู้บริหารหลักสูตรตรวจสอบย้อนหลังได้ตาม PDPA (AB-07) | เขียนโดยแกนประสานงานทุกครั้งที่มีการเข้าถึงหลักฐานสำเร็จ อ่านได้เฉพาะผู้บริหารหลักสูตร |

**หมายเหตุเรื่องความสอดคล้องกับ `align-technical-design.md`**: ตารางข้างต้นสอดคล้องกับภาพในหัวข้อ 1 ของ `align-technical-design.md` (Backend API ↔ ที่นี่คือ "ประตูควบคุมสิทธิ์" + "แกนประสานงาน" รวมกัน, AI Matching Service ↔ "กลไกจับคู่/วิเคราะห์ด้วย AI", Evidence/File Storage ↔ "ที่เก็บหลักฐาน...", Word-export Service ↔ "กลไกสร้างเอกสารส่งออก") เพียงแต่เอกสารนี้แยก "ประตูควบคุมสิทธิ์" ออกจาก "แกนประสานงาน" อย่างชัดเจนเป็น 2 หน้าที่เชิงตรรกะ เพื่อเน้น trust boundary ที่เป็นข้อบังคับ (กฎ #5/#6) ให้เห็นชัดกว่าการรวมเป็นกล่องเดียว — ไม่ใช่การขัดแย้งกับโครงสร้างเดิม

## 3. Data Flow ตาม User Journey

ทุก flow ด้านล่างอ้างอิงหมายเลขหน้าจอจาก [[../01-prototypes/align-navigation-flow|align-navigation-flow]] และ [[../01-prototypes/align-user-journey|align-user-journey]] โดยตรง ไม่ได้แต่งขั้นตอนขึ้นใหม่

### 3.1 บันทึกการสอน → AI จับคู่ CLO/PLO → อาจารย์ยืนยัน/แก้ไข/ปฏิเสธ

อ้างอิง: journey แถว "ระหว่างเทอม — หลังสอนแต่ละคาบ" และ navigation-flow หัวข้อ 1 (เส้นทาง `5 → 6 → 1`)

1. อาจารย์ผู้สอน (บัญชี `approved` แล้ว) อยู่ที่**ส่วนติดต่อผู้ใช้** หน้าจอ 5 (บันทึกการสอน) ซึ่งเข้าถึงได้เฉพาะรายวิชาที่ผูก CLO–PLO ครบแล้ว (กฎ #1 — ปุ่มถูกปลดล็อกจากหน้าจอ 3 ตามเงื่อนไข `clo_plo_ready`)
2. อาจารย์กรอกหัวข้อการสอน + แนบไฟล์หลักฐาน 1 ไฟล์ขึ้นไป (AB-05/06) แล้วกด "บันทึกและให้ AI ประมวลผล"
3. คำร้องขอผ่าน**ประตูควบคุมสิทธิ์** (ตรวจ `account_status = approved` + role = instructor) เข้าสู่**แกนประสานงาน**
4. แกนประสานงานตรวจซ้ำเงื่อนไข "วิชานี้ผูก CLO–PLO ครบแล้วหรือไม่" (บังคับที่ฝั่งระบบเสมอ ไม่ใช่เชื่อ UI ฝั่งเดียว) แล้วจึง (ก) เขียนบันทึกการสอนลง**ที่เก็บข้อมูลโครงสร้าง** และ (ข) ส่งไฟล์ที่แนบเข้า**ที่เก็บหลักฐาน/ชิ้นงานควบคุมสิทธิ์ PDPA**
5. แกนประสานงานส่งข้อมูลบันทึกการสอน + เนื้อหาหลักฐาน + **เฉพาะชุด CLO ของกลุ่มหลักสูตรเดียวกับวิชานั้น** ให้**กลไกจับคู่ด้วย AI** ประมวลผล (ป้องกันการจับคู่ข้ามกลุ่ม 2565↔2570 ตาม AB-08)
6. กลไก AI คืนผล `{CLO, ค่าความตรง}` ต่อ CLO แต่ละข้อในชุดที่อนุญาต พร้อม PLO ที่เชื่อมต่อ (ดึงจากการผูกที่มีอยู่แล้ว ไม่ใช่ AI เดา) — แกนประสานงานเขียนผลนี้ลงที่เก็บข้อมูลโครงสร้างเป็น **"ค่าตั้งต้น/draft" เท่านั้น**
7. **[TRUST BOUNDARY / DRAFT STATE — กฎ #3]** ส่วนติดต่อผู้ใช้พาอาจารย์ไปหน้าจอ 6 (AI Review Panel) **ทันที** แสดงผลจับคู่ทั้งหมดด้วยสถานะภาพ "draft" (เส้นขอบประ) — ยังไม่ถือเป็นข้อมูลจริงของระบบ ไม่ถูกนับในแดชบอร์ด/แผนที่ CLO×สัปดาห์/เอกสารส่งออกใดๆ ในขั้นนี้
8. อาจารย์ตรวจสอบทีละรายการ: **ยืนยัน** (state → confirmed), **แก้ไข** ค่า/ปลด CLO ที่จับคู่ผิดก่อนยืนยัน (state → edited แล้วค่อยยืนยัน), หรือ **ปฏิเสธ** (state → rejected, ไม่ถูกนับเป็นหลักฐาน)
9. เฉพาะรายการที่ผ่านการ**ยืนยันโดยอาจารย์**เท่านั้นที่แกนประสานงานนำไปคำนวณสรุป (% ความสอดคล้องระดับวิชา ฐาน 100% จากจำนวน CLO ทั้งหมด, ความถี่ที่แมทช์ต่อ CLO) และป้อนต่อให้แดชบอร์ด (หน้าจอ 1), แผนที่ CLO×สัปดาห์ (หน้าจอ 7), และกลไกแจ้งเตือนช่องว่างหลักฐาน
10. อาจารย์กลับสู่หน้าจอ 1 (แดชบอร์ดอัปเดตค่าใหม่) หรือหน้าจอ 8 (สรุปรายวิชา)

### 3.2 วิเคราะห์ Gap เทียบ Course Syllabus (แยกจาก CLO/PLO matching)

อ้างอิง: journey แถว "ระหว่างเทอม — เทียบกับแผนการสอน", `align-app-screens.md` หน้าจอ 6 ส่วนที่ 2, และ AB-19/AB-22/AB-23

1. เงื่อนไขเบื้องต้น: อาจารย์เคยกรอก "หัวข้อที่วางแผนสอนแต่ละสัปดาห์" ของวิชานั้นไว้แล้วที่หน้าจอ 4 (แยกจากไฟล์ syllabus ทางการที่อัปโหลดไว้เฉยๆ ตาม AB-19 — ไฟล์ทางการ**ไม่ถูกนำไปวิเคราะห์อัตโนมัติ**)
2. เมื่ออาจารย์บันทึกการสอน (ขั้นตอน 3.1) เสร็จ แกนประสานงานจะเรียก**กลไกวิเคราะห์ gap**ของกลไก AI เป็นงานที่**เป็นอิสระ**จากงานจับคู่ CLO/PLO (คนละ endpoint/entity ตาม `align-technical-design.md` §3) โดยส่ง (ก) หัวข้อการสอนจริง**สะสมทั้งหมด**ของวิชานั้น และ (ข) หัวข้อรายสัปดาห์ที่วางแผนไว้ (จาก syllabus.content) เป็น input
3. กลไกวิเคราะห์ gap เปรียบเทียบเชิงความหมาย (ไม่ใช่ string ตรงตัว) แล้วคืนผล `missing_topics` (หัวข้อในแผนที่ยังไม่พบการสอนจริงรองรับ) และ `extra_topics` (หัวข้อที่สอนจริงแต่ไม่อยู่ในแผน)
4. **[TRUST BOUNDARY / DRAFT STATE — กฎ #3]** แกนประสานงานเขียนผลนี้เป็น draft เช่นเดียวกับ 3.1 — แสดงที่หน้าจอ 6 ส่วนที่ 2 ด้วยสถานะภาพ "draft" **แยกกล่องชัดเจนจาก**ผลจับคู่ CLO/PLO ส่วนที่ 1 (คนละปุ่มยืนยัน คนละ entity — ยืนยันส่วนใดก่อนก็ได้ ไม่ผูกกัน)
5. อาจารย์ตรวจสอบ/แก้ไข/ยืนยัน/ปฏิเสธผลนี้แยกต่างหากจากขั้นตอน 3.1
6. เฉพาะผลที่**ยืนยันแล้ว**เท่านั้นที่ถูกใช้ใน (ก) ส่วนเปรียบเทียบ "การสอนจริงเทียบ CLO/syllabus" ในแดชบอร์ด (AB-23, หน้าจอ 1) ซึ่งแยกจากส่วน % ความสอดคล้องรวมและการแจ้งเตือน CLO ขาดหลักฐานอย่างชัดเจน และ (ข) ส่วน "Area of Improvement" ในเอกสารส่งออก (ดูขั้นตอน 3.4)

### 3.3 สมัครสมาชิก → รออนุมัติ → ผู้บริหารหลักสูตรอนุมัติ/ปฏิเสธ (E6)

อ้างอิง: journey แถว "ก่อนเริ่มใช้งาน — สมัครและรออนุมัติบัญชี" (ฝั่งอาจารย์) และ "ต้นปีการศึกษา — อนุมัติบัญชีอาจารย์ผู้สอนใหม่" (ฝั่งผู้บริหารหลักสูตร), navigation-flow หัวข้อ 0 และหัวข้อ 3 (จุดตัดระหว่าง 2 บทบาท)

1. ผู้ที่ยังไม่มีบัญชีเปิด**ส่วนติดต่อผู้ใช้**หน้าจอ 0A (สมัครใช้งาน) กรอกชื่อ/อีเมล/รหัสผ่านเท่านั้น แล้วส่งฟอร์ม
2. คำร้องนี้เป็นคำร้อง**สาธารณะ** — เป็นหนึ่งใน 2 กรณีเดียวที่**ประตูควบคุมสิทธิ์**ไม่ต้องตรวจสถานะบัญชี (เพราะยังไม่มีบัญชีให้ตรวจ) แต่ยังคงเข้าสู่แกนประสานงานตามปกติ
3. แกนประสานงานสร้างบัญชีใหม่ใน**ที่เก็บข้อมูลโครงสร้าง**ด้วยสถานะ **"รออนุมัติ" ทันที** บทบาท = อาจารย์ผู้สอนเสมอ — **ไม่มีการออก token/สิทธิ์ใดๆ ที่พาเข้าถึงฟีเจอร์อื่นของระบบ** ไม่ว่ากรณีใด (กฎ #6)
4. ส่วนติดต่อผู้ใช้พาไปหน้าจอ 0B (สถานะบัญชี) แสดงสถานะ "รออนุมัติ" — เป็น**ทางตัน** ไม่มีเส้นทางลัดไปหน้าจออื่นของระบบ
5. **[TRUST BOUNDARY — ไม่มี handoff ในแอปเดียวกัน]** แยกไปอีกฝั่ง: ผู้บริหารหลักสูตร (บัญชี `approved` แล้ว) เปิด**ส่วนติดต่อผู้ใช้ของตนเอง** (คนละแอป/คนละสิทธิ์) เข้าหน้าจอ 6 (คิวอนุมัติบัญชี) — ประตูควบคุมสิทธิ์อนุญาตเฉพาะบทบาทผู้บริหารหลักสูตรเท่านั้น (admin-only visibility, AB-26)
6. แกนประสานงานส่งรายการบัญชี "รออนุมัติ" และ "บัญชีทั้งหมดที่เคยสมัคร" จากที่เก็บข้อมูลโครงสร้างมาแสดง
7. ผู้บริหารหลักสูตรกด **"อนุมัติ"** หรือ **"ปฏิเสธ"** ต่อบัญชี — แกนประสานงานอัปเดตสถานะในที่เก็บข้อมูลโครงสร้างเป็น `approved` หรือ `rejected` พร้อมบันทึกผู้อนุมัติ+เวลา (audit trail, เหตุผลปฏิเสธเป็นทางเลือก)
8. จุดตัดข้อมูลระหว่าง 2 บทบาทเกิดขึ้น**ผ่านที่เก็บข้อมูลโครงสร้างเท่านั้น** ไม่ใช่ผ่านลิงก์ในแอป — เมื่ออาจารย์ผู้สมัครกลับมาเปิดหน้าจอ 0B อีกครั้ง (หรือระบบ poll สถานะผ่านคำร้องขอสถานะตนเอง ซึ่งเป็นกรณีที่ 2 ที่ประตูควบคุมสิทธิ์ยกเว้นการตรวจ `approved`) จะเห็นสถานะที่เปลี่ยนแล้ว
9. ถ้า `approved` — ปุ่ม "เข้าสู่หน้าแรก" ปรากฏ พาไปหน้าจอ 1 (แดชบอร์ด) และตั้งแต่นี้ **ทุกคำร้องขอถัดไป** (ไม่ใช่แค่ตอน login) จะถูกประตูควบคุมสิทธิ์ตรวจสถานะบัญชีซ้ำทุกครั้ง (AB-25) — หากถูกเปลี่ยนเป็น `rejected` ภายหลังระหว่างใช้งาน ต้องตัดสิทธิ์ทันที
10. ถ้า `rejected` — อาจารย์ยังคงติดอยู่ที่หน้าจอ 0B พร้อมข้อความแจ้งสถานะ (และเหตุผลถ้ามีการระบุ) ไม่มีทางเข้าถึงฟีเจอร์ใดของระบบได้อีก

### 3.4 ออกเอกสาร Word ที่อ้างอิงเฉพาะข้อมูลยืนยันแล้ว

อ้างอิง: journey แถว "ปลายภาคการศึกษา — จัดทำหลักฐานประกันคุณภาพ/มคอ." (ฝั่งอาจารย์) และ "ปลายภาค/ปลายปี — จัดทำรายงานประเมินตนเอง (SAR)" (ฝั่งผู้บริหารหลักสูตร), navigation-flow เส้นทาง `8 → 9` และ `3 → 4`

**เส้นทางฝั่งอาจารย์ผู้สอน:**
1. อาจารย์เปิดหน้าจอ 8 (สรุปรายวิชา) — ถ้ามี draft ค้างที่ยังไม่ยืนยัน ส่วนติดต่อผู้ใช้พากลับไปหน้าจอ 6 ก่อนเสมอ (บังคับให้ human-in-the-loop เสร็จสิ้นก่อนจึงออกเอกสารได้)
2. เปิดหน้าจอ 9 (Export Panel) กด "ดาวน์โหลดเอกสาร Word"
3. คำร้องผ่านประตูควบคุมสิทธิ์ (ตรวจ `approved` + เป็นอาจารย์ผู้สอนของวิชานั้น) เข้าสู่แกนประสานงาน
4. แกนประสานงานรวบรวมข้อมูลให้**กลไกสร้างเอกสารส่งออก** โดยดึง**เฉพาะ**: ผลจับคู่ CLO/PLO ที่สถานะ "ยืนยันแล้ว", ค่าสรุป %ความสอดคล้อง/ความถี่ที่คำนวณจากค่ายืนยันแล้วเท่านั้น, ผลวิเคราะห์ gap ที่ "ยืนยันแล้ว" (สำหรับส่วน Area of Improvement, AB-16), และไฟล์หลักฐานที่แนบไว้จริงในที่เก็บหลักฐาน (ผ่านการตรวจสิทธิ์ PDPA) — **[TRUST BOUNDARY — กฎ #3 + #4 ทำงานร่วมกัน]** กลไกสร้างเอกสารไม่มีทางเข้าถึง draft จาก AI ได้เลยไม่ว่ากรณีใด
5. กลไกสร้างเอกสารประกอบไฟล์ Word พร้อมระบุกลุ่มหลักสูตร (2565/2570) ของวิชากำกับชัดเจน — ทุกการอ้างอิงหลักฐานในเอกสารต้องมีไฟล์จริงรองรับในที่เก็บหลักฐานเท่านั้น (ห้ามสร้างข้อมูลอ้างอิงลอยๆ)
6. ทุกครั้งที่มีการอ้างอิง/แนบหลักฐานในการสร้างเอกสาร แกนประสานงานเขียนบันทึกไว้ที่**บันทึกการเข้าถึงหลักฐาน**
7. ไฟล์เอกสารถูกส่งกลับให้อาจารย์ดาวน์โหลด — **จากจุดนี้ไฟล์ได้ออกจากขอบเขตของระบบแล้ว**

**เส้นทางฝั่งผู้บริหารหลักสูตร (สำหรับ SAR):**
8. ผู้บริหารหลักสูตรเปิดหน้าจอ 3 (แดชบอร์ดภาพรวมหลักสูตร) → หน้าจอ 4 (ดาวน์โหลดเอกสาร SAR)
9. ประตูควบคุมสิทธิ์ตรวจว่าวิชาที่ขอเอกสารอยู่ใน `program_admin_curriculum_scope` ของผู้ใช้หรือไม่ (PDPA, กฎ #5) — ถ้าไม่อยู่ในขอบเขต ปฏิเสธคำร้อง
10. แกนประสานงาน/กลไกสร้างเอกสารทำงานเหมือนขั้นตอน 4–6 ข้างต้น (อ่านเฉพาะข้อมูลยืนยันแล้วเท่านั้นเช่นกัน) แล้วส่งไฟล์ให้ดาวน์โหลด
11. **[System Boundary กับ QA]** ผู้บริหารหลักสูตรนำไฟล์ที่ดาวน์โหลดแล้วไปส่งต่อให้งานประกันคุณภาพ (QA) **ด้วยตนเองนอกระบบ** (เช่น ส่งไฟล์ทางช่องทางภายนอก) — ไม่มี component ใดในระบบ ALIGN ที่ทำหน้าที่ "ส่ง/แจ้ง" ไปยัง QA โดยตรง เพราะ QA ไม่ใช่ปลายทางที่ระบบรู้จัก (out of scope)

|---|---|
| #1 ผูก CLO–PLO ก่อนบันทึกการสอน | แกนประสานงานต้องตรวจเงื่อนไขนี้**ที่ฝั่งระบบทุกครั้งก่อนเขียนข้อมูล** — การ disable ปุ่มที่ UI เป็นเพียงส่วนเสริม UX ไม่ใช่กลไกบังคับใช้จริง ห้ามมีเส้นทางใดในระบบที่เขียนบันทึกการสอนได้โดยไม่ผ่านการตรวจนี้ |
| #2 แจ้งเตือน CLO ที่ไม่มีหลักฐานทันที | กลไกแจ้งเตือนต้องเป็นการคำนวณแบบใกล้เคียงเวลาจริง (สดใหม่ทุกครั้งที่มีเหตุการณ์เกี่ยวข้องเกิดขึ้น หรือทุกครั้งที่แดชบอร์ดถูกเปิด) ไม่ใช่งานสรุปผลเป็นรอบ (เช่น รันทุกคืน) เพราะจะขัดกับ "ทันที" ตามสเปค |
| #3 AI เป็นค่าตั้งต้น ไม่ใช่ค่าบังคับ (**ข้อบังคับที่พลาดไม่ได้ที่สุดของทั้งระบบ**) | **ทุก**ผลลัพธ์จากกลไก AI (ทั้งการจับคู่ CLO/PLO และการวิเคราะห์ gap) ต้องถูกเขียนเป็นสถานะ "draft" เสมอ แกนประสานงานเป็นผู้เดียวที่มีสิทธิ์เปลี่ยนเป็น "ยืนยันแล้ว" และทำได้**ก็ต่อเมื่อ**ได้รับคำสั่งยืนยันชัดเจนจากอาจารย์ผู้สอนคนนั้นเท่านั้น ไม่มีเงื่อนไข ค่าความมั่นใจ หรือ timeout ใดที่ทำให้ระบบ auto-confirm ได้เอง — ทุก component ปลายทาง (แดชบอร์ด, แผนที่ CLO×สัปดาห์, เอกสารส่งออก) ต้องอ่านเฉพาะสถานะ "ยืนยันแล้ว" |
| #4 เอกสารส่งออกอ้างอิงหลักฐานจริงเท่านั้น | กลไกสร้างเอกสารส่งออกต้อง**ไม่มีทางเชื่อมต่อโดยตรง**กับกลไก AI หรือข้อมูลสถานะ draft ใดๆ — เข้าถึงได้เฉพาะข้อมูล/ไฟล์ที่แกนประสานงานยืนยันแล้วว่า "confirmed" และมีไฟล์จริงรองรับในที่เก็บหลักฐานเท่านั้น |
| #5 PDPA — จำกัดสิทธิ์เข้าถึงข้อมูลส่วนบุคคล | ทุก component ที่แตะที่เก็บหลักฐาน (ไม่ว่าจะเป็นแดชบอร์ด, การบันทึกการสอน, การสร้างเอกสาร) ต้องผ่านประตูควบคุมสิทธิ์ก่อนเสมอ ไม่มีทางลัด และทุกการเข้าถึงสำเร็จต้องถูกบันทึกไว้ที่บันทึกการเข้าถึงหลักฐาน |
| #6 บัญชีต้องผ่านการอนุมัติก่อนเสมอ | ประตูควบคุมสิทธิ์ต้องตรวจสถานะบัญชี**ทุกคำร้องขอ**ที่ต้อง login (ไม่ใช่แค่ตอน login ครั้งแรก) ยกเว้นเพียง 2 กรณี (สมัครสมาชิก, เช็คสถานะตนเอง) — หากสถานะเปลี่ยนเป็น "รออนุมัติ"/"ถูกปฏิเสธ" ระหว่างใช้งาน ต้องตัดสิทธิ์ทันที |
| Out of Scope — QA ไม่ใช่ user | ไม่มี logical component ใดในเอกสารนี้ (รวมกลไกสร้างเอกสารส่งออก) ที่เปิดช่องทาง/endpoint ให้ QA เข้าถึงได้โดยตรงไม่ว่าทางใด การส่งเอกสารให้ QA เป็นกิจกรรมที่เกิด**นอกขอบเขตระบบเสมอ** โดยผู้บริหารหลักสูตรเป็นผู้ดำเนินการเอง |
| Cross-cutting — แยกกลุ่มหลักสูตร 2565/2570 | ที่เก็บข้อมูลโครงสร้าง, กลไก AI (ขอบเขตชุด CLO ที่ใช้จับคู่), และกลไกสร้างเอกสาร ต้องเคารพขอบเขตกลุ่มหลักสูตรเสมอ — ห้าม component ใด query/ผสานข้อมูลข้ามกลุ่ม 2565↔2570 |

### 4.2 สมมติฐาน/ข้อจำกัดเชิง conceptual

- ระบบให้บริการ**เฉพาะสาขา New Media Communication สาขาเดียว** (ตาม [[../../01-requirements/01-spec/plo-course-master-data|plo-course-master-data]] และ `CLAUDE.md`) — ไม่ได้ออกแบบให้รองรับหลายสาขา/หลายคณะในชั้นนี้ ฟอร์มสมัครสมาชิกจึงไม่มีฟิลด์ "สังกัด" โดยเจตนา (AB-24)
- สเปคและ backlog **ไม่ได้ระบุปริมาณผู้ใช้คาดการณ์** (จำนวนอาจารย์/รายวิชา/นักศึกษาพร้อมกัน) ไว้ชัดเจน — เอกสารนี้จึงไม่ตั้งสมมติฐานเรื่องขนาด/ปริมาณการใช้งานเอง ปล่อยเป็นเรื่องที่ผู้ใช้/ทีมพัฒนาต้องประเมินร่วมกันในชั้น technical design ถ้าจำเป็นต้องออกแบบเรื่อง capacity
- ทั้งสองบทบาทมี**บัญชีแยกกันเด็ดขาด** ไม่มีผู้ใช้คนเดียวที่ถือทั้งสองบทบาทพร้อมกันตามที่ระบุในสเปค — เอกสารนี้จึงออกแบบ Access Gate ให้ตรวจ role แบบทางเลือกเดียว (exclusive) ไม่ใช่แบบ multi-role

### 4.3 สิ่งที่ยังไม่ตัดสินใจ ณ ชั้นนี้โดยเจตนา (ปล่อยให้ `technical-designer` ตัดสินใจต่อ)

- **เทคโนโลยี/ผลิตภัณฑ์จริง**ของทุก logical component ข้างต้น (ภาษาโปรแกรม, framework, ยี่ห้อฐานข้อมูล, ผู้ให้บริการ cloud, ไลบรารีสร้างเอกสาร Word) — ดู [[align-technical-design|align-technical-design]] §5 (ระบุชัดว่าเป็นข้อเสนอที่ยังไม่ยืนยัน)
- **กลไกภายในที่แท้จริง**ของการเรียกกลไก AI ว่าเป็นการเรียกแบบรอผลทันทีในคำร้องเดียว หรือเป็นงานเบื้องหลังที่ระบบสถานะแล้ว poll ผลภายหลัง — ในเชิงประสบการณ์ผู้ใช้ ระบบต้องพาอาจารย์ไปเห็นผล draft "ทันที" หลังกดบันทึก (ตามที่ยืนยันแล้วใน [[../01-prototypes/align-app-screens|align-app-screens]] หน้าจอ 5→6) แต่**วิธี implement เบื้องหลัง**ว่าเป็นการประมวลผลแบบซิงโครนัสจริงหรือมีคิวงานภายในที่โปร่งใสต่อผู้ใช้ ยังเป็นการตัดสินใจของ technical-designer
- **นิยามที่แน่นอนของ "ช่วงเวลานับความถี่ที่แมทช์" (`match_frequency`)** เมื่อวิชาเดียวกันมีหลายภาคการศึกษาซ้อนกัน — เป็นประเด็นที่ [[align-technical-design|align-technical-design]] §2.10 ระบุไว้แล้วว่ายังไม่ฟันธง เอกสารนี้รับทราบและไม่ตัดสินใจซ้ำ เพียงส่งต่อเป็นคำถามเปิดที่ต้องยืนยันก่อนเริ่มพัฒนาจริง
- **โมเดล/เทคนิค AI ที่ใช้จริง** สำหรับทั้งงานจับคู่ CLO/PLO และงานวิเคราะห์ gap (เช่น จะใช้ text embedding + similarity scoring หรือเรียกบริการภายนอก) — เอกสารนี้อธิบายเฉพาะ input/output/สถานะ (contract) ของกลไก AI ไม่ผูกกับเทคนิคใดเทคนิคหนึ่ง เช่นเดียวกับแนวทางใน `align-technical-design.md` §4
- **รูปแบบ deployment/hosting** ของทุก component (on-premise, cloud เดียว/หลาย region ฯลฯ) — ไม่อยู่ในขอบเขตของเอกสาร conceptual นี้เลย
- **กลไก authentication ที่แท้จริง** (เช่น รูปแบบ session/token) — เอกสารนี้พูดถึงเฉพาะ "ประตูควบคุมสิทธิ์" ในเชิงหน้าที่ (ต้องตรวจ role + สถานะบัญชีทุกคำร้อง) ไม่ระบุกลไกยืนยันตัวตนที่เป็นรูปธรรม
