
# Tech Stack (Concrete): ระบบติดตามความสอดคล้อง CLO/PLO (ALIGN)

เอกสารนี้เป็น**ชั้นที่เจาะจง (concrete)** — คนละชั้นกับเอกสาร conceptual 3 ฉบับ ([[align-high-level-architecture|align-high-level-architecture]], [[align-api-schema-design|align-api-schema-design]], [[align-technical-design|align-technical-design]]) ที่ตั้งใจไม่ผูกกับ stack ใดๆ — งานของเอกสารนี้คือ**เลือก stack จริง**พร้อมเหตุผลรองรับ โดยอ้างอิงผลสัมภาษณ์ทีมพัฒนา/ผู้เกี่ยวข้องจริง (บันทึกไว้ในหัวข้อ 1) ไม่ใช่ข้อเสนอลอยๆ

ต่อยอดจาก: [[align-high-level-architecture|align-high-level-architecture]] (logical component ที่ต้อง map กับเทคโนโลยีจริง) · [[align-api-schema-design|align-api-schema-design]] (ER diagram/schema ที่ต้องเลือก database engine รองรับ) · [[align-technical-design|align-technical-design]] §5 (ข้อเสนอ stack แบบคร่าวๆ เดิม ที่ยังไม่ผ่านการสัมภาษณ์จริง — ดูหัวข้อ 5 ด้านล่างว่าเอกสารนี้ต่างจาก §5 เดิมตรงไหนและทำไม) · [[../../01-requirements/01-spec/requirement-align|requirement-align]]

> **สถานะ (รอบที่ 1 — 2026-08-23)**: รอบสัมภาษณ์ครั้งแรก คำตอบครบทั้ง 7 มิติ (9 คำถามย่อย) — บางมิติผู้ใช้ตอบว่า "ยังไม่ทราบ/ตัดสินใจทีหลัง" (งบประมาณ, data residency, สถานะ SSO, ที่เก็บไฟล์หลักฐาน, deployment สุดท้าย) จึงแนะนำทางเลือกที่ **portable/reversible** สำหรับมิติเหล่านั้นแทนการฟันธง พร้อมระบุจุดที่ต้องกลับมายืนยันซ้ำไว้ชัดเจนในหัวข้อ 4
>
> **สถานะ (รอบที่ 2 — 2026-09-05, อัปเดตล่าสุด)**: ผู้ใช้ยืนยันข้อจำกัดใหม่ที่**บังคับ**ต้องใช้ **Firebase/Firestore** (ข้อกำหนดของวิชา/อาจารย์ผู้สอน — ไม่ใช่ความชอบที่เปลี่ยนใจได้) ซึ่งขัดกับคำแนะนำเดิมของรอบที่ 1 ที่ปฏิเสธ Firebase ไว้โดยเจตนา (ดูหัวข้อ 2.2/2.3 เดิม) เพราะตอนนั้นยังไม่รู้ข้อจำกัดนี้ — เอกสารนี้จึงปรับคำแนะนำทุกชั้นที่เกี่ยวข้อง (database, backend/API, auth, evidence storage, hosting, AI/LLM) ให้สอดคล้องกับ Firebase เป็นแกนหลัก โดย**คงคำอธิบายเดิมที่เคยปฏิเสธ Firebase ไว้ทุกจุด (ไม่ลบทิ้ง)** แล้วเพิ่มคำอธิบายชัดเจนว่าทำไมตอนนี้ยอมรับ trade-off นั้นแทน — **ย้ำว่านี่คือการยอมรับข้อกำหนดบังคับ ไม่ใช่เพราะเหตุผลทางเทคนิคที่ดีกว่าเดิม** เหตุผลทางเทคนิคเดิมที่เคยใช้ปฏิเสธ Firebase (โมเดลข้อมูลเชิงสัมพันธ์ที่เข้มงวด, ไม่ portable/self-host ไม่ได้) **ยังเป็นจริงอยู่ทั้งหมด** เพียงแต่ตอนนี้มีข้อกำหนดที่สำคัญกว่ามาบังคับแทน
>
> **ยังมีคำถามค้างที่ต้องสัมภาษณ์ผู้ใช้เพิ่มก่อนถือว่าการปรับรอบนี้เสร็จสมบูรณ์** (เครื่องมือ `AskUserQuestion` ไม่พร้อมใช้งานในบริบทนี้ — ดูคำถามเต็มพร้อม 3 ตัวเลือก+ข้อดีข้อเสียในหัวข้อ 4.1 ด้านล่าง และในรายงานสรุปที่ส่งกลับไปยังผู้เรียกงาน): (1) ขอบเขตที่แท้จริงของข้อกำหนด (เฉพาะ Firestore เป็น database หรือทั้ง Firebase suite รวม Auth/Storage/Hosting), (2) เงื่อนไข portable/self-host ที่เคยต้องการยังจำเป็นอยู่ไหมสำหรับส่วนที่ไม่ถูกบังคับโดยตรง, (3) บริบทการใช้งานจริง (งานส่งวิชา/ต้นแบบวิชาการที่ใช้ข้อมูลจำลอง vs ตั้งใจ deploy ใช้งานจริงกับข้อมูลนักศึกษาจริง — กระทบความเข้มงวดของ PDPA/data residency ตามกฎ #5), (4) งบ/data residency/SSO/deployment ที่เคยตอบ "ยังไม่ทราบ" มีอะไรเปลี่ยนไปหรือไม่ — ระหว่างรอคำตอบ เอกสารนี้ใช้ **ค่า default ที่ระบุไว้ชัดเจนพร้อมเหตุผล** ในแต่ละหัวข้อ ตามแนวทางเดียวกับที่ใช้มาตั้งแต่รอบสัมภาษณ์แรก (ห้ามถือเป็นการตัดสินใจสุดท้าย)
>
> **สถานะ (รอบที่ 3 — 2026-09-05, ปิดคำถามค้างจากรอบที่ 2)**: ผู้ใช้ยืนยันคำตอบครบทั้ง 4 คำถามที่ค้างไว้ในหัวข้อ 4.1 แล้ว — สรุปสั้น (รายละเอียดเต็มพร้อมตัวเลือกที่ไม่ได้เลือกดูในหัวข้อ 4.1 ที่ทำเครื่องหมาย "[ยืนยันแล้ว 2026-09-05]" ทุกข้อ): **(1)** ขอบเขตข้อกำหนดบังคับ = **ทั้ง Firebase suite** (Firestore + Firebase Authentication + Cloud Storage + Firebase Hosting ครบทุกส่วน) ไม่ใช่แค่ Firestore อย่างเดียวแล้วผสมกับ Vercel/Supabase Auth ที่เคยเป็น default ระหว่างรอคำตอบ; **(2)** เงื่อนไข portable/self-host ที่เคยพยายามรักษาไว้ = **ไม่จำเป็นอีกต่อไป** ยอมรับ full Firebase lock-in ทุกชั้น (ไม่ใช่แค่ชั้น database) เป็นผลตามมาที่ยอมรับได้ เพราะเลือกใช้ทั้ง suite ไปแล้วตามข้อ (1); **(3)** บริบทโปรเจกต์ = **ไม่ deploy ใช้งานจริงกับข้อมูลนักศึกษาจริง** ในรอบนี้ ใช้งานเฉพาะอาจารย์ผู้สอน — ความเข้มงวดของ PDPA/data residency (กฎทางธุรกิจ #5) ยังคงถูกออกแบบไว้ในสเปคเหมือนเดิมทุกจุด เพียงแต่ไม่ใช่ conflict เชิง legal ที่ต้องแก้เร่งด่วนในตอนนี้; **(4)** งบ/data residency/SSO/deployment สุดท้าย = **ไม่เปลี่ยนจากที่เคยตอบไว้เดิม** ("ยังไม่ทราบ"/"ตัดสินใจทีหลัง" ทุกข้อเหมือนรอบที่ 1) — เอกสารนี้จึงปรับทุกจุดที่เคยเขียนแบบมีเงื่อนไข ("ถ้าคำตอบคำถามที่ 1 ออกมาว่าเฉพาะ Firestore...") ให้กลายเป็นข้อสรุปที่ปิดแล้วตลอดทั้งฉบับ (ดูหัวข้อ 2.2/2.5/2.6/2.7 และตารางหัวข้อ 4 ที่ปรับตามแล้ว) — **ประเด็นที่ยังเปิดค้างอยู่จริง** (งบประมาณ/บัญชี billing, data residency ทาง legal, สถานะ SSO, deployment สุดท้าย) **ไม่ได้ถูกปิดในรอบนี้** ยังคงเป็น default ที่ต้องกลับมายืนยันซ้ำเหมือนเดิม (ดูหัวข้อ 4)
>
> **หมายเหตุสำคัญเรื่องบริบทการใช้งาน (ยืนยันแล้ว 2026-09-05)**: การใช้งานจริงของโปรเจกต์นี้ ณ ตอนนี้คือ**เฉพาะอาจารย์ผู้สอนเท่านั้น ไม่ใช่ production deployment ที่มีข้อมูลนักศึกษาจริงหมุนเวียนอยู่** — ข้อนี้ลดความเร่งด่วนเชิง legal ของประเด็น data residency/PDPA ที่ยังค้างอยู่ (งบ/data residency ตัวจริงยังไม่ทราบตามข้อ 4 ด้านบน) **แต่ไม่ใช่ข้ออ้างให้ลดทอนการออกแบบ schema/สิทธิ์การเข้าถึงตามกฎทางธุรกิจ #5 (PDPA)** — ทุกจุดที่เกี่ยวกับสิทธิ์การเข้าถึงไฟล์หลักฐาน/ข้อมูลนักศึกษาในเอกสารนี้ (หัวข้อ 2.2, 2.5, 2.7, หัวข้อ 3) ยังคงต้องออกแบบให้ถูกต้องครบถ้วนเหมือนกับว่าจะ deploy จริง เผื่ออนาคตขยายเป็น production ใช้งานจริงกับข้อมูลนักศึกษาจริง

### รอบที่ 2 (2026-09-05): ข้อจำกัดใหม่ — บังคับใช้ Firebase/Firestore

| # | มิติ | คำตอบที่ได้ |
|---|---|---|
| 1.4 | ข้อกำหนดเทคโนโลยีบังคับ (ใหม่) | **ต้องใช้ Firebase/Firestore** — เป็นข้อกำหนดบังคับของวิชา/อาจารย์ผู้สอน (เช่น ข้อกำหนดการบ้าน/เกณฑ์การให้คะแนนที่ระบุเทคโนโลยีไว้) **ไม่ใช่ความชอบของทีมที่เปลี่ยนใจได้** — จึงมีน้ำหนักเหนือกว่าเกณฑ์ทางเทคนิคอื่นๆ ที่เคยใช้ตัดสินใจในรอบที่ 1 |
| 1.5 | ขอบเขตที่แท้จริงของข้อกำหนด (เฉพาะ Firestore database หรือทั้ง Firebase suite) | *(ปิดแล้ว — ดูตารางรอบที่ 3 ด้านล่าง)* เดิม: **ยังไม่ยืนยัน** — ต้องถามผู้ใช้เพิ่ม (ดูหัวข้อ 4.1 คำถามที่ 1) — เอกสารนี้ใช้ default: **ทั้ง Firebase suite** (Firestore + Firebase Auth + Firebase Storage + Firebase App Hosting) เพื่อความสอดคล้องของสถาปัตยกรรมเดียว (ตรงกับหลักการ "1 deployable unit" ของรอบที่ 1) จนกว่าจะยืนยันว่าขอบเขตแคบกว่านี้ (เช่น บังคับเฉพาะ Firestore) — **[ยืนยันแล้ว 2026-09-05]: ทั้ง Firebase suite ตามที่ default ไว้ ไม่ใช่ขอบเขตแคบกว่า** |
| 1.6 | เงื่อนไข portable/self-host ที่เคยต้องการ (รอบที่ 1) ยังจำเป็นอยู่ไหม | *(ปิดแล้ว — ดูตารางรอบที่ 3 ด้านล่าง)* เดิม: **ยังไม่ยืนยันสำหรับชั้นอื่น** — แต่สำหรับชั้น **Database (Firestore)** เงื่อนไขนี้**ผ่อนคลายลงแล้วโดยปริยาย**เพราะ Firestore ไม่มีทาง self-host ได้ไม่ว่ากรณีใด (นี่คือ trade-off ที่ยอมรับเพราะข้อกำหนดบังคับ ข้อ 1.4 — ไม่ใช่เพราะทีมเปลี่ยนใจว่า portability ไม่สำคัญอีกต่อไป) ส่วนชั้น Storage/Hosting/Auth ยังต้องถามว่าจะพยายามรักษาความ portable ไว้แค่ไหน (ดูหัวข้อ 4.1 คำถามที่ 2) — **[ยืนยันแล้ว 2026-09-05]: ไม่จำเป็นแล้วสำหรับทุกชั้น ยอมรับ full lock-in ทั้งหมด** |
| 1.7 | บริบทการใช้งานจริง (งานส่งวิชา/ต้นแบบวิชาการ vs deploy ใช้จริงกับข้อมูลนักศึกษาจริง) | *(ปิดแล้ว — ดูตารางรอบที่ 3 ด้านล่าง)* เดิม: **ยังไม่ยืนยัน** — กระทบความเข้มงวดของ PDPA/data residency (กฎทางธุรกิจ #5) ว่าต้องบังคับใช้จริงระดับใด (ดูหัวข้อ 4.1 คำถามที่ 3) — **[ยืนยันแล้ว 2026-09-05]: ไม่ deploy จริงกับข้อมูลนักศึกษาจริง เฉพาะอาจารย์ผู้สอน — กฎ PDPA #5 ยังคงออกแบบไว้เต็มรูปแบบเหมือนเดิม** |
| 2.1 (ทบทวน) งบประมาณ | **ยังไม่ยืนยันว่าเปลี่ยนไปหรือไม่จากคำตอบเดิม "ยังไม่ทราบ"** — แต่พบข้อมูลใหม่ที่ต้องแจ้ง: Firebase มี free tier (Spark) และ pay-as-you-go (Blaze) — Firebase App Hosting และการเรียก API ภายนอก (เช่น external LLM API แบบ feature-flag) **ต้องใช้ Blaze เท่านั้น** ซึ่งต้องผูกบัตร/บัญชี billing ไว้ล่วงหน้า (ดูหัวข้อ 2.6) |
| 2.2 (ทบทวน) Data residency | **ยังไม่ยืนยันว่าเปลี่ยนไปหรือไม่** — Firebase/Firestore ไม่มี region ในประเทศไทย ใกล้ที่สุดคือ `asia-southeast1` (สิงคโปร์)/`asia-southeast2` (จาการ์ตา) ซึ่งเป็นข้อจำกัดคล้ายเดิมกับที่เคยประเมิน Supabase ไว้ (ไม่ได้แย่ลง แต่ก็ไม่ได้ดีขึ้น) |
| 5 (ทบทวน) SSO | **ยังไม่ยืนยันว่าเปลี่ยนไปหรือไม่** — Firebase Authentication รองรับ OAuth2/OIDC ได้ในตัวฟรี แต่ SAML ต้องอัปเกรดเป็น Google Cloud Identity Platform (เสียเงิน) — ข้อจำกัดคล้ายเดิมกับ Supabase Pro/Enterprise ที่เคยระบุไว้ |

**ตัวแปรหลักที่กำหนดทิศทางคำแนะนำที่เปลี่ยนไปในรอบที่ 2**: ข้อกำหนดบังคับ Firebase/Firestore (ข้อ 1.4) เป็น**ข้อจำกัดที่อยู่นอกเหนือการชั่งน้ำหนักทางเทคนิคล้วนๆ** — ทำให้คำแนะนำ database (หัวข้อ 2.3) เปลี่ยนจาก PostgreSQL/Supabase เป็น Cloud Firestore โดยตรง และส่งผลกระทบต่อเนื่องไปยัง Auth/Storage/Hosting/Backend (หัวข้อ 2.2/2.5/2.6/2.7) เพื่อความสอดคล้องของสถาปัตยกรรมเดียวตามหลักการเดิม (ทีมเล็ก/ผู้ดูแลไม่ใช่โปรแกรมเมอร์มืออาชีพ) — **เงื่อนไข "portable/ย้ายได้" ของรอบที่ 1 (ข้อ ง) เสียไปอย่างถาวรสำหรับชั้น database** เพราะเป็น trade-off ที่ยอมรับแล้ว แต่ยังพยายามรักษาความ portable ไว้ให้มากที่สุดเท่าที่ทำได้ในชั้นอื่นที่ยังไม่ถูกบังคับตรงๆ จนกว่าจะได้คำตอบคำถามที่ยังค้าง (หัวข้อ 4.1)

### รอบที่ 3 (2026-09-05): ปิดคำถามค้างจากรอบที่ 2 — ยืนยันทั้ง Firebase suite เป็นข้อบังคับ

|---|---|---|
| 1.5 (ปิด) | ขอบเขตที่แท้จริงของข้อกำหนดบังคับ | **[ยืนยันแล้ว] ทั้ง Firebase suite** — ต้องใช้ Firebase Authentication, Cloud Firestore, Cloud Storage, และ Firebase Hosting ครบทุกส่วน (ไม่ใช่แค่ Firestore อย่างเดียวแล้วคง Vercel/Supabase Auth ไว้เหมือนที่เคยเป็น default ระหว่างรอคำตอบ) |

| 2.1/2.2/5/7 (ยังเปิดอยู่) | งบ/data residency/SSO/deployment สุดท้าย | **[ยืนยันแล้วว่า] ไม่เปลี่ยนจากที่เคยตอบไว้เดิม** — ยังไม่ทราบ/ตัดสินใจทีหลังเหมือนเดิมทุกข้อ (ไม่ใช่ข้อที่ปิดในรอบนี้ ยังคงเป็น default portable-as-far-as-possible ในหัวข้อ 4 เหมือนเดิม เพียงแต่ตอนนี้ "portable" เหลือความหมายแค่ระดับ "ยังไม่ผูก billing/region สุดท้าย" ไม่ใช่ "ยังเลือก provider อื่นได้" อีกต่อไป เพราะข้อ 1.5/1.6 ปิดแล้ว) |

**ผลของการปิดคำถามรอบที่ 3**: ทุกจุดในเอกสารนี้ที่เคยเขียนแบบมีเงื่อนไข ("ถ้าคำตอบคำถามที่ 1 ในหัวข้อ 4.1 ออกมาว่าบังคับเฉพาะ Firestore เท่านั้น ก็ยังสามารถ...") **ปิดแล้วและไม่ใช่ทางเลือกที่เปิดอยู่อีกต่อไป** — ปรับเป็นข้อสรุปเดียวคือ Firebase ทั้ง suite ตลอดทั้งฉบับ (ดูหัวข้อ 2.2/2.5/2.6/2.7 และตารางหัวข้อ 4 ที่ปรับตามแล้ว) — ประเด็นที่ยังเปิดค้างจริง (งบประมาณ/บัญชี billing, data residency ทาง legal, สถานะ SSO, deployment สุดท้าย) ไม่ได้รับผลกระทบจากการปิดรอบนี้ ยังคงต้องกลับมายืนยันซ้ำเหมือนเดิม

### 2.1 Frontend — Next.js (React) + Tailwind CSS

**เหตุผล**: ทีมตอบข้อ 1.2 ว่า "ไม่ถนัดภาษาใดเป็นพิเศษ ต้องการ stack ที่เรียนรู้ง่ายที่สุด" — React/Next.js เป็นระบบนิเวศที่มี tutorial/เอกสารภาษาไทยและอังกฤษมากที่สุดในบรรดา frontend framework ปัจจุบัน และมี **starter template อย่างเป็นทางการที่ผูกกับ Supabase โดยตรง** (`create-next-app --example with-supabase`) ซึ่งตัดงาน setup auth/DB client ไปได้เกือบทั้งหมด — สำคัญมากเมื่อเดดไลน์เหลือ ~2 เดือน (ข้อ 3) และไม่มีใครในทีมมีพื้นฐานเดิม (ข้อ 1.1/1.2) การเลือก ecosystem ที่มี "ทางลัดสำเร็จรูป" ตรงกับ stack ที่เลือกทั้งชุดจึงลดความเสี่ยงด้าน timeline ได้มากกว่าการเลือกภาษาที่ไม่มีใครถนัดแล้วยังต้องต่อกับ backend เองทั้งหมด
- ส่วนติดต่อผู้ใช้ต้องรองรับการโต้ตอบเชิงลึก (แก้ไขผล AI ก่อนยืนยัน, ตารางแผนที่ CLO×สัปดาห์ — ตาม [[align-high-level-architecture|align-high-level-architecture]] §2) ซึ่งเหมาะกับ SPA/React มากกว่า server-rendered แบบเดิม (ตรงกับที่ `align-technical-design.md` §5 เดิมก็เสนอ SPA อยู่แล้ว)
- Tailwind CSS ถูกเลือกเพราะเรียนรู้เร็ว (utility class ไม่ต้องเขียน CSS แยกไฟล์เยอะ) และนำ design token จาก `DESIGN.md` มา configure เป็นตัวแปรได้ตรงไปตรงมา (การนำ token จริงไปใช้เป็นงานของ prototype-designer/DESIGN.md ไม่ใช่ขอบเขตเอกสารนี้ แต่ framework นี้ไม่ปิดกั้นการทำตาม token)

> **อัปเดตรอบที่ 2 (2026-09-05)**: เลือก Next.js/Tailwind CSS ยังคง**ไม่เปลี่ยนแปลง**จากข้อกำหนดบังคับ Firebase (ข้อ 1.4) — Firebase ไม่ได้บังคับ frontend framework ใดเป็นการเฉพาะ สิ่งที่เปลี่ยนคือ**ที่ deploy** (ดูหัวข้อ 2.6) ไม่ใช่ตัว framework เอง

**ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก**:
- **React SPA (Vite) + backend แยกต่างหาก** — ปฏิเสธ เพราะต้องดูแล 2 โปรเจกต์/2 deployment แยกกัน เพิ่มภาระ DevOps ที่ทีม 1–2 คนและอาจารย์ผู้ดูแลต่อ (ไม่ใช่โปรแกรมเมอร์มืออาชีพ) รับไม่ไหวในระยะยาว ขณะที่ Next.js รวม frontend+API ไว้ใน deploy เดียว
- **Vue.js/Nuxt** — ความยากง่ายใกล้เคียงกัน แต่จำนวน starter template ที่ผูกกับ Supabase สำเร็จรูปน้อยกว่า Next.js อย่างชัดเจน เมื่อทีมไม่มีความถนัดเดิมเป็นตัวตัดสิน (ข้อ 1.2) การเลือก ecosystem ที่มีทางลัดตรงกับ stack ทั้งชุดมากที่สุดจึงคุ้มกว่าเมื่อเดดไลน์บีบ (ข้อ 3)
- **Server-rendered framework แบบดั้งเดิม (Laravel Blade/Django templates)** — ปฏิเสธ เพราะไม่เหมาะกับหน้าจอเชิงโต้ตอบสูงตามที่ [[align-high-level-architecture|align-high-level-architecture]] ระบุไว้ (AI Review Panel ที่ต้องแก้ไข/ยืนยันทีละรายการแบบไม่ reload หน้า)

### 2.2 Backend / API layer — Next.js API Routes / Server Actions (ในโปรเจกต์เดียวกับ frontend) เรียก Firestore ผ่าน Firebase Admin SDK

**เหตุผล**: ทีมเล็ก (ข้อ 1.1) + เดดไลน์ ~2 เดือน (ข้อ 3) — การรวม backend logic ไว้ในโปรเจกต์ Next.js เดียวกัน (แทนการตั้งเซิร์ฟเวอร์ backend แยก) ลดจำนวนสิ่งที่ต้อง deploy/monitor เหลือ "1 แอปพลิเคชัน" ซึ่งตรงกับผู้ดูแลระยะยาวเป็นอาจารย์ที่ไม่ใช่โปรแกรมเมอร์มืออาชีพ (ข้อ 1.3) — Server Action/API Route ทำหน้าที่เป็น **"ประตูควบคุมสิทธิ์" + "แกนประสานงาน"** ตามที่ [[align-high-level-architecture|align-high-level-architecture]] กำหนดไว้ (ตรวจ `account_status=approved`, ตรวจ role, บังคับกฎ #1 "ผูก CLO–PLO ก่อนบันทึกการสอน" **ที่ฝั่งเซิร์ฟเวอร์เสมอ** ไม่พึ่ง UI disable ปุ่มเพียงอย่างเดียว)
- **ใช้ Firestore Security Rules เป็น defense-in-depth ชั้นที่สอง** (กันกรณีมี bug ในโค้ด server) แทนที่ PostgreSQL RLS เดิม — เหตุผลเดียวกับรอบที่ 1: กฎทางธุรกิจที่ซับซ้อน (draft→confirmed workflow กฎ #3, curriculum-scope isolation cross-cutting) เขียนเป็น security rule ล้วนๆ ยากต่อการดูแลของทีมที่ไม่ชำนาญ ยิ่งกว่านั้น Firestore Security Rules มีข้อจำกัดเพิ่มเติมที่ RLS ของ Postgres ไม่มี (เช่น query ข้าม collection เพื่อตรวจ curriculum scope ทำได้จำกัดกว่า SQL join) — จึงยังคงยึดหลักเดิมว่า**การบังคับใช้กฎหลักอยู่ที่โค้ด server (Next.js Server Action/API Route)** ไม่ใช่ security rules

> **อัปเดตรอบที่ 2 (2026-09-05)**: การเปลี่ยนจาก Supabase Postgres client → **Firebase Admin SDK** เป็นผลจากข้อกำหนดบังคับ Firebase/Firestore (ข้อ 1.4) เท่านั้น ไม่ใช่การเปลี่ยนใจทางเทคนิค — ต้องพิจารณาเพิ่มเติมว่าจะ deploy Next.js บน Firebase ด้วยแนวทางใด มี 2 ทางเลือกหลัก:
> 1. **Firebase App Hosting (แนะนำ)** — บริการของ Firebase ที่รองรับ Next.js SSR แบบเต็มรูปแบบ (framework-aware รวม Server Actions/API Routes) รันบน Cloud Run เบื้องหลัง ผูกกับ Firebase project เดียวกับ Firestore/Auth/Storage โดยตรง — ใกล้เคียงประสบการณ์ "deploy คำสั่งเดียว" แบบ Vercel เดิมมากที่สุด ตรงกับเหตุผลเดิมที่ต้องการลดสิ่งที่ทีมเล็ก/ผู้ดูแลไม่ใช่โปรแกรมเมอร์มืออาชีพต้องดูแล (ข้อ 1.1/1.3) — **ข้อควรระวัง**: เป็นบริการค่อนข้างใหม่ (เทียบกับ App Router/Server Actions ของ Next.js เอง) ควรตรวจสอบ compatibility ล่าสุดกับเวอร์ชัน Next.js ที่จะใช้จริงก่อนเริ่มพัฒนา ไม่ควรถือว่าเอกสารนี้ยืนยัน compatibility 100%
> 2. **Cloud Functions for Firebase (2nd gen) + Firebase Hosting rewrites** — แนวทางดั้งเดิมก่อนมี App Hosting ที่ต้องแปลง Next.js ให้ export เป็น Cloud Function เอง (ผ่าน community tooling อย่าง `firebase-frameworks`) — ซับซ้อนกว่า ต้องดูแล config เพิ่ม (memory allocation ต่อ function, cold start ต่อ region) และมีประวัติปัญหา compatibility กับ Server Actions มากกว่า App Hosting ที่ Google ดูแลเอง (ดูผลกระทบต่อ AI/LLM ในหัวข้อ 2.4 ด้วย)
>
> **แนะนำ Firebase App Hosting เป็น default — [ยืนยันแล้ว 2026-09-05]** ผู้ใช้ยืนยันแล้วว่าขอบเขตข้อกำหนดบังคับครอบคลุม**ทั้ง Firebase suite รวม Hosting ด้วย** (หัวข้อ 4.1 คำถามที่ 1 — เลือกตัวเลือก B) — ทางเลือกที่เคยเสนอไว้ก่อนหน้านี้ว่า "ถ้าบังคับเฉพาะ Firestore database เท่านั้น ก็ยังคง Vercel เดิมเป็น hosting ได้" **ปิดแล้ว ไม่ใช่ทางเลือกที่เปิดอยู่อีกต่อไป** (เก็บข้อความเดิมไว้ด้านล่างเพื่อ traceability ว่าเคยพิจารณาทางนี้ตอนที่ยังไม่มีคำตอบ) — สิ่งที่ยังต้องตัดสินใจต่อคือ**เลือกระหว่าง 2 ทางเลือกด้านบน (App Hosting vs Cloud Functions 2nd gen)** ซึ่งเป็นรายละเอียดการ deploy ภายในระบบนิเวศ Firebase เท่านั้น ไม่ใช่คำถามเรื่อง provider อีกต่อไป — App Hosting ยังคงเป็น default ที่แนะนำด้วยเหตุผลเดิม (ใกล้เคียงประสบการณ์ deploy คำสั่งเดียวแบบ Vercel มากที่สุด ตรงกับข้อ 1.1/1.3)
>
> *(ข้อความเดิมก่อนยืนยัน — เก็บไว้เพื่อ traceability)*: เดิมยังไม่ยืนยันกับผู้ใช้ว่า "ข้อกำหนดบังคับ Firebase" ครอบคลุมส่วนนี้ด้วยหรือไม่ (App Hosting ใช้ Cloud Run ของ Google Cloud เบื้องหลัง ซึ่งเป็นคนละผลิตภัณฑ์กับ "Firebase" อย่างเป็นทางการในบางบริบท) — ถ้าคำตอบออกมาว่า **บังคับเฉพาะ Firestore database เท่านั้น** ก็ยังสามารถคง **Vercel เดิมเป็น hosting** และเรียก Firestore ผ่าน Firebase Admin SDK จาก Vercel ได้ตามปกติ (Firestore เป็น API ภายนอกที่เรียกจากที่ไหนก็ได้ ไม่ผูกกับ hosting เดียวกัน) — เป็นทางเลือกที่เคยรักษา portability ของชั้น hosting ไว้ได้มากกว่า แม้ database จะผูกกับ Firebase แล้วก็ตาม — **ทางเลือกนี้ปิดแล้วตามคำตอบยืนยันด้านบน**

**ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก**:
- **Backend แยก (Express/Django/Laravel/Spring)** — ปฏิเสธ เพราะเพิ่มโปรเจกต์/deployment ที่ต้องดูแลแยก ขัดกับข้อจำกัดผู้ดูแลระยะยาวที่ไม่ใช่โปรแกรมเมอร์มืออาชีพ (ข้อ 1.3) และใช้เวลา setup มากกว่าภายในกรอบ ~2 เดือน (ข้อ 3)
- **Firebase (Google BaaS) แทน Supabase** *(เดิมปฏิเสธในรอบที่ 1 — อัปเดตรอบที่ 2: กลับมายอมรับแล้ว)* — รอบที่ 1 เคยปฏิเสธด้วย 2 เหตุผล: (ก) Firestore เป็น NoSQL document store ไม่เหมาะกับโมเดลข้อมูลเชิงสัมพันธ์ที่เข้มงวดใน [[align-api-schema-design|align-api-schema-design]] (FK, unique constraint ภายใน curriculum เดียวกัน, ห้าม query ข้าม curriculum) ซึ่งต้องพึ่ง relational DB จริง (ข) Firebase เป็น proprietary ล้วน ไม่มีทาง self-host — ขัดกับความต้องการ "portable" ที่จำเป็นเพราะคำตอบเรื่องงบ/data residency (ข้อ 2.1/2.2) ยังไม่ทราบ ณ ตอนนั้น — **ทั้ง 2 เหตุผลนี้ยังเป็นจริงอยู่ทั้งหมดในเชิงเทคนิค** แต่ตอนนี้ผู้ใช้ยืนยันข้อกำหนดบังคับ (ข้อ 1.4) ที่มีน้ำหนักเหนือกว่าการชั่งน้ำหนักทางเทคนิคเดิม จึงเปลี่ยนมาใช้ Firebase/Firestore โดยยอมรับผลกระทบทั้งสองข้อเป็น trade-off ที่จำเป็น (รายละเอียดผลกระทบต่อโมเดลข้อมูลอยู่ในหัวข้อ 2.3)
- **ให้ Firestore Security Rules เป็นกลไกบังคับใช้กฎธุรกิจทั้งหมดโดยไม่มีชั้น server code** — ปฏิเสธตามเหตุผลข้างต้น (ความซับซ้อนของกฎ #1/#3 เกินกว่าที่ทีมขนาดนี้จะดูแล security rules ล้วนๆ ได้อย่างปลอดภัยในระยะยาว ยิ่งกว่านั้น Firestore rules มีข้อจำกัดด้าน cross-collection query มากกว่า SQL RLS ที่เคยประเมินไว้)

### 2.3 Database — Cloud Firestore (เปลี่ยนจาก PostgreSQL/Supabase — บังคับตามข้อกำหนดวิชา ข้อ 1.4)

> **อัปเดตรอบที่ 2 (2026-09-05)**: คำแนะนำเดิมของหัวข้อนี้ (รอบที่ 1) คือ PostgreSQL ผ่าน Supabase — เอกสารนี้เปลี่ยนคำแนะนำเป็น **Cloud Firestore** โดยตรงตามข้อกำหนดบังคับที่ผู้ใช้ยืนยัน (ข้อ 1.4) **นี่ไม่ใช่การเปลี่ยนใจเพราะเหตุผลทางเทคนิคที่ดีกว่าเดิม — เหตุผลทางเทคนิคเดิมที่เลือก PostgreSQL ยังคงเป็นจริงอยู่ทั้งหมด (ดูด้านล่าง) แต่มีข้อกำหนดที่อยู่นอกเหนือการชั่งน้ำหนักทางเทคนิคมาบังคับแทน**

**เหตุผลเดิม (รอบที่ 1) ที่เคยเลือก PostgreSQL/Supabase — ยังคงเป็นจริง**: โมเดลข้อมูลใน [[align-api-schema-design|align-api-schema-design]] เป็นเชิงสัมพันธ์ชัดเจน (curriculum → PLO/CLO → mapping → course → teaching_record) มี constraint ที่ต้องบังคับผ่าน FK/unique/check (เช่น ห้าม `clo_plo_mapping` ข้าม curriculum) — PostgreSQL รองรับ constraint เหล่านี้ได้ตรงจุดที่สุด

**ผลกระทบสำคัญที่ต้องยอมรับจากการเปลี่ยนมาใช้ Firestore (trade-off)**:
1. **โมเดลข้อมูลทั้งหมดใน [[align-api-schema-design|align-api-schema-design]] ต้องถูกออกแบบใหม่** — ER diagram/FK/unique constraint/partial unique index เชิงสัมพันธ์ที่มีอยู่ **ไม่มีกลไกเทียบเท่าใน Firestore** (ไม่มี FK, ไม่มี join ระดับ database engine, ไม่มี unique constraint ข้าม document โดยตรง) ต้องออกแบบใหม่เป็นรูปแบบ NoSQL:
   - **Denormalization** — เก็บข้อมูลซ้ำที่จำเป็นต่อการ query ไว้ในแต่ละ document โดยตรง (เช่น ฝัง `curriculum_id` ซ้ำในทุก document ที่เกี่ยวข้อง แทนการ join ผ่าน FK เหมือน Postgres)
   - **Subcollection** แทนตารางลูกที่เคยผูกด้วย FK (เช่น `curriculum/{id}/plo/{id}/clo_mapping/{id}`)
   - **Firestore Security Rules** เขียนกฎเฉพาะของ Firestore แทน PostgreSQL RLS — แต่ยังแนะนำให้บังคับกฎทางธุรกิจหลัก (#1, #3, #5) ที่ชั้น server (Next.js Server Action) เป็นหลักเหมือนเดิม ตามเหตุผลในหัวข้อ 2.2
   - **Unique constraint ข้าม curriculum ที่เคยบังคับด้วย partial unique index ใน Postgres** (เช่นที่เพิ่งใช้กับ `notification` — ดู [[../../05-log/2026-09-05-notification-account-approval-log|log 2026-09-05]]) **ไม่มีกลไกเทียบเท่าใน Firestore โดยตรง** ต้อง enforce ด้วย transaction ฝั่งเซิร์ฟเวอร์เอง (อ่าน-ตรวจ-เขียนในธุรกรรมเดียว ผ่าน Firestore transaction API) ซึ่งเพิ่มความซับซ้อนของโค้ดที่ทีมเล็ก (ข้อ 1.1) ต้องเขียน/ดูแลเอง — เป็น**ความเสี่ยงที่ต้องยอมรับ ไม่ใช่ประโยชน์**
2. **งานออกแบบใหม่นี้อยู่นอกขอบเขตของเอกสารนี้** — ต้องส่งต่อให้ `api-schema-designer` ออกแบบ Firestore data model ใหม่ทั้งหมด (denormalization strategy, subcollection structure, security rules) แทน ER diagram เชิงสัมพันธ์เดิม และส่งต่อให้ `technical-designer` ปรับ §2 (entity tables)/§3 (API) ให้สอดคล้อง (ดูรายงานสรุปที่ส่งกลับพร้อมเอกสารนี้)
3. **Portability ที่เคยต้องการ (ข้อ 2.1/2.2 รอบที่ 1) เสียไปอย่างถาวรสำหรับชั้นนี้** — Firestore เป็นบริการ proprietary ของ Google ล้วนๆ ไม่มีทาง self-host ต่างจาก Supabase Postgres ที่เคยวางแผน escape hatch ไป self-host ผ่าน Docker Compose ได้ (ดูหัวข้อ 4 เดิม) — **นี่คือ trade-off ที่ยอมรับเพราะข้อกำหนดบังคับสำคัญกว่า** (ข้อ 1.4/1.6) ไม่ใช่เพราะข้อจำกัดเรื่อง data residency (ข้อ 2.2) ผ่อนคลายลง — ข้อ 2.2 ยังตอบว่า "ยังไม่ทราบ" เหมือนเดิม และยังเป็นความเสี่ยงจริงถ้าคำตอบออกมาเข้มงวด (ดูหัวข้อ 4) — **[ยืนยันแล้ว 2026-09-05]**: ผู้ใช้ยืนยันแล้ว (หัวข้อ 4.1 คำถามที่ 2) ว่าเงื่อนไข portable **ไม่จำเป็นอีกต่อไปสำหรับทุกชั้น** ไม่ใช่แค่ชั้น database นี้ — trade-off นี้จึงกลายเป็น**การยอมรับถาวรสำหรับทั้งระบบ** ไม่ใช่แค่ชั้นนี้ชั้นเดียวเหมือนที่เคยประเมินไว้ก่อนหน้านี้

**ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก (อัปเดตรอบที่ 2)**:
- **PostgreSQL ผ่าน Supabase** *(คำแนะนำเดิมของรอบที่ 1)* — ไม่เลือกอีกต่อไป **ไม่ใช่เพราะเหตุผลทางเทคนิคเปลี่ยนไป** (เหตุผลเดิมที่เคยเลือก Postgres ในหัวข้อนี้ยังคงเป็นจริงอยู่ทั้งหมด — โมเดลข้อมูลเชิงสัมพันธ์ยังเหมาะกับ constraint ของระบบนี้มากกว่า Firestore ในเชิงเทคนิคล้วนๆ) แต่เพราะข้อกำหนดบังคับของวิชา/อาจารย์ผู้สอน (ข้อ 1.4) ทำให้ไม่มีทางเลือกอื่นนอกจาก Firestore
- **MySQL** — เหตุผลเดิม (รอบที่ 1) ยังใช้ได้แต่ไม่ใช่ประเด็นหลักอีกต่อไป เพราะไม่ใช่ relational DB ที่ถูกเลือกใช้อยู่แล้ว
- **MongoDB/NoSQL อื่น (self-hosted)** *(พิจารณาเพิ่มในรอบที่ 2)* — ในทางเทคนิคจะช่วยแก้ปัญหาความไม่ portable ของ Firestore ได้ (MongoDB self-host ได้จริง) แต่**ไม่ตรงกับข้อกำหนดที่ระบุเจาะจงว่าต้องเป็น Firebase/Firestore** (ข้อ 1.4) จึงไม่ใช่ทางเลือกที่ตอบโจทย์ข้อกำหนดวิชา แม้จะแก้ปัญหา portability ได้ก็ตาม — ปฏิเสธ

### 2.4 แนวทางเชื่อมต่อ AI/LLM — Hybrid: Transformers.js (in-process) + external API แบบ feature-flag

ผู้ใช้ตอบชัดเจนว่าต้องการ **hybrid** (ข้อ 4) — เอกสารนี้แปลงคำตอบนี้เป็นแนวทางที่ทำได้จริงภายในข้อจำกัดอื่น (ทีมเล็ก, ไม่มี infra AI, เดดไลน์ 2 เดือน, งบ/data residency ยังไม่ทราบ):

**ส่วนหลัก (default, เปิดใช้เสมอ)**: ใช้ `@xenova/transformers` (Transformers.js) รันโมเดล embedding แบบ multilingual open-source (เช่น `Xenova/multilingual-e5-small` หรือรุ่นที่รองรับภาษาไทย) **โดยตรงในโค้ด Next.js/Node** (ไม่ต้องมีเซิร์ฟเวอร์ Python/GPU แยก) เพื่อคำนวณ similarity สำหรับ:
- งานจับคู่การสอนกับ CLO (E3 ส่วน a) — เทียบ embedding ของหัวข้อการสอนกับ embedding ของ CLO แต่ละข้อในกลุ่มหลักสูตรเดียวกัน
- งานวิเคราะห์ gap เทียบ syllabus แบบพื้นฐาน (E3 ส่วน b) — เทียบ embedding หัวข้อที่วางแผนกับหัวข้อที่สอนจริงสะสม

**เหตุผลที่เลือกวิธีนี้เป็นแกนหลัก**: (1) ข้อมูล (หัวข้อการสอน/CLO ซึ่งไม่ใช่ไฟล์หลักฐานดิบที่มี PII) **ไม่ออกนอกระบบเลย** — ปลอดภัยที่สุดเผื่อคำตอบ data residency (ข้อ 2.2) ออกมาเข้มงวด (2) ไม่มีค่าใช้จ่ายต่อการเรียก — ปลอดภัยเผื่องบ (ข้อ 2.1) ไม่มาจริง (3) รันเป็นไลบรารี npm ธรรมดา ไม่ต้องตั้ง GPU/Python service แยก — ทีมเล็ก/ไม่มีโปรแกรมเมอร์มืออาชีพดูแลต่อ (ข้อ 1.1/1.3) ทำได้จริงในกรอบเวลา 2 เดือน (ข้อ 3) ต่างจากการ self-host LLM ขนาดใหญ่ที่ต้องมี infra เฉพาะ

**ส่วนเสริม (optional, ปิดโดย default เป็น feature flag)**: เรียก external LLM API (เช่น OpenAI/Anthropic/Gemini) เฉพาะสำหรับเสริมคุณภาพคำอธิบาย gap analysis (เช่น สรุปเป็นข้อความ "ขาดอะไร/เพิ่มอะไร" ที่อ่านง่ายกว่า similarity score ดิบ) — **เปิดใช้ได้ก็ต่อเมื่อยืนยันงบประมาณ (ข้อ 2.1) และนโยบายข้อมูลออกนอกระบบ (ข้อ 2.2) แล้วเท่านั้น** เพราะเป็นเส้นทางเดียวที่มีข้อมูลออกนอกระบบมหาวิทยาลัยจริง — ส่งเฉพาะข้อความหัวข้อ (ไม่ใช่ไฟล์หลักฐาน/ข้อมูลนักศึกษา) เพื่อลดความเสี่ยง PDPA ให้น้อยที่สุดเท่าที่จะทำได้แม้เปิดใช้จริง

ทุกผลลัพธ์จากทั้งสองเส้นทาง (local หรือ external) ต้องเขียนเป็น state `draft` เสมอ ตามกฎ #3 — สอดคล้องกับ contract ที่ [[align-api-schema-design|align-api-schema-design]] §3.9/3.11 กำหนดไว้แล้ว ไม่เปลี่ยนแปลง

**ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก**:
- **External API เป็นเส้นทางเดียว (ไม่มี local embedding เลย)** — ปฏิเสธ เพราะขัดกับคำตอบ hybrid ที่ผู้ใช้ระบุชัดเจน (ข้อ 4) และมีค่าใช้จ่ายต่อเนื่อง+ความเสี่ยงข้อมูลออกนอกระบบที่ยังไม่มีคำตอบมารองรับ (ข้อ 2.1/2.2)
- **Self-host LLM ขนาดใหญ่บน GPU server เอง (on-prem)** — ปฏิเสธ เพราะต้องมี infra/งบเฉพาะที่ยังไม่ยืนยัน (ข้อ 2.1) และทีม 1–2 คนที่ไม่ถนัดภาษาใดเป็นพิเศษ (ข้อ 1.1/1.2) ไม่มีความเชี่ยวชาญ ML-ops ที่จะดูแลได้ทันเดดไลน์ 2 เดือน (ข้อ 3)

> **อัปเดตรอบที่ 2 (2026-09-05) — ผลกระทบของข้อกำหนดบังคับ Firebase ต่อแนวทางนี้**: แนวทาง hybrid ข้างต้น**ยังคงเป็นคำแนะนำหลัก** (เหตุผลเดิมทุกข้อยังใช้ได้) แต่ต้องทบทวน**ตำแหน่งที่รันโค้ด Transformers.js** ใหม่ เพราะ backend ย้ายจาก Vercel Node runtime ไปเป็น Firebase (ข้อ 1.4, หัวข้อ 2.2):
> - **ถ้า deploy ผ่าน Firebase App Hosting (แนะนำในหัวข้อ 2.2)**: Next.js server action ยังรันเป็น process เดียวกันบน Cloud Run เบื้องหลัง App Hosting — โหลดโมเดล embedding เข้าหน่วยความจำ**ครั้งเดียวต่อ instance** (ไม่ใช่ทุกครั้งที่เรียก) ได้ใกล้เคียงพฤติกรรมเดิมบน Vercel ตราบใดที่ instance ไม่ถูก scale-to-zero บ่อย — **ความเสี่ยง**: ถ้าไม่ตั้งค่า minimum instances (มีค่าใช้จ่ายเพิ่ม กระทบข้อ 2.1 ที่งบยังไม่ทราบ) จะเกิด cold start ที่ต้องโหลดโมเดลใหม่ทุกครั้งที่ instance ตื่นจาก idle — โมเดล embedding ขนาดหลายสิบ MB ทำให้ cold start ยาวกว่าปกติ แต่**ไม่ใช่ปัญหาใหม่ที่เกิดจาก Firebase โดยเฉพาะ** (Vercel serverless functions ก็มี cold start ลักษณะเดียวกัน)
> - **ถ้าใช้ Cloud Functions (2nd gen) แบบดั้งเดิมแทน App Hosting** (ทางเลือกที่ 2 ในหัวข้อ 2.2): แต่ละ invocation มักถูกออกแบบให้ stateless/short-lived มากกว่า และมี memory limit ต่อ function ที่ต้องตั้งค่าเอง (ค่าเริ่มต้นอาจไม่พอสำหรับโมเดล embedding) — **มีความเสี่ยงสูงกว่า App Hosting** ที่จะเจอปัญหา cold start/out-of-memory เพราะไม่ได้ออกแบบมาให้รัน long-running Next.js server เหมือนกัน — นี่เป็นอีกเหตุผลหนึ่งที่สนับสนุนให้เลือก App Hosting แทน Cloud Functions ตรงๆ (ดูหัวข้อ 2.2)
> - **ถ้า cold start กระทบการใช้งานจริงมากเกินยอมรับได้**: พิจารณาลดขนาดโมเดล embedding ลง (ใช้รุ่น `-small`/`-tiny` ที่ระบุไว้แล้วในคำแนะนำเดิมข้างต้น) หรือเพิ่มสัดส่วนการพึ่ง external LLM API (ส่วนเสริมเดิม) ให้เป็น default มากขึ้น — **ยังไม่ใช่การตัดสินใจสุดท้าย** เพราะงบ (ข้อ 2.1) ยังไม่ยืนยันเหมือนเดิม และต้องทดสอบจริงก่อนสรุป
>
> **ทางเลือกเพิ่มเติมที่พิจารณาแล้วไม่เลือกในรอบที่ 2**:
> - **Vertex AI (บริการ ML ของ Google Cloud ในเครือเดียวกับ Firebase)** สำหรับรัน embedding model แทน Transformers.js — พิจารณาเพราะอยู่ใน ecosystem เดียวกับ Firebase อยู่แล้ว (ลด friction ด้าน IAM) แต่ปฏิเสธเป็นค่าเริ่มต้น เพราะมีค่าใช้จ่ายต่อการเรียก (กระทบข้อ 2.1 ที่งบยังไม่ทราบ เหมือนเหตุผลที่เคยใช้ปฏิเสธ external LLM API เป็นเส้นทางหลัก) และเพิ่มความซับซ้อนของการตั้งค่า service account/IAM เกินความจำเป็นเมื่อเทียบกับ Transformers.js ที่รันเป็น npm library ธรรมดาไม่ต้องพึ่งบริการภายนอกเพิ่ม

### 2.5 ที่เก็บไฟล์หลักฐาน (Evidence Storage) — Firebase Cloud Storage (เปลี่ยนจาก Supabase Storage)

ผู้ใช้ตอบว่า **"ยังไม่ตัดสินใจ"** (ข้อ 6) — ในรอบที่ 1 เอกสารนี้เคยแนะนำค่าเริ่มต้นที่ **ย้ายได้ง่ายที่สุด**แทนการฟันธง (Supabase Storage) — รอบที่ 2 ต้องปรับตามข้อกำหนดบังคับ Firebase (ข้อ 1.4)

**แนะนำ (อัปเดตรอบที่ 2)**: **Firebase Cloud Storage** (สร้างบน Google Cloud Storage bucket) แทน Supabase Storage — เหตุผลหลักคือความสอดคล้องของระบบนิเวศเดียวกัน: Firebase Storage Security Rules อ้าง `request.auth` ชุดเดียวกับ Firestore/Firebase Auth ได้โดยตรง (เหมือนที่ Supabase Storage เคยผูกกับ RLS/Auth ของ Supabase ในรอบที่ 1) — ทำให้ยัง implement กฎ #5 (จำกัดสิทธิ์เฉพาะอาจารย์ผู้สอนวิชานั้น/ผู้บริหารหลักสูตรที่มี curriculum scope ตรงกัน) ได้ในโค้ดชุดเดียวกับ Access Gate เหมือนหลักการเดิม ไม่ต้องตั้งระบบสิทธิ์แยกข้าม provider

**ผลกระทบต่อ portability ที่เคยวางแผนไว้ในรอบที่ 1 (สำคัญ)**: คำแนะนำเดิมเลือก Supabase Storage เพราะพูดโปรโตคอล **S3-compatible** ทำให้มีทางย้ายไป self-hosted MinIO ได้โดย**แก้แค่ configuration/endpoint** — **Firebase Cloud Storage ไม่ใช่ S3-compatible** (ใช้ Google Cloud Storage API/SDK ของตัวเอง) ทางย้าย MinIO ที่เคยวางแผนไว้ในหัวข้อ 4 **ใช้ไม่ได้อีกต่อไป** — ถ้าภายหลังพบว่าต้องเก็บไฟล์ on-prem ตาม PDPA (ข้อ 2.2 ที่ยังไม่ยืนยัน) จะต้อง**เขียนโค้ดชั้น access-control ใหม่ทั้งหมด** (ไม่ใช่แค่เปลี่ยน endpoint เหมือนแผนเดิม) — บันทึกเป็นความเสี่ยงเพิ่มเติมไว้ในหัวข้อ 4

**ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก (อัปเดตรอบที่ 2)**:
- **Supabase Storage** *(คำแนะนำเดิมของรอบที่ 1)* — ไม่เลือกอีกต่อไปเพราะข้อกำหนดบังคับ Firebase (ข้อ 1.4) แม้เหตุผลเดิม (S3-compatible, portable ไป MinIO ได้) ยังเป็นข้อดีเชิงเทคนิคจริงที่เสียไป — **[ยืนยันแล้ว 2026-09-05]**: ผู้ใช้ยืนยันแล้วว่าขอบเขตข้อกำหนดบังคับครอบคลุม**ทั้ง Firebase suite รวม Storage ด้วย** (หัวข้อ 4.1 คำถามที่ 1 — ตัวเลือก B) ทางเลือก "ใช้ Supabase Storage คู่กับ Firestore" ที่เคยเสนอไว้เป็นไปได้ระหว่างรอคำตอบ **ปิดแล้ว ไม่ใช่ทางเลือกที่เปิดอยู่อีกต่อไป** — Firebase Cloud Storage เป็นทางเลือกสุดท้าย ไม่ใช่ทางเลือกที่ต้องเปรียบเทียบอีก
- **เก็บไฟล์เป็น field แนบใน Firestore document โดยตรง** — ปฏิเสธ เพราะ Firestore document มีขีดจำกัดขนาด 1 MiB ต่อ document ไม่เหมาะกับไฟล์หลักฐาน (เอกสาร/รูปภาพ/PDF) ที่มีขนาดใหญ่กว่านั้นได้บ่อย — สอดคล้องกับหลักการเดิมใน [[align-high-level-architecture|align-high-level-architecture]] ที่ระบุว่าที่เก็บหลักฐานควรแยกจากที่เก็บข้อมูลโครงสร้าง
- **ตั้ง on-prem file server (NAS) ของมหาวิทยาลัยตั้งแต่วันแรก** — ปฏิเสธเป็นค่าเริ่มต้นเหมือนรอบที่ 1 เพราะคำตอบ data residency ยังไม่ยืนยัน (ข้อ 2.2) และงบ/เซิร์ฟเวอร์ที่มีจริงยังไม่ทราบ (ข้อ 2.1) — แนะนำเก็บเป็นทางเลือกสำรองที่ทำได้ทันทีที่คำตอบชัดเจน (ดูหัวข้อ 4) — **ข้อควรระวังเพิ่มเติมในรอบที่ 2**: ทางย้ายจาก Firebase Storage ไป on-prem NAS ตอนนี้ซับซ้อนกว่าที่เคยวางแผนไว้กับ Supabase Storage (ไม่มีทาง MinIO เป็นสะพานเชื่อมอีกต่อไป — ดูด้านบน)

### 2.6 Hosting / Deployment — Firebase App Hosting + Firebase project เดียว (เปลี่ยนจาก Vercel + Supabase Cloud)

ผู้ใช้ตอบว่า **"ตัดสินใจทีหลัง"** (ข้อ 7) และงบ/data residency ยังไม่ทราบ (ข้อ 2.1/2.2) — รอบที่ 1 เคยแนะนำ Vercel+Supabase Cloud เป็น managed hosting free-tier ที่ portable — รอบที่ 2 ต้องปรับให้สอดคล้องกับ Firebase/Firestore ที่บังคับใช้แล้ว (ข้อ 1.4, หัวข้อ 2.3)

**แนะนำ (อัปเดตรอบที่ 2)**: เพราะ database/auth/storage ทั้งหมดอยู่ใน Firebase project เดียวกันแล้ว (หัวข้อ 2.3/2.5/2.7) การ deploy frontend/backend (Next.js) แยกไปอยู่ Vercel (คนละผู้ให้บริการ) จะทำให้ต้องบริหารจัดการ 2 ผู้ให้บริการคู่ขนาน (Vercel สำหรับ compute + Google Cloud/Firebase สำหรับข้อมูล) เพิ่มความซับซ้อนของการตั้งค่าเครือข่าย/สิทธิ์ (service account credential ข้าม provider) เกินความจำเป็นเมื่อเทียบกับ deploy ทั้งหมดในระบบนิเวศ Firebase เดียว — ตรงกับเหตุผลเดิมที่ต้องการ "1 deployable unit" สำหรับทีมเล็ก/ผู้ดูแลไม่ใช่โปรแกรมเมอร์มืออาชีพ (ข้อ 1.1/1.3):

- **Frontend+API (Next.js)**: **Firebase App Hosting** (ดูรายละเอียดทางเลือก deploy ในหัวข้อ 2.2) — region ที่ใกล้ไทยที่สุดเท่าที่ Firebase มีให้ ณ ตอนเขียนเอกสารนี้คือ `asia-southeast1` (สิงคโปร์) — **ต้องตรวจสอบรายชื่อ region ที่ Firebase App Hosting รองรับจริงอีกครั้งก่อนตั้งค่าใช้งานจริง** เพราะเป็นบริการค่อนข้างใหม่ อาจมี region ให้เลือกจำกัดกว่า Firebase Hosting/Firestore ทั่วไป
- **Firestore/Auth/Storage**: อยู่ใน Firebase project เดียวกัน เลือก region เดียวกันเพื่อลด latency ข้าม region และลดความซับซ้อนของการตั้งค่า

**ข้อควรระวังเรื่องงบประมาณ (ข้อมูลใหม่ ผูกกับข้อ 2.1 ที่ยังไม่ทราบ)**: Firebase มี 2 tier หลัก — **Spark (ฟรี)** และ **Blaze (pay-as-you-go)** — Firebase App Hosting และการเรียก network ออกภายนอกโปรเจกต์ (เช่น external LLM API แบบ feature-flag ในหัวข้อ 2.4) **ต้องใช้ Blaze plan เท่านั้น** (Spark plan จำกัดไม่ให้เรียก API ภายนอก Google และไม่รองรับบริการ compute แบบ App Hosting) — ต่างจากรอบที่ 1 ที่ Vercel+Supabase free tier ครอบคลุมทุกฟีเจอร์ที่วางแผนไว้ได้โดยไม่ต้องอัปเกรด — **นี่เป็นข้อมูลใหม่ที่ต้องแจ้งผู้ใช้อย่างชัดเจน**: แม้ Blaze จะมี free quota รายเดือนให้ในตัว (ไม่ได้แปลว่าเสียเงินทันทีที่สมัคร) แต่ต้องผูกบัตรเครดิต/billing account ไว้ล่วงหน้า ซึ่งอาจกระทบขั้นตอนขออนุมัติงบ/บัญชีของมหาวิทยาลัย (ข้อ 2.1) — **ยังไม่ยืนยันว่าทีม/มหาวิทยาลัยมีช่องทางผูก billing account ได้หรือไม่** — **[ยืนยันแล้ว 2026-09-05]** ผู้ใช้ตอบคำถามที่ 4 (หัวข้อ 4.1) ว่า **ไม่มีอะไรเปลี่ยนแปลงจากคำตอบเดิม** งบประมาณ/ช่องทางผูก billing account **ยังไม่ทราบเหมือนเดิม** (ตัวเลือก A) — ประเด็นนี้จึงยังคงเปิดค้างจริง ไม่ได้ถูกปิดในการยืนยันรอบนี้ ต้องกลับมายืนยันซ้ำก่อนเริ่ม deploy จริง (ดูหัวข้อ 4)

**เหตุผลที่ไม่เลือก on-prem ทั้งหมดตั้งแต่วันแรก (คงเดิมจากรอบที่ 1)**: ผู้ดูแลระยะยาวคืออาจารย์ที่ไม่ใช่โปรแกรมเมอร์มืออาชีพ (ข้อ 1.3) — การดูแลเซิร์ฟเวอร์เอง (patch OS, ต่ออายุ SSL, สำรองข้อมูล, monitor uptime) ต้องมีความรู้ sysadmin ที่เกินกำลังของผู้ดูแลกลุ่มนี้ในระยะยาว และในรอบที่ 2 ยิ่งทำไม่ได้เต็มรูปแบบกว่าเดิม เพราะ Firestore เป็นบริการ cloud ของ Google ล้วนๆ ไม่มีทาง self-host เลย (ต่างจาก Supabase ที่เคยมี escape hatch ไป self-host)

**ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก (อัปเดตรอบที่ 2)**:
- **Vercel (frontend+API) + Firebase แยก (สำหรับ database เท่านั้น)** — เป็นไปได้ทางเทคนิค (Vercel เรียก Firestore ผ่าน Firebase Admin SDK ได้ปกติเหมือนเรียก API ภายนอกทั่วไป ไม่ต้องอยู่ใน infrastructure เดียวกัน) แต่ไม่เลือกเป็น default เพราะเพิ่มจำนวนผู้ให้บริการที่ต้องดูแลสิทธิ์/บัญชีแยกกัน (ขัดกับหลักการเดิม "ลดจำนวนสิ่งที่ต้องดูแล" ข้อ 1.1/1.3) — **[ยืนยันแล้ว 2026-09-05]**: ผู้ใช้ยืนยันแล้วว่าขอบเขตข้อกำหนดบังคับครอบคลุม**ทั้ง Firebase suite รวม Hosting ด้วย** (หัวข้อ 4.1 คำถามที่ 1 — ตัวเลือก B) เงื่อนไข "ถ้าบังคับเฉพาะ Firestore database เท่านั้น ไม่บังคับ hosting" ที่เคยเปิดให้พิจารณาทางเลือกนี้ใหม่ **ปิดแล้ว ไม่ใช่ทางเลือกที่เปิดอยู่อีกต่อไป** — ปฏิเสธทางเลือกนี้อย่างถาวร แม้จะมี DX ที่ทีมคุ้นเคยกว่า (จากรอบที่ 1) และไม่ต้องผูก billing account ล่วงหน้าเหมือน Blaze plan ก็ตาม เพราะขัดกับข้อกำหนดบังคับที่ยืนยันแล้ว
- **On-premise server ของมหาวิทยาลัยทั้งหมดตั้งแต่วันแรก** — ปฏิเสธเป็นค่าเริ่มต้นตามเหตุผลข้างต้น (เหตุผลเดิมยังใช้ได้) แต่เก็บไว้เป็นทางเลือกสำรองที่ชัดเจนเมื่อคำตอบงบ/data residency ยืนยันว่าจำเป็น — **ข้อควรระวังในรอบที่ 2**: ทำได้เฉพาะชั้น frontend/backend (containerize Next.js เอง) เท่านั้น ชั้น database/storage ไม่มีทาง self-host ได้เลยตราบใดที่ยังผูก Firestore/Firebase Storage อยู่ (ต่างจากแผนเดิมที่ทั้งระบบย้าย on-prem ได้ทั้งหมด)
- **Managed cloud รายใหญ่แบบเต็มรูปแบบ (AWS/Azure โดยตรง ไม่ผ่าน BaaS)** — ปฏิเสธเหมือนรอบที่ 1 (เหตุผลเดิมยังใช้ได้) และยิ่งไม่เกี่ยวข้องในรอบนี้เพราะข้อกำหนดบังคับระบุ Firebase (ผลิตภัณฑ์ Google) ไว้ชัดเจนแล้ว (ข้อ 1.4)

### 2.7 Authentication — Firebase Authentication (เปลี่ยนจาก Supabase Auth) รองรับ flow E6 ของสเปค พร้อมช่องเชื่อม SSO ในอนาคต

ผู้ใช้ตอบว่า **"ยังไม่ทราบ"** สถานะ SSO ของมหาวิทยาลัย (ข้อ 5, ยังคงเหมือนเดิมในรอบที่ 2 — และ**[ยืนยันแล้ว 2026-09-05]**ว่ายังไม่เปลี่ยน ตามคำตอบคำถามที่ 4 ในหัวข้อ 4.1) — ในรอบที่ 1 เอกสารนี้เคยแนะนำ Supabase Auth คู่กับ PostgreSQL — รอบที่ 2 เปลี่ยนเป็น **Firebase Authentication** เพราะเหตุผลเดียวกับที่เคยใช้เลือก Supabase Auth คู่กับ Supabase Postgres: **auth ผูกกับ database engine เดียวกัน** (Firestore Security Rules อ้าง `request.auth.uid`/custom claims ของ Firebase Auth ได้โดยตรง — ถ้าใช้ auth provider คนละเจ้ากับ database จะต้องเขียนกลไก sync user id/token ข้ามระบบเองเพิ่ม ซึ่งเพิ่มความเสี่ยง bug ให้ทีมเล็กที่ไม่มีความชำนาญด้าน security ข้อ 1.1/1.2) — **[ยืนยันแล้ว 2026-09-05]**: ผู้ใช้ยืนยันแล้วว่าขอบเขตข้อกำหนดบังคับครอบคลุม**ทั้ง Firebase suite รวม Authentication ด้วย** (หัวข้อ 4.1 คำถามที่ 1 — ตัวเลือก B) **Firebase Authentication จึงเป็นทางเลือกสุดท้าย ไม่ใช่ทางเลือกที่ต้องเปรียบเทียบกับ Supabase Auth อีกต่อไป**

ยังคงหลักการเดิมจากรอบที่ 1 ทั้งหมด (เปลี่ยนแค่ชื่อผลิตภัณฑ์):
- Firebase Authentication เป็น implementation ที่ผ่านการทดสอบด้านความปลอดภัยมาแล้วเช่นเดียวกับ Supabase Auth (password hashing, session/JWT, reset flow) — ทีมเล็กที่ไม่มีความชำนาญด้าน security (ข้อ 1.1/1.2) ไม่ต้องเขียนกลไกเหล่านี้เอง ซึ่งเสี่ยงเกิดช่องโหว่ถ้าเขียนเองในกรอบเวลา 2 เดือน (ข้อ 3)
- ออกแบบให้สถานะบัญชี (`pending`/`approved`/`rejected`), role (`instructor`/`program_admin`), และ `program_admin_curriculum_scope` **ยังคงเก็บแยกใน Firestore collection `users` ต่างหาก** (ไม่ใช่แค่ Firebase Auth custom claims เพียงอย่างเดียว) ตามหลักการเดิมที่ต้องการแยก identity ออกจาก role/status/scope — การแยกเช่นนี้ทำให้ Access Gate (ชั้น Next.js server) ตรวจ "ทุกคำร้องขอ" ตามกฎ #6 ได้จาก collection นี้โดยตรง ไม่ผูกกับกลไก auth provider ใดเป็นการเฉพาะ (สอดคล้องกับที่ [[align-api-schema-design|align-api-schema-design]] §3 กำหนดไว้ — แม้ต้องถูกออกแบบใหม่เป็น Firestore document ตามหัวข้อ 2.3 ก็ตาม หลักการแยก identity/authorization ยังคงเดิม) — ถ้าต้องการ performance ที่ดีกว่า (ลดจำนวน Firestore read ต่อ request) อาจ mirror บางส่วน (role, status) เข้า **Firebase custom claims** เพิ่มเติมได้ แต่ยังต้องเก็บ source of truth ไว้ที่ Firestore collection เหมือนเดิม เพราะ custom claims ต้อง force refresh token ก่อนถึงจะเห็นผลการเปลี่ยนแปลง (มีดีเลย์ ไม่เหมาะเป็น source of truth เพียงอย่างเดียวสำหรับ revoke สิทธิ์ทันที)
- **ช่องเชื่อม SSO ในอนาคต**: Firebase Authentication รองรับ OAuth2/OIDC provider เพิ่มได้ในตัวฟรี (Google/Microsoft/ผู้ให้บริการ OIDC ทั่วไป) — ถ้าภายหลังมหาวิทยาลัยยืนยันว่ามี SSO ที่รองรับ OAuth2/OIDC สามารถเพิ่มเป็น auth provider เสริมได้โดยไม่ต้องแก้โครงสร้าง collection `users` (เพราะ role/status/scope อยู่แยกจาก auth identity อยู่แล้ว) — ถ้า SSO ของมหาวิทยาลัยใช้ **SAML** จะต้องอัปเกรดเป็น **Google Cloud Identity Platform (GCIP)** ซึ่งเป็น superset แบบเสียเงินของ Firebase Auth ที่รองรับ SAML/Enterprise SSO — เป็นข้อจำกัดคล้ายเดิม (Supabase ก็ต้องอัปเกรดเป็น Pro/Enterprise สำหรับ SAML เหมือนกัน) จึงไม่ใช่ trade-off ใหม่ที่เกิดจากการเปลี่ยนมาใช้ Firebase โดยเฉพาะ (ดูหัวข้อ 4)

**ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก (อัปเดตรอบที่ 2)**:
- **Supabase Auth** *(คำแนะนำเดิมของรอบที่ 1)* — ไม่เลือกอีกต่อไปเพราะข้อกำหนดบังคับ Firebase (ข้อ 1.4) และเพื่อหลีกเลี่ยงความซับซ้อนของการผูก auth คนละเจ้ากับ database (ถ้าใช้ Firestore เป็น database แต่ยังใช้ Supabase Auth เป็น identity provider จะต้อง sync user id ข้ามระบบเอง เพิ่มความเสี่ยง bug ให้ทีมเล็ก ข้อ 1.1) — เหตุผลเดิมที่เคยเลือก Supabase Auth (ทดสอบความปลอดภัยมาแล้ว, ลดงานเขียนเอง) ยังใช้ได้กับ Firebase Auth เช่นเดียวกัน จึงไม่ใช่การเสีย trade-off ด้านความปลอดภัยแต่อย่างใด เป็นเพียงการเปลี่ยนผลิตภัณฑ์ให้สอดคล้องกับ database ที่ถูกบังคับ
- **เขียนระบบ auth เอง (custom password hashing/session)** — ปฏิเสธเหมือนรอบที่ 1 เพราะเป็นโค้ดที่กระทบความปลอดภัยโดยตรง เสี่ยงเกินไปสำหรับทีมเล็กที่ไม่มีความชำนาญเฉพาะทางภายใต้เดดไลน์บีบ (ข้อ 1.1/1.2/3)
- **สร้างระบบเชื่อม SSO/SAML เต็มรูปแบบตั้งแต่วันแรก** — ปฏิเสธเหมือนรอบที่ 1 เพราะยังไม่ทราบว่ามหาวิทยาลัยมี SSO จริงหรือไม่ (ข้อ 5) การลงทุนเวลาสร้างระบบเชื่อมที่อาจไม่มีปลายทางให้เชื่อมจริงเป็นการเสียเวลาที่มีจำกัดมาก (ข้อ 3) โดยเปล่าประโยชน์

## 4. ประเด็นที่ยังไม่ยืนยัน — ต้องกลับมาทบทวนเมื่อรู้คำตอบจริง

รายการต่อไปนี้คือจุดที่เอกสารนี้เลือกทางเลือก **default ที่ portable ไว้ก่อน** เพราะคำตอบสัมภาษณ์ยังไม่ชัดเจน — **ห้ามถือว่าเป็นการตัดสินใจสุดท้าย** ต้องกลับมายืนยันซ้ำทันทีที่รู้คำตอบจริง (อัปเดตรอบที่ 2 — 2026-09-05 ตามข้อกำหนดบังคับ Firebase ข้อ 1.4)

> **อัปเดตรอบที่ 3 (2026-09-05)**: คำถามที่ 1–3 ในหัวข้อ 4.1 (ขอบเขตข้อกำหนดบังคับ, เงื่อนไข portable, บริบทงานส่งวิชา vs deploy จริง) **ปิดครบแล้ว** — 2 แถวสุดท้ายของตารางนี้ (ขอบเขตข้อกำหนดบังคับ Firebase, บริบทการใช้งานจริง) จึงไม่ใช่ "ประเด็นที่ยังไม่ยืนยัน" อีกต่อไป ทำเครื่องหมายปิดไว้ท้ายตาราง — ส่วนแถวอื่นๆ (งบประมาณ/data residency ทาง legal/สถานะ SSO/ที่เก็บไฟล์หลักฐานสุดท้าย/deployment สุดท้าย/การเปิดใช้ external AI API) **ยังเปิดค้างอยู่เหมือนเดิม** เพราะคำถามที่ 4 ยืนยันแล้วว่า **ไม่มีอะไรเปลี่ยนแปลง** จากคำตอบเดิม ("ยังไม่ทราบ"/"ตัดสินใจทีหลัง" ทุกข้อ) — สิ่งที่เปลี่ยนคือ**เนื้อหา migration path บางแถว**ที่เคยเขียนแบบมีเงื่อนไขผูกกับคำถามที่ 1 (เช่น "ถ้าบังคับเฉพาะ Firestore ก็ยังย้ายกลับ Vercel ได้") ซึ่งปิดแล้วตามคำตอบยืนยัน — ปรับให้เหลือทางออกเดียวคือ Firebase ทั้ง suite เท่านั้น

| ประเด็นที่ยังไม่ทราบ | Default ที่แนะนำไว้ก่อน (อัปเดตรอบ 2) | เงื่อนไขที่ต้องกลับมาทบทวน | ทางย้าย (migration path) |

### 4.1 คำถามที่ยังค้าง — ต้องสัมภาษณ์ผู้ใช้เพิ่มก่อนถือว่าการปรับรอบนี้เสร็จสมบูรณ์

> เครื่องมือ `AskUserQuestion` ไม่พร้อมใช้งานในบริบทการทำงานนี้ — คำถามทั้งหมดด้านล่าง (พร้อม 3 ตัวเลือก + ข้อดี/ข้อเสียของแต่ละตัวเลือก) ถูกส่งกลับไปในรายงานสรุปให้ผู้เรียกงาน (skill/บทสนทนาหลัก) นำไปถามผู้ใช้แทน แล้วส่งคำตอบกลับมาปรับเอกสารนี้ต่อ
>
> **[ยืนยันแล้ว 2026-09-05 — รอบที่ 3]**: ผู้ใช้ตอบครบทั้ง 4 ข้อแล้ว — ตัวเลือกที่ผู้ใช้เลือกทำเครื่องหมายไว้ที่หัวข้อของแต่ละคำถามด้านล่าง ตัวเลือกที่ไม่ได้เลือกยังคงเก็บไว้ทั้งหมดเพื่อ traceability ว่าเคยพิจารณาอะไรบ้างก่อนตัดสินใจ — คำถามทั้ง 4 ข้อนี้ถือว่า**ปิดสมบูรณ์**แล้ว ไม่ต้องสัมภาษณ์ซ้ำ เว้นแต่ข้อกำหนดวิชา/นโยบายมหาวิทยาลัยเปลี่ยนแปลงในอนาคต

**คำถามที่ 1 — ขอบเขตที่แท้จริงของข้อกำหนด "ต้องใช้ Firebase/Firestore" — [ยืนยันแล้ว: เลือกตัวเลือก B]**
- ตัวเลือก A: บังคับเฉพาะ Firestore เป็น database เท่านั้น (ส่วน hosting/auth/storage เลือกอะไรก็ได้) — ข้อดี: ยังคง portable สำหรับ hosting (กลับไป Vercel ได้)/auth ได้ ลดผลกระทบต่อ stack เดิมของรอบที่ 1 มากที่สุด · ข้อเสีย: ต้องดูแล 2 ผู้ให้บริการคู่ขนาน (Vercel+Firebase), Security Rules ของ Firestore อ้าง auth คนละเจ้าไม่ได้ตรงๆ ต้องเขียน sync เอง — **ไม่ได้เลือก**
- **ตัวเลือก B (เลือกแล้ว): บังคับทั้ง Firebase suite** (Firestore+Auth+Storage+Hosting) — ข้อดี: สถาปัตยกรรมเรียบง่าย ดูแลที่เดียว ตรงกับหลักการเดิมของทีมเล็ก (ข้อ 1.1/1.3) · ข้อเสีย (ยอมรับแล้ว): เสีย portability ทุกชั้น ผูก vendor lock-in เต็มรูปแบบ ต้องผูก billing account (Blaze plan) ตั้งแต่ต้น — **ผู้ใช้ยืนยัน: ต้องใช้ Firebase Authentication, Cloud Firestore, Cloud Storage, และ Firebase Hosting ครบทุกส่วน ไม่ใช่แค่ Firestore อย่างเดียวแล้วคง Vercel/Supabase Auth ไว้**
- ตัวเลือก C: ยังไม่แน่ใจ/ต้องถามอาจารย์ผู้สอนก่อน — ข้อดี: ไม่ตัดสินใจผิดจากการเดา · ข้อเสีย: งานต่อเนื่อง (`api-schema-designer`/`technical-designer`) ต้องรอคำตอบก่อนเริ่มออกแบบ Firestore data model ใหม่ได้เต็มที่ — **ไม่ได้เลือก**

**คำถามที่ 2 — เงื่อนไข portable/self-host ที่เคยต้องการ (รอบที่ 1) ยังจำเป็นอยู่ไหมสำหรับส่วนที่ Firebase ไม่ได้บังคับตรงๆ — [ยืนยันแล้ว: เลือกตัวเลือก A]**
- **ตัวเลือก A (เลือกแล้ว): ไม่จำเป็นอีกต่อไป** ยอมรับ full Firebase lock-in ทุกชั้นเพื่อความเรียบง่าย — ข้อดี: สถาปัตยกรรมง่ายที่สุด ดูแลง่ายสุดสำหรับทีมเล็ก · ข้อเสีย (ยอมรับแล้ว): ถ้า data residency (ข้อ 2.2) ออกมาเข้มงวดภายหลัง จะไม่มีทางย้ายได้เลย — **ผู้ใช้ยืนยัน: ไม่จำเป็นแล้ว ยอมรับว่าระบบผูกกับ Firebase ถาวร (lock-in เต็มรูปแบบ) เป็นผลตามมาที่ยอมรับได้ เพราะเลือกใช้ทั้ง suite ไปแล้วตามคำถามที่ 1**
- ตัวเลือก B: ยังต้องการ portable ให้มากที่สุดเท่าที่ไม่ขัดกับ Firestore บังคับ (เช่น เก็บไฟล์หลักฐานที่ storage อื่นที่ portable กว่า แม้ database เป็น Firestore) — ข้อดี: ลดความเสี่ยง lock-in ต่อ PDPA/data residency ในอนาคต · ข้อเสีย: สถาปัตยกรรมซับซ้อนขึ้น (ข้ามผู้ให้บริการ) — **ไม่ได้เลือก**
- ตัวเลือก C: ยังไม่ได้คิด/ต้องปรึกษาก่อน — ข้อดี: ไม่ฟันธงเกินข้อมูลที่มี · ข้อเสีย: เอกสารนี้ต้องคง default ไว้ก่อนซึ่งอาจไม่ตรงใจภายหลัง — **ไม่ได้เลือก**

**คำถามที่ 3 — บริบทของโปรเจกต์ (งานส่งวิชา/ต้นแบบวิชาการ vs deploy ใช้งานจริง) — [ยืนยันแล้ว: เลือกตัวเลือก A]**
- **ตัวเลือก A (เลือกแล้ว): เป็นงานส่งวิชา/ต้นแบบวิชาการที่ใช้ข้อมูลจำลอง** ไม่ deploy ใช้งานจริงกับข้อมูลนักศึกษาจริงของมหาวิทยาลัย — ข้อดี: PDPA/data residency ไม่ใช่ข้อบังคับทางกฎหมายที่เข้มงวดจริงจัง (ยังควรออกแบบให้ถูกหลักไว้เพื่อการเรียนรู้ แต่ไม่ต้องแก้ conflict เชิง legal จริง) · ข้อเสีย: ถ้าภายหลังจะ deploy ใช้จริงต้องกลับมาทบทวนใหม่ทั้งหมด — **ผู้ใช้ยืนยัน: ใช้งานเฉพาะอาจารย์ผู้สอนเท่านั้น (ไม่ใช่ production deployment ที่มีข้อมูลนักศึกษาจริงหมุนเวียน) — แปลว่าความเข้มงวดเรื่อง PDPA/data residency ยังคงออกแบบไว้ในสเปคตามเดิม (ห้ามลดทอนกฎ #5) แต่บริบทการใช้งานจริงรอบนี้ไม่ใช่ production ที่มีข้อมูลนักศึกษาจริงหมุนเวียนอยู่**
- ตัวเลือก B: ตั้งใจ deploy ใช้งานจริงกับข้อมูลนักศึกษาจริงของมหาวิทยาลัยด้วย (ไม่ใช่แค่ส่งงาน) — ข้อดี: ออกแบบให้ถูกต้องตาม PDPA ตั้งแต่ต้น ลดความเสี่ยงทาง legal ภายหลัง · ข้อเสีย: ข้อจำกัดเรื่อง data residency (ไม่มี Firebase region ในไทย) กลายเป็นความเสี่ยงจริงที่ต้องแก้ไขจริงจัง ไม่ใช่แค่ทฤษฎีในเอกสาร — **ไม่ได้เลือก**
- ตัวเลือก C: ยังไม่แน่ใจ (อาจเริ่มจากส่งงานก่อน แล้วพิจารณา deploy จริงทีหลังถ้าได้ผลตอบรับดี) — ข้อดี: ไม่ต้องตัดสินใจเกินความจำเป็นตอนนี้ · ข้อเสีย: เอกสารนี้ต้องออกแบบแบบระมัดระวังไว้ก่อนทั้งสองกรณี เพิ่มงานเผื่อ — **ไม่ได้เลือก**

**คำถามที่ 4 — งบ/data residency/SSO/deployment ที่เคยตอบ "ยังไม่ทราบ" มีอะไรเปลี่ยนไปหรือไม่ตอนนี้ที่รู้ว่าต้องใช้ Firebase — [ยืนยันแล้ว: เลือกตัวเลือก A]**
- **ตัวเลือก A (เลือกแล้ว): ไม่มีอะไรเปลี่ยน** ยังไม่ทราบเหมือนเดิมทุกข้อ — ข้อดี: เอกสารนี้ใช้ default ที่ระบุไว้ในหัวข้อ 4 ต่อไปได้เลยโดยไม่ต้องรื้อใหม่ · ข้อเสีย (ยอมรับแล้ว): ความไม่แน่นอนยังค้างอยู่ทุกมิติ โดยเฉพาะเรื่อง billing account (Blaze plan) ที่เป็นข้อจำกัดใหม่ — **ผู้ใช้ยืนยัน: ไม่เปลี่ยนจากที่เคยตอบไว้เดิม (ยังไม่ทราบ/ตัดสินใจทีหลังเหมือนเดิมทุกข้อ)**
- ตัวเลือก B: มีการเปลี่ยนแปลง (ระบุเพิ่มเติมว่าเปลี่ยนอะไรบ้าง) — ข้อดี: ได้ข้อมูลที่แม่นยำขึ้นทันที ปรับเอกสารให้ตรงจริงได้เลย · ข้อเสีย: ต้องรอคำตอบละเอียดก่อนเขียนส่วนที่เกี่ยวข้องต่อให้สมบูรณ์ — **ไม่ได้เลือก**
- ตัวเลือก C: บางข้อเปลี่ยน บางข้อไม่เปลี่ยน (ระบุทีละข้อ: งบ/data residency/SSO/deployment) — ข้อดี: แม่นยำที่สุด ไม่ต้องเดารวมทั้งหมด · ข้อเสีย: ใช้เวลาสัมภาษณ์เพิ่มมากกว่า 2 ตัวเลือกแรก — **ไม่ได้เลือก**

## 5. ข้อเสนอต่อ [[align-technical-design|align-technical-design]] §5

`align-technical-design.md` §5 (เดิม) เป็น "ข้อเสนอคร่าวๆ ยังไม่ยืนยัน" ที่เขียนไว้ก่อนมีการสัมภาษณ์จริง — เทียบกับคำแนะนำในเอกสารนี้แล้วมีจุดที่ **ต่างออกไปอย่างมีนัยสำคัญ** เพราะตอนนี้มีข้อมูลสัมภาษณ์จริงรองรับ:
- §5 เดิมเสนอ backend เป็น "framework เชิง object-oriented หรือ Node.js/Python ที่ทีมคุ้นเคย" (ลอยๆ ไม่ระบุ) — เอกสารนี้ระบุจริงเป็น Next.js API Routes/Server Actions ในโปรเจกต์เดียวกับ frontend เพราะทีมไม่มีความถนัดเดิม + เดดไลน์ 2 เดือน
- §5 เดิมเสนอ "AI Matching Service … internal service หรือเรียก LLM API ภายนอก" แบบเปิดกว้าง — เอกสารนี้ระบุ hybrid ที่เจาะจง (Transformers.js in-process + external API แบบ feature-flag) ตามคำตอบสัมภาษณ์จริง
- §5 เดิมไม่ได้พูดถึงความ portable ของ hosting/storage เพราะตอนนั้นยังไม่มีคำถามเรื่องงบ/data residency ที่ยังไม่ทราบ — เอกสารนี้เพิ่มมิตินี้เข้ามาทั้งหมด (หัวข้อ 4)
