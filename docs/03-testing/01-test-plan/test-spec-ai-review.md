# Test Spec: ตรวจสอบและยืนยันผล AI (AI Review & Confirmation)

**สถานะเอกสาร**: Test Spec เดี่ยว (standalone) — เป็นตัวอย่าง Test Spec ที่ผูกกับ **1 Feature** และ **1 จุดใน User Journey** อย่างชัดเจน ตามข้อกำหนด "ต้องมี Test Spec อย่างน้อย 1 ฉบับที่สอดคล้องกับ User Journey/Feature ที่เลือก"

**ความสัมพันธ์กับเอกสารอื่น**: เอกสารนี้ **ไม่ใช่ตัวแทน** ของ [[e3-ai-matching-gap-analysis|e3-ai-matching-gap-analysis]] ซึ่งเป็น Test Case ฉบับเต็มของ Epic E3 ทั้งหมด (ครอบคลุม AB-08, AB-09, AB-10, AB-20, AB-21, AB-22 รวม 32 test case) — เอกสารนี้เป็น**ฉบับโฟกัส (companion)** ที่หยิบเฉพาะ AB-08/AB-09/AB-10 (ส่วน "ตรวจสอบและยืนยันผล AI" ล้วนๆ ไม่รวมสูตรคำนวณ % ของ AB-20/AB-21 หรือ gap analysis ของ AB-22) มาเรียบเรียงใหม่ให้เห็นภาพ **Feature เดียว + User Journey step เดียว** อย่างเป็นระบบ พร้อม traceability ที่ตามรอยกลับไปยัง test case เต็มในไฟล์ e3 ได้ทุกจุด — ไม่มี test case ใดในเอกสารนี้ที่ขัดแย้งกับ e3

## (a) Feature ที่ทดสอบและเหตุผลที่เลือก

### Feature ที่เลือก
**"ตรวจสอบและยืนยันผล AI ก่อนบันทึกจริง (Human-in-the-loop)"** — ตรงกับรายการใน [[../../01-requirements/02-plan/feature-list|feature-list]] Epic E3 และ User Story:
- **AB-08** — AI จับคู่การสอนกับ CLO เฉพาะกลุ่มหลักสูตรที่ถูกต้อง พร้อม match %
- **AB-09** — AI เชื่อมโยงผลจับคู่ CLO ไปยัง PLO ของกลุ่มหลักสูตรเดียวกัน
- **AB-10** — อาจารย์ตรวจสอบและยืนยัน/แก้ไขผลจับคู่ AI ก่อนบันทึกจริงทุกครั้ง

### จุดใน User Journey ที่ Feature นี้ผูกอยู่
ตรงกับแถว **"ระหว่างเทอม — หลังสอนแต่ละคาบ"** ใน [[../../02-design/01-prototypes/align-user-journey|align-user-journey]] §1 (User Journey ของอาจารย์ผู้สอน):

> "บันทึกหัวข้อการสอน + แนบหลักฐานทันทีหลังสอนจริง ระบบให้ AI จับคู่ CLO/PLO อัตโนมัติเป็นค่าตั้งต้น อาจารย์แค่ตรวจสอบและกดยืนยัน (ไม่ต้องนั่งไล่จับคู่เองทีละ CLO)"

Touchpoint ของขั้นตอนนี้คือ [[../../02-design/01-prototypes/align-app-screens#หน้าจอ 5 — บันทึกการสอน (Teaching Record Entry)|หน้าจอ 5 — Teaching Record Entry]] → [[../../02-design/01-prototypes/align-app-screens#หน้าจอ 6 — ตรวจสอบและยืนยันผล AI (AI Review Panel)|หน้าจอ 6 — AI Review Panel]] ซึ่งในต้นแบบ interactive prototype คือไฟล์ `AIReviewPanel.dc.html` (desktop) / `M-AIReviewPanel.dc.html` (mobile) ตาม [[../../02-design/01-prototypes/align-interactive-prototype|align-interactive-prototype]]

### ทำไมถึงเลือก Feature นี้เป็นตัวอย่าง Test Spec
1. **เป็นกฎที่สำคัญที่สุดของทั้งระบบ** — `DESIGN.md` §4 **UX Rule 1** ระบุไว้ตรงๆ ว่า "Draft ≠ Confirmed ต้องแยกด้วยตาเปล่าได้ทันที ... ห้ามให้ draft กับ confirmed ใช้ visual เดียวกัน" และหน้าจอ 6 เองก็เขียนกำกับไว้ว่า **"นี่คือกฎที่พลาดไม่ได้ที่สุดของระบบ"** (`align-app-screens.md` บรรทัดอธิบายหน้าจอ 6 ส่วนที่ 1)
2. **เป็นกฎทางธุรกิจข้อบังคับ (BR#3)** ใน `CLAUDE.md`: "AI เป็นค่าตั้งต้น ไม่ใช่ค่าบังคับ ... ห้ามออกแบบให้ระบบบันทึกผล AI ทันทีโดยไม่ผ่านการยืนยันของมนุษย์" — ถ้ากฎนี้พัง ข้อมูลทั้งระบบ (แดชบอร์ด, มคอ., SAR) จะอ้างอิงผลที่ยังไม่ผ่านการตรวจสอบของมนุษย์ทันที กระทบทุก Epic ปลายน้ำ (E4, E5)
3. **เป็นจุดตัดสินใจเดียวที่ผู้ใช้ต้องลงมือทำเองในทั้ง flow** — ขั้นตอนอื่นในหน้าจอ 5 เป็นการบันทึกข้อมูลตามปกติ แต่หน้าจอ 6 คือจุดที่ "มนุษย์" ต้องเข้ามาตรวจสอบผลของ "เครื่องจักร" ก่อนที่ข้อมูลจะกลายเป็นทางการ — เหมาะเป็นตัวอย่าง Test Spec ที่แสดงให้เห็นทั้ง happy path, edge case และ rejection ของกฎเดียวกันได้ครบในเอกสารเดียว

## (c) Test Cases (Given/When/Then)

### กลุ่ม 1 — AI จับคู่เฉพาะภายในกลุ่มหลักสูตรที่ถูกต้อง (AB-08)

**TS-AIREV-01 | Happy path**
- **Given**: `TR-001` เป็นบันทึกการสอนของ `COS101` (หลักสูตร 2565, CLO1–CLO4)
- **When**: ระบบเรียกประมวลผล AI สำหรับ `TR-001` (กดปุ่ม "บันทึกและให้ AI ประมวลผล" จากหน้าจอ 5)
- **Then**: หน้าจอ 6 แสดงผลจับคู่เฉพาะ CLO ของ `COS101` เท่านั้น (เช่น CLO3 ด้วย `match_confidence` ≈ 0.82 ตาม `AIM-001`) พร้อม Curriculum Tag `2565` กำกับทุกรายการ
- **อ้างอิง**: AB-08 AC ข้อ 1–2; รายละเอียดระดับ API ดู `TC-AB08-01` ใน e3

**TS-AIREV-02 | Rejection — ห้ามข้ามกลุ่มหลักสูตร**
- **Given**: `COS101` (2565) และ `COS301` (2570) มีอยู่ในระบบพร้อมกัน มี CLO คนละชุด
- **When**: ประมวลผล AI สำหรับบันทึกการสอนของ `COS101`
- **Then**: หน้าจอ 6 ต้อง**ไม่แสดง** CLO ใดๆ ของ `COS301`/หลักสูตร 2570 เลย แม้เนื้อหาการสอนจะมีความหมายใกล้เคียงกัน — Curriculum Tag ที่ปรากฏในหน้าจอต้องเป็น `2565` ล้วน ไม่มี `2570` ปนอยู่แม้แถวเดียว (ตรงตาม `DESIGN.md` §2.1 กฎ "ห้ามใช้สีสองกลุ่มหลักสูตรสลับกันหรือใช้ปนกัน")
- **อ้างอิง**: AB-08 AC ข้อ 1; รายละเอียดระดับ API ดู `TC-AB08-02` ใน e3

**TS-AIREV-03 | Rejection — รายวิชายังไม่ระบุกลุ่มหลักสูตร**
- **Given**: `COS-DRAFT` มี `teaching_record` แล้วแต่ตัวรายวิชายังไม่ระบุกลุ่มหลักสูตร (2565/2570)
- **When**: ผู้ใช้พยายามกด "บันทึกและให้ AI ประมวลผล" จากหน้าจอ 5 ของ `COS-DRAFT`
- **Then**: ระบบไม่ประมวลผล AI และไม่พาไปหน้าจอ 6 — ต้องแจ้งด้วยโทนกลาง (ตาม UX Rule 3) ว่าต้องระบุกลุ่มหลักสูตรของรายวิชาก่อน ไม่ใช้คำว่า "ผิดพลาด"
- **อ้างอิง**: AB-08 AC ข้อ 3; รายละเอียดระดับ API ดู `TC-AB08-03` ใน e3

### กลุ่ม 2 — Draft ≠ Confirmed ต้องแยกด้วยตาเปล่าได้ทันที (UX Rule 1, AB-10)

**TS-AIREV-04 | Happy path — สถานะ Draft ต้องมองเห็นชัดเจนตั้งแต่แรก**
- **Given**: `AIM-001`, `AIM-002`, `AIM-003` ทั้งหมดเพิ่งถูกสร้าง state = `draft`
- **When**: `U-INSTR-A` เปิดหน้าจอ 6
- **Then**: ทุกรายการแสดง **Match % Indicator แบบ Draft** — เส้นขอบ**ประ** สี `status.draft` (`#B8863C`), พื้นหลัง `status.draft-tint` พร้อม label กำกับข้อความ **"ผลจาก AI — ยังไม่ยืนยัน"** ทุกรายการ ไม่มีรายการใดแสดงเป็นเส้นทึบ `status.confirmed`
- **อ้างอิง**: AB-10 AC ข้อ 1, BR#3, `DESIGN.md` §4 UX Rule 1, `align-app-screens.md` หน้าจอ 6 ส่วนที่ 1

**TS-AIREV-05 | Happy path — เปลี่ยนเป็น Confirmed ทันทีที่กดยืนยัน**
- **Given**: `AIM-002` (`TR-002` ↔ CLO2, confidence 0.75) แสดงเป็น draft ในหน้าจอ 6
- **When**: `U-INSTR-A` กดปุ่ม **"ยืนยัน"** ที่รายการนี้ (ไม่ใช่ auto-save)
- **Then**: badge ของรายการเปลี่ยนจากเส้นขอบประ `status.draft` เป็นเส้นทึบ `status.confirmed` ทันทีแบบ visual feedback ชัดเจน (ไม่ต้องรีเฟรชหน้า), backend บันทึก `state = confirmed`, `confirmed_by = U-INSTR-A`, `confirmed_at` ถูกบันทึกเวลา
- **อ้างอิง**: AB-10 AC ข้อ 1, 3, BR#3; รายละเอียดระดับ API ดู `TC-AB10-01` ใน e3

**TS-AIREV-06 | Edge case — หน้าจอผสม draft และ confirmed พร้อมกัน**
- **Given**: `AIM-002` ถูกยืนยันแล้ว (`confirmed`) แต่ `AIM-001` และ `AIM-003` ยังเป็น `draft`
- **When**: `U-INSTR-A` เปิดหน้าจอ 6 อีกครั้งของ `COS101`
- **Then**: ทั้งสามรายการแสดงพร้อมกันในหน้าเดียวได้ แต่ **ต้องแยก visual ต่อรายการอย่างชัดเจน** — `AIM-002` เป็นเส้นทึบ confirmed, `AIM-001`/`AIM-003` ยังเป็นเส้นประ draft ห้ามมีจุดใดที่ผสมสถานะจนดูเหมือนยืนยันครบแล้วทั้งหน้า
- **อ้างอิง**: AB-10, `align-app-screens.md` หน้าจอ 6 หัวข้อ "States — ยืนยันบางส่วนแล้ว"

### กลุ่ม 3 — อาจารย์แก้ไขผลจับคู่ที่ความมั่นใจต่ำก่อนยืนยัน (AB-10)

**TS-AIREV-07 | Happy path — แก้ไขผลจับคู่ค่าความมั่นใจต่ำก่อนยืนยัน**
- **Given**: `AIM-003` (`TR-003` ↔ CLO1, `match_confidence = 0.40`) แสดงเป็น draft — ตัวอย่างนี้ถูกกำหนดไว้ในชุดข้อมูลทดสอบว่าเป็นค่าจับคู่ที่ไม่แม่น (ดูหมายเหตุเรื่อง threshold ท้ายเอกสาร)
- **When**: `U-INSTR-A` กดปุ่ม **"แก้ไข"** ที่รายการนี้ แล้วปลด CLO1 ออก เพราะเห็นว่าเนื้อหา "Workshop เสริม Git/GitHub" ไม่เกี่ยวข้องกับ CLO1 จริง
- **Then**: state เปลี่ยนเป็น `edited` — ยังคงแสดงเป็นเส้นประ `status.draft` ต่อไป (ยังไม่ใช่ confirmed) จนกว่าจะกดปุ่ม "ยืนยัน" อีกครั้งหลังแก้ไข ซึ่งเมื่อกดแล้ว state จึงเปลี่ยนเป็น `confirmed` โดยไม่มี CLO1 อยู่ในผลที่ยืนยัน
- **อ้างอิง**: AB-10 AC ข้อ 2, BR#3; รายละเอียดระดับ API ดู `TC-AB10-02` ใน e3

**TS-AIREV-08 | Edge case — PLO chip ที่เชื่อมโยงต้องปรับตามการแก้ไข CLO และคงกลุ่มหลักสูตรเดิม**
- **Given**: `AIM-001` (CLO3 ผูกกับ `PLO1565-2`, `PLO1565-3`) แสดงเป็น draft พร้อม chip "PLO 2 · PLO 3 เชื่อมแล้ว"
- **When**: `U-INSTR-A` กด "แก้ไข" แล้วปลด CLO3 ออกจากผลจับคู่
- **Then**: chip PLO ที่เคยแสดงใต้ CLO3 ต้องหายไปพร้อมกัน (ไม่ค้างแสดง PLO ของ CLO ที่ถูกปลดแล้ว) และ chip ที่ยังคงเหลือของ CLO อื่นต้องยังคง Curriculum Tag `2565` กำกับอยู่เสมอ
- **อ้างอิง**: AB-09 AC ข้อ 1–2, AB-10 AC ข้อ 2; รายละเอียดระดับ API ดู `TC-AB09-01` ใน e3

### กลุ่ม 4 — อาจารย์ปฏิเสธผลจับคู่ (AB-10)

**TS-AIREV-09 | Happy path — ปฏิเสธผลจับคู่ทั้งรายการ**
- **Given**: `AIM-003` แสดงเป็น draft (confidence 0.40)
- **When**: `U-INSTR-A` กดปุ่ม **"ปฏิเสธ"** (ไม่ใช่ "แก้ไข") เพราะเห็นว่าจับคู่ผิดทั้งหมด ไม่ใช่แค่บางส่วน
- **Then**: state เปลี่ยนเป็น `rejected` — รายการยังคงอยู่ในประวัติ (ไม่ถูกลบ) แต่ไม่นับเป็นหลักฐานในการคำนวณใดๆ ต่อไป และ badge ต้องไม่แสดงเป็นทั้ง draft และ confirmed (ต้องมี visual แยกสำหรับ rejected เช่นกัน ไม่ใช้ปนกับ draft)

## หมายเหตุ — คำถามเปิดที่ต้องตอบก่อน implement/ทดสอบจริง

เอกสารนี้สืบทอดคำถามเปิดที่เกี่ยวข้องจาก [[test-plan-align|test-plan-align]] §6 และเพิ่มคำถามใหม่ 1 ข้อที่พบระหว่างเขียน Test Spec นี้โดยเฉพาะ (ไม่สมมติคำตอบเอง):

### เดิม (สืบทอดจาก test-plan-align §6.1) — [แก้ไขแล้ว]
คำถามเรื่องสูตรรวมค่าความถี่ที่แมทช์กับสัดส่วน % coverage ได้รับคำตอบยืนยันแล้ว (ดู [[test-plan-align|test-plan-align §6.1]]): % ความถี่ที่แมทช์ = teaching_record ที่ตรง ÷ teaching_record ทั้งหมดของวิชา × 100 แสดง**คู่กัน**กับจำนวนดิบ ไม่ใช่สูตรรวมกับ coverage % — ไม่กระทบ test case ในเอกสารนี้โดยตรงเพราะเอกสารนี้ไม่ครอบคลุม AB-20/AB-21 (ดู test case ที่ปรับปรุงแล้วที่ TC-AB21-04/05 ใน [[e3-ai-matching-gap-analysis|e3-ai-matching-gap-analysis]] และ TC-AB11-05 ใน [[e4-dashboard-alerts|e4-dashboard-alerts]] ซึ่งแสดงผลในหน้าจอ 6/8 ถัดจากส่วนที่ทดสอบในเอกสารนี้)

### ใหม่ — นิยาม "ค่าความมั่นใจต่ำ" (low confidence) ที่ต้องแก้ไขก่อนยืนยัน
สเปค/backlog (AB-10) ใช้คำว่า "อาจารย์แก้ไข/ปลด CLO ที่จับคู่ผิด หรือปรับค่า % ... ที่ AI คำนวณผิดได้ก่อนกดยืนยัน" แต่ **ไม่มีที่ใดกำหนดเกณฑ์ตัวเลข (threshold) ที่ระบบถือว่า `match_confidence` ค่าใดเป็น "ต่ำ"** อย่างเป็นทางการ (เช่น ไม่มีการระบุว่าต้อง highlight พิเศษ/เตือนอาจารย์เมื่อค่าต่ำกว่า 0.5) — TS-AIREV-07 ในเอกสารนี้ใช้ `AIM-003` (`match_confidence = 0.40`) เพียงเพราะเป็นตัวอย่างที่ชุดข้อมูลทดสอบ (`test-plan-align.md` §3.7) กำกับไว้ว่า "ค่าต่ำ" ในเชิงบรรยาย ไม่ใช่เพราะมีกฎ threshold ในระบบจริง **ต้องยืนยันกับผู้ใช้ก่อนว่าระบบจำเป็นต้องมี threshold นี้หรือไม่** ก่อนเขียน test case ที่ตรวจสอบพฤติกรรม auto-highlight/auto-warning ของค่าความมั่นใจต่ำในระบบจริง (ปัจจุบันการ "แก้ไขค่าต่ำ" เป็นการตัดสินใจของอาจารย์เองล้วนๆ ไม่ใช่ระบบบังคับ)
