# 2026-09-05: ข้อกำหนดบังคับ Firebase/Firestore — ปรับ align-tech-stack.md รอบที่ 2

## บริบท

ผู้ใช้ยืนยันข้อจำกัดใหม่ที่กระทบการตัดสินใจ tech stack ของโปรเจกต์ ALIGN โดยตรง: **จำเป็นต้องใช้ Firebase/Firestore** เป็นข้อกำหนดบังคับของวิชา/อาจารย์ผู้สอน — ไม่ใช่ความชอบของทีมที่เปลี่ยนใจได้ ซึ่งขัดกับคำแนะนำเดิมในรอบสัมภาษณ์ที่ 1 ของ [[../02-design/02-technical/align-tech-stack|align-tech-stack]] ที่ปฏิเสธ Firebase ไว้โดยเจตนา (หัวข้อ 2.2/2.3 เดิม — เหตุผล: Firestore เป็น NoSQL ไม่เหมาะกับโมเดลข้อมูลเชิงสัมพันธ์ที่เข้มงวดของระบบนี้ และ Firebase เป็น proprietary ล้วน ไม่ portable/self-host ไม่ได้) เพราะตอนนั้นยังไม่รู้ข้อจำกัดนี้

## สิ่งที่เปลี่ยน

ปรับ [[../02-design/02-technical/align-tech-stack|align-tech-stack.md]] ทั้งไฟล์ให้สอดคล้องกับ Firebase เป็นแกนหลัก โดย**คงเนื้อหารอบที่ 1 ไว้ทุกจุด (ไม่ลบทิ้ง)** แล้วเพิ่มคำอธิบายรอบที่ 2 ต่อท้าย/แทรกเพื่อ traceability ว่าทำไมตอนนี้ยอมรับ trade-off ที่เคยปฏิเสธ:

- **หัวข้อ 1**: เพิ่มตารางสัมภาษณ์รอบที่ 2 (ข้อ 1.4–1.7) บันทึกข้อกำหนดบังคับ Firebase, ขอบเขตที่ยังไม่ยืนยัน (เฉพาะ Firestore หรือทั้ง suite), เงื่อนไข portable ที่ผ่อนคลายลงสำหรับชั้น database เท่านั้น, และบริบทการใช้งานจริง (งานส่งวิชา vs deploy จริง) ที่ยังไม่ยืนยัน
- **หัวข้อ 2.2 (Backend/API)**: ยังใช้ Next.js API Routes/Server Actions แต่เรียก Firestore ผ่าน Firebase Admin SDK — เสนอ **Firebase App Hosting** เป็น deploy target แทน Vercel (ทางเลือกอื่น: Cloud Functions 2nd gen + Hosting rewrites)
- **หัวข้อ 2.3 (Database)**: เปลี่ยนจาก PostgreSQL/Supabase เป็น **Cloud Firestore** พร้อมระบุผลกระทบสำคัญ 3 ข้อ: (1) โมเดลข้อมูลเชิงสัมพันธ์ทั้งหมดใน `align-api-schema-design.md` ต้องออกแบบใหม่เป็น denormalization/subcollection/Security Rules, (2) เป็นงานที่ต้องส่งต่อ `api-schema-designer`/`technical-designer`, (3) portability เสียไปถาวรสำหรับชั้นนี้ — **ระบุชัดว่าเป็น trade-off ที่ยอมรับเพราะข้อกำหนดบังคับ ไม่ใช่เพราะเหตุผลทางเทคนิคที่ดีกว่าเดิม** (เหตุผลเดิมที่เลือก PostgreSQL ยังเป็นจริงอยู่ทั้งหมด)
- **หัวข้อ 2.4 (AI/LLM)**: คงแนวทาง hybrid เดิม แต่เพิ่มการวิเคราะห์ cold start/memory ของ Transformers.js เมื่อรันบน Firebase App Hosting (Cloud Run) เทียบกับ Cloud Functions ดั้งเดิม และประเมิน Vertex AI เป็นทางเลือกเพิ่มเติม (ปฏิเสธเพราะมีค่าใช้จ่ายและซับซ้อนเกินจำเป็น)
- **หัวข้อ 2.5 (Evidence storage)**: เปลี่ยนจาก Supabase Storage เป็น **Firebase Cloud Storage** — ระบุชัดว่า**ทางย้าย self-hosted MinIO ที่เคยวางแผนไว้ใช้ไม่ได้แล้ว** (Firebase Storage ไม่ใช่ S3-compatible) เป็นความเสี่ยงเพิ่มเติมที่บันทึกไว้ในหัวข้อ 4
- **หัวข้อ 2.6 (Hosting)**: เปลี่ยนจาก Vercel+Supabase Cloud เป็น **Firebase App Hosting + Firebase project เดียว** — เพิ่มข้อควรระวังเรื่องงบประมาณ: Firebase App Hosting และการเรียก external API **ต้องใช้ Blaze plan (pay-as-you-go)** ไม่ใช่ Spark free tier เฉยๆ ต้องผูก billing account ล่วงหน้า (ข้อมูลใหม่ที่กระทบข้อ 2.1 งบประมาณที่ยังไม่ทราบ)
- **หัวข้อ 2.7 (Auth)**: เปลี่ยนจาก Supabase Auth เป็น **Firebase Authentication** — ยังคงหลักการเดิม (แยก role/status/scope ไว้ใน Firestore collection `users` ต่างหาก ไม่ใช่แค่ auth custom claims) SSO SAML ยังต้องอัปเกรด Google Cloud Identity Platform (คล้ายข้อจำกัดเดิมของ Supabase Pro/Enterprise)
- **หัวข้อ 3 (Mapping)**: ปรับตาราง mapping logical component ให้สะท้อนเทคโนโลยีใหม่ (คงคอลัมน์รอบที่ 1 ไว้เทียบ)
- **หัวข้อ 4 (ประเด็นที่ยังไม่ยืนยัน)**: อัปเดตทุกแถวที่กระทบ (งบ/data residency/ที่เก็บไฟล์/deployment) + เพิ่ม 2 แถวใหม่ (ขอบเขตข้อกำหนดบังคับ, บริบทงานส่งวิชา vs deploy จริง)
- **หัวข้อ 4.1 (ใหม่)**: บันทึกคำถามที่ยังค้าง 4 ข้อ พร้อม 3 ตัวเลือก + ข้อดี/ข้อเสียแต่ละข้อ (เพราะ `AskUserQuestion` ไม่พร้อมใช้งานในบริบทการทำงานนี้ — ดูหัวข้อ "คำถามที่ยังไม่ได้คำตอบ" ด้านล่าง)
- **หัวข้อ 5**: เพิ่มหมายเหตุแจ้ง `technical-designer` ว่า §5 ของ `align-technical-design.md` ยังชี้มาถูกที่ แต่เนื้อหาที่ชี้มาหาเปลี่ยนไปมาก
- **หัวข้อ 6 (ใหม่)**: ระบุงานต่อเนื่องที่ต้องส่งต่อ `api-schema-designer` (ออกแบบ Firestore data model ใหม่ทั้งฉบับ) และ `technical-designer` (ปรับ §2/§3 ให้สอดคล้อง) พร้อมลำดับที่แนะนำ

## คำถามที่ยังไม่ได้คำตอบ (ต้องสัมภาษณ์ผู้ใช้เพิ่มก่อนถือว่าปิดงานสมบูรณ์)

เครื่องมือ `AskUserQuestion` ไม่พร้อมใช้งานในบริบทการทำงานนี้ จึงบันทึกคำถามทั้งหมดไว้ในหัวข้อ 4.1 ของ `align-tech-stack.md` แทน (พร้อม 3 ตัวเลือก+ข้อดีข้อเสียแต่ละข้อ) และสรุปสั้นในรายงานที่ส่งกลับผู้เรียกงาน:

1. **ขอบเขตที่แท้จริงของ "ต้องใช้ Firebase"** — เฉพาะ Firestore database หรือทั้ง Firebase suite (Auth+Storage+Hosting ด้วย)
2. **เงื่อนไข portable/self-host** ที่เคยต้องการยังจำเป็นอยู่ไหมสำหรับส่วนที่ Firebase ไม่ได้บังคับตรงๆ
3. **บริบทของโปรเจกต์** — งานส่งวิชา/ต้นแบบวิชาการที่ใช้ข้อมูลจำลอง vs ตั้งใจ deploy ใช้งานจริงกับข้อมูลนักศึกษาจริง (กระทบความเข้มงวดของ PDPA/data residency)
4. **งบ/data residency/SSO/deployment** ที่เคยตอบ "ยังไม่ทราบ" มีอะไรเปลี่ยนไปหรือไม่ตอนนี้ที่รู้ว่าต้องใช้ Firebase

ระหว่างรอคำตอบ เอกสารใช้ default ที่ระบุไว้ชัดเจนในหัวข้อ 4/4.1 ของ `align-tech-stack.md` (ทั้ง Firebase suite, ยอมรับ full lock-in สำหรับ database, สมมติเป็นต้นแบบวิชาการก่อน) — **ไม่ถือเป็นการตัดสินใจสุดท้าย**

## อัปเดต (2026-09-05, ต่อเนื่องในวันเดียวกัน): ปิดคำถามค้างทั้ง 4 ข้อ — รอบที่ 3

ผู้ใช้ตอบคำถามที่ค้างไว้ในหัวข้อ 4.1 ของ `align-tech-stack.md` ครบทั้ง 4 ข้อแล้ว:

1. **ขอบเขตข้อกำหนดบังคับ (คำถามที่ 1)** → **เลือกตัวเลือก B — ทั้ง Firebase suite** ต้องใช้ Firebase Authentication, Cloud Firestore, Cloud Storage, และ Firebase Hosting ครบทุกส่วน ไม่ใช่แค่ Firestore อย่างเดียวแล้วคง Vercel/Supabase Auth ไว้
2. **เงื่อนไข portable/self-host (คำถามที่ 2)** → **เลือกตัวเลือก A — ไม่จำเป็นแล้ว** ยอมรับว่าระบบผูกกับ Firebase ถาวร (lock-in เต็มรูปแบบทุกชั้น) เป็นผลตามมาที่ยอมรับได้ เพราะเลือกใช้ทั้ง suite ไปแล้วตามข้อ 1
3. **บริบทโปรเจกต์ (คำถามที่ 3)** → **เลือกตัวเลือก A — ไม่ deploy จริงกับข้อมูลนักศึกษาจริง** ใช้งานเฉพาะอาจารย์ผู้สอนเท่านั้น — ความเข้มงวดของ PDPA/data residency (กฎ #5) ยังคงออกแบบไว้ในสเปคเต็มรูปแบบเหมือนเดิม ไม่ใช่ข้ออ้างให้ลดทอนการออกแบบ เพียงแต่ลดความเร่งด่วนเชิง legal ของ conflict data residency ในตอนนี้
4. **งบ/data residency/SSO/deployment สุดท้าย (คำถามที่ 4)** → **เลือกตัวเลือก A — ไม่มีอะไรเปลี่ยน** ยังไม่ทราบ/ตัดสินใจทีหลังเหมือนเดิมทุกข้อ — ประเด็นเหล่านี้ยังคงเปิดค้างอยู่จริง ไม่ได้ถูกปิดในรอบนี้

### สิ่งที่แก้ไขใน `align-tech-stack.md` (รอบที่ 3)

- **บล็อกสถานะบนสุด**: เพิ่มพารากราฟ "สถานะ (รอบที่ 3)" สรุปคำตอบทั้ง 4 ข้อ และเพิ่มหมายเหตุสำคัญเรื่องบริบทการใช้งาน (เฉพาะอาจารย์ผู้สอน ไม่ใช่ production กับข้อมูลนักศึกษาจริง — แต่ยังต้องออกแบบตามกฎ PDPA #5 ให้ครบถ้วน)
- **หัวข้อ 1**: เพิ่มตารางสัมภาษณ์ "รอบที่ 3" บันทึกคำตอบยืนยันทั้ง 4 ข้อ พร้อมทำเครื่องหมาย "(ปิด)" ที่แถวเดิมของรอบที่ 2 (ข้อ 1.5–1.7) ชี้ไปตารางใหม่
- **หัวข้อ 2.2 (Backend/Hosting)**: ปิดเงื่อนไข "ถ้าบังคับเฉพาะ Firestore ก็ยังคง Vercel เป็น hosting ได้" — ยืนยันแล้วว่าไม่ใช่ทางเลือกที่เปิดอยู่ เก็บข้อความเดิมไว้พร้อมทำเครื่องหมายปิด (traceability)
- **หัวข้อ 2.3 (Database)**: เพิ่มหมายเหตุยืนยันว่าเงื่อนไข portable ไม่จำเป็นแล้วสำหรับ**ทุกชั้น** ไม่ใช่แค่ database
- **หัวข้อ 2.5 (Evidence storage)**: ปิดทางเลือก "Supabase Storage คู่กับ Firestore ถ้าขอบเขตแคบกว่านี้" — ยืนยันว่า Firebase Cloud Storage เป็นทางเลือกสุดท้าย
- **หัวข้อ 2.6 (Hosting)**: ปิดทางเลือก "Vercel+Firebase แยก" อย่างถาวร และปิดคำถามเรื่อง billing account ที่ยังไม่ยืนยัน (ยังไม่ทราบเหมือนเดิม)
- **หัวข้อ 2.7 (Auth)**: เพิ่มหมายเหตุยืนยันว่า Firebase Authentication เป็นทางเลือกสุดท้าย ไม่ใช่ทางเลือกที่ต้องเปรียบเทียบกับ Supabase Auth อีกต่อไป
- **หัวข้อ 4 (ตารางประเด็นค้างคา)**: เพิ่มหมายเหตุอัปเดตรอบที่ 3 ต้นตาราง, ทำเครื่องหมาย ~~ขีดฆ่า~~ 2 แถวที่ปิดแล้ว (ขอบเขตข้อกำหนดบังคับ, บริบทการใช้งานจริง), ปรับ migration path ของแถว "งบประมาณ"/"deployment สุดท้าย" ให้ตัดทางเลือก "กลับไป Vercel" ที่ปิดแล้วออก, เพิ่มหมายเหตุยืนยันในแถว "Data residency" ว่าไม่ใช่ conflict เร่งด่วนตอนนี้เพราะบริบทเป็นต้นแบบวิชาการ
- **หัวข้อ 4.1**: ทำเครื่องหมาย "[ยืนยันแล้ว 2026-09-05]" ที่หัวข้อคำถามทั้ง 4 ข้อ พร้อมระบุตัวเลือกที่เลือก/ไม่ได้เลือกในแต่ละ bullet (คงตัวเลือกอื่นไว้ทั้งหมดเพื่อ traceability)
- **หัวข้อ 5**: เพิ่มพารากราฟ "อัปเดตรอบที่ 3" แจ้งว่าเอกสารนี้ปิดสมบูรณ์แล้ว ไม่มีเงื่อนไขค้างที่จะกระทบทิศทาง §5/§2/§3 ของ `align-technical-design.md` อีกต่อไป
- **หัวข้อ 6**: ทำเครื่องหมายขั้นตอน (1) "ปิดคำถามค้างในหัวข้อ 4.1" ว่าเสร็จแล้ว พร้อมให้เริ่มขั้นตอน (2) ได้ทันที
